# Семинар к Лекции 8. Docker Compose

В этом конспекте мы с нуля собираем стек **FastAPI + PostgreSQL + Redis** одним
файлом `compose.yaml`. Цель — увидеть своими глазами, как сервисы находят друг
друга по имени, как healthcheck выстраивает порядок старта и как named volume
сохраняет данные БД между перезапусками. Всё это — базовый набор, на котором
дальше собирается любое многосервисное приложение.

Работать удобнее в терминале, повторяя каждую команду у себя и сверяя вывод с
ожидаемым — так материал закрепляется гораздо лучше, чем при чтении.

## Что понадобится

- Docker с плагином Compose: проверьте `docker compose version` — плагин
  `docker compose` не ниже 2.20 (сейчас актуальны 2.3x и v5, они тоже подходят).
  Нужен именно `docker compose` (через пробел), а не старый `docker-compose`.
- Один раз заранее стоит скачать образы, чтобы потом не ждать (`docker pull`
  принимает только один образ за раз, поэтому три команды):
  ```bash
  docker pull postgres:16
  docker pull redis:7
  docker pull python:3.12-slim
  ```
- Пустая рабочая папка, например `~/compose-demo`.
- Свободный порт 8000 на машине (проверить: `lsof -i :8000` — пустой вывод
  значит, что порт свободен). Если занят — см. подсказку в разделе 1.

Набор файлов, который мы соберём по ходу дела:

```
compose-demo/
├── compose.yaml
├── compose.override.yaml   # раздел 6, для dev-среды
├── .env
├── .gitignore
├── Dockerfile
├── requirements.txt
└── main.py
```

## 0. Разминка: почему не набор docker run

Представьте задачу: поднять приложение из API, базы и кэша только через
`docker run`. Что для этого пришлось бы сделать вручную?

> Нужно вручную: создать сеть, запустить 3 контейнера с `--network`, `-p`,
> `-e`, в правильном порядке, а потом всё это останавливать и чистить по одному.
> Одна опечатка в имени сети — сервисы не видят друг друга.

Docker Compose заменяет весь этот набор команд одним декларативным файлом. Мы
описываем, *что* должно работать, а не *как* это запускать по шагам.

## 1. Минимальный compose: api + cache

Сначала соберём само приложение. Создаём папку и файлы:

```bash
mkdir ~/compose-demo && cd ~/compose-demo
```

`main.py` — крошечный FastAPI, который умеет пинговать БД и кэш **по имени**:

```python
import os
import psycopg
import redis
from fastapi import FastAPI

app = FastAPI()
R = redis.from_url(os.environ["REDIS_URL"])

@app.get("/health")
def health():
    try:
        with psycopg.connect(os.environ["DATABASE_URL"], connect_timeout=2) as c:
            c.execute("SELECT 1")
        db_ok = True
    except Exception:
        db_ok = False
    try:
        R.ping(); cache_ok = True
    except Exception:
        cache_ok = False
    return {"db": db_ok, "cache": cache_ok}

@app.get("/hit")
def hit():
    return {"hits": R.incr("hits")}
```

`requirements.txt`:

```
fastapi
uvicorn[standard]
psycopg[binary]
redis
```

`Dockerfile`:

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

Теперь первый `compose.yaml` — только api и cache, чтобы увидеть минимум:

```yaml
services:
  api:
    build: .
    ports: ["8000:8000"]
    environment:
      DATABASE_URL: postgresql://app:secret@db:5432/app
      REDIS_URL: redis://cache:6379/0
  cache:
    image: redis:7
```

Запускаем:

```bash
docker compose up -d --build
docker compose ps
```

**Ожидаемый вывод `ps`:** две строки — `compose-demo-api-1` и
`compose-demo-cache-1`, в колонке `STATUS` — `Up …` (например, `Up 5 seconds`),
у api в `PORTS` — `0.0.0.0:8000->8000/tcp`.

> **Если порт 8000 занят**, `up` завершится ошибкой вида
> `Bind for 0.0.0.0:8000 failed: port is already allocated` (или
> `address already in use`). Поменяйте **левую** часть — порт на хосте:
> `ports: ["8001:8000"]`. Правая часть (8000 — порт внутри контейнера) остаётся
> прежней. Тогда во всех `curl` ниже обращайтесь к `localhost:8001` вместо
> `localhost:8000`.

Обратите внимание: сеть мы руками не создавали. Compose сам завёл сеть проекта и
подключил к ней оба сервиса. Имя контейнера формируется как
`<проект>-<сервис>-<номер>`.

Проверяем кэш:

```bash
curl localhost:8000/hit
curl localhost:8000/hit
curl localhost:8000/health
```

**Ожидаемый вывод:** `{"hits":1}`, затем `{"hits":2}` — счётчик живёт в Redis.
Последняя команда вернёт `{"db":false,"cache":true}`: Postgres ещё нет, поэтому
`db:false` — это нормально.

## 2. Связь сервисов по DNS-имени — ключевая идея

Обратите внимание: в `REDIS_URL` стоит хост **`cache`** — это имя сервиса, не IP.
Убедимся, что это работает через встроенный DNS. Зайдём внутрь контейнера api:

```bash
docker compose exec api sh
# теперь мы внутри контейнера api
getent hosts cache      # имя cache резолвится в IP сети Compose
python -c "import redis,os; print(redis.from_url(os.environ['REDIS_URL']).ping())"
exit
```

**Ожидаемый вывод:** строка вида `172.18.0.2      cache` (IP у вас будет свой),
затем `True`.

Внутри сети Compose `cache` — это полноценное имя хоста. Docker поднял свой DNS,
который резолвит имена сервисов. Именно поэтому в коде мы пишем
`redis://cache:6379`, а не адрес: адрес может меняться при пересоздании
контейнера, а имя сервиса стабильно.

Важная деталь: имя хоста жёстко связано с именем сервиса. Если переименовать
сервис `cache` → `redis` в yaml, то и `REDIS_URL` придётся поменять. Имя хоста =
имя сервиса, один к одному.

## 3. Добавляем PostgreSQL + healthcheck + depends_on

Теперь добавим базу и правильный порядок старта. Дополняем `compose.yaml`:

```yaml
services:
  api:
    build: .
    ports: ["8000:8000"]
    environment:
      DATABASE_URL: postgresql://app:secret@db:5432/app
      REDIS_URL: redis://cache:6379/0
    depends_on:
      db: {condition: service_healthy}
      cache: {condition: service_started}
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 5s
      retries: 5
  cache:
    image: redis:7
volumes:
  pgdata:
```

Применяем изменения:

```bash
docker compose up -d
docker compose ps
```

Compose не пересоздаёт весь стек: он создаст только новый сервис `db` и том
`compose-demo_pgdata`, а api и cache оставит работать (в выводе `up` у них
`Running`). Зато перед тем как отпустить терминал, `up` дождётся готовности БД —
в выводе видно `Container compose-demo-db-1 Waiting`, а через несколько секунд
`Healthy`.

**Ожидаемый вывод `ps`:** три сервиса со статусом `Up …`; у `db` в колонке
статуса — `Up 5 seconds (healthy)`. Если заглянуть в `ps` раньше, чем пройдёт
первый healthcheck (например, из другого терминала), там будет
`(health: starting)`.

Проверяем, что api теперь видит и БД, и кэш:

```bash
curl localhost:8000/health
```

**Ожидаемый вывод:** `{"db":true,"cache":true}`.

Главное здесь — про порядок старта:

> `depends_on` с `condition: service_healthy` заставляет Compose **дождаться**,
> пока healthcheck БД станет зелёным, и только потом запускать api. Без этого api
> стартовал бы одновременно с БД и мог упасть на первом же соединении —
> Postgres ещё не успел принять подключения.

Сейчас api уже был запущен, поэтому порядок толком не виден. Он хорошо заметен
при старте стека с нуля (это будет в разделе 5, после `down`): в выводе `up`
сначала идёт `compose-demo-db-1 Healthy`, и только потом
`compose-demo-api-1 Starting`.

Посмотрим, чем healthcheck отличается от «просто запущен»:

```bash
docker inspect --format '{{.State.Health.Status}}' compose-demo-db-1
```

**Ожидаемый вывод:** `healthy`. Разница принципиальна: `service_started` ждёт
только запуск процесса, `service_healthy` — готовность принимать работу.

## 4. Жизненный цикл: logs / exec / ps

Разберём повседневные команды. Логи всего стека и одного сервиса:

```bash
docker compose logs --tail 20        # последние 20 строк лога КАЖДОГО сервиса
docker compose logs -f api           # живой лог только api (Ctrl+C выйти)
```

Пока `logs -f api` открыт, сделайте в соседнем терминале `curl localhost:8000/hit`
— в логе сразу появится строка `"GET /hit HTTP/1.1" 200 OK`.

`logs -f` — первое, куда стоит смотреть, когда сервис не поднялся. Слева у каждой
строки помечено, от какого сервиса пришёл лог (`api-1  | …`, `db-1  | …`).

Заходим внутрь БД настоящим psql — прямо через exec, без установки клиента на хост:

```bash
docker compose exec db psql -U app -d app -c "SELECT version();"
```

**Ожидаемый вывод:** табличка с колонкой `version` и одной строкой вида
`PostgreSQL 16.x (Debian …) on …`, внизу `(1 row)`.

Важная деталь: `exec` работает только с **уже запущенным** контейнером. Если
сервис остановлен или упал, `exec` ответит `service "api" is not running`.
Тогда можно запустить **новый разовый** контейнер того же сервиса:
`docker compose run --rm api sh`. Это не вход в упавший контейнер, а свежий
контейнер из того же образа (имя вида `compose-demo-api-run-…`), который
удалится после выхода (`--rm`). Он годится, чтобы проверить окружение, файлы и
сеть, но состояние упавшего контейнера в нём не увидеть — для разбора падения
смотрите `docker compose logs api`.

Статус и остановка одного сервиса:

```bash
docker compose ps
docker compose stop cache
docker compose ps          # cache пропал из списка: ps показывает только работающие
docker compose ps -a       # с -a видно и остановленные: cache в статусе Exited (0)
docker compose start cache
docker compose ps          # cache снова Up
```

Пока cache остановлен, `curl localhost:8000/health` вернёт
`{"db":true,"cache":false}` — api жив, но до Redis не достучаться.

## 5. Named volume: данные переживают перезапуск — кульминация

Самое важное про volumes. Кладём данные в БД:

```bash
docker compose exec db psql -U app -d app -c \
  "CREATE TABLE students(name text); INSERT INTO students VALUES ('Ivan');"
docker compose exec db psql -U app -d app -c "SELECT * FROM students;"
```

**Ожидаемый вывод:** первая команда ответит `CREATE TABLE` и `INSERT 0 1`,
вторая — табличку с колонкой `name` и строкой `Ivan`, внизу `(1 row)`.

Теперь **пересоздаём контейнеры** (не удаляя том) и проверяем, что данные на месте:

```bash
docker compose down          # удалили контейнеры и сеть, том pgdata остался
docker compose up -d
docker compose exec db psql -U app -d app -c "SELECT * FROM students;"
```

**Ожидаемый вывод:** снова `Ivan`.

Это ядро всей темы:

> Контейнер эфемерный — при `down` он удалён, при `up` создан заново. Но данные
> лежали не в контейнере, а в **томе `pgdata`**, смонтированном в
> `/var/lib/postgresql/data`. Том — отдельная сущность, он пережил пересоздание.

Убедимся, что том действительно существует отдельно:

```bash
docker volume ls | grep compose-demo
```

**Ожидаемый вывод:** `local     compose-demo_pgdata` — Compose добавляет к имени
тома префикс проекта (`<проект>_<том>`).

Теперь — контрпример. Удаляем стек **вместе с томом**:

```bash
docker compose down -v       # -v удаляет и volume
docker compose up -d
docker compose exec db psql -U app -d app -c "SELECT * FROM students;"
```

**Ожидаемый вывод:** `ERROR:  relation "students" does not exist` — данных нет:
`down -v` удалил том, и `up` создал пустую базу заново.

Запомните: `down -v` стирает тома. На проде флаг `-v` — это фактически «удалить
базу», поэтому его случайно не набирают.

## 6. .env и override под среды

Вынесем секреты из yaml в `.env`:

```bash
printf "DB_USER=app\nDB_PW=secret\n" > .env
echo ".env" >> .gitignore
```

Сам по себе `.env` ничего не меняет — нужно, чтобы `compose.yaml` на него
ссылался. Заменяем хардкод логина и пароля подстановкой `${...}` (меняются
`DATABASE_URL` у api, `POSTGRES_USER`/`POSTGRES_PASSWORD` и healthcheck у db):

```yaml
services:
  api:
    build: .
    ports: ["8000:8000"]
    environment:
      DATABASE_URL: postgresql://${DB_USER}:${DB_PW}@db:5432/app
      REDIS_URL: redis://cache:6379/0
    depends_on:
      db: {condition: service_healthy}
      cache: {condition: service_started}
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: ${DB_USER}
      POSTGRES_PASSWORD: ${DB_PW}
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${DB_USER}"]
      interval: 5s
      retries: 5
  cache:
    image: redis:7
volumes:
  pgdata:
```

Compose читает `.env` из папки проекта автоматически. Посмотреть, каким он видит
итоговый файл после подстановки, помогает `docker compose config`:

```bash
docker compose config | grep -E 'DATABASE_URL|POSTGRES_|pg_isready'
```

**Ожидаемый вывод:** вместо `${...}` подставлены реальные значения:

```
      DATABASE_URL: postgresql://app:secret@db:5432/app
      POSTGRES_DB: app
      POSTGRES_PASSWORD: secret
      POSTGRES_USER: app
        - pg_isready -U app
```

Если переменной нет в `.env`, Compose предупредит
`The "DB_USER" variable is not set. Defaulting to a blank string.` и подставит
пустую строку — это частая причина `{"db":false}`. Значения в `.env` те же, что
были в yaml, поэтому `docker compose up -d` после этой правки ничего не
пересоздаст, и `curl localhost:8000/health` по-прежнему вернёт
`{"db":true,"cache":true}`.

`.env` не коммитим — он в `.gitignore`. Для dev-среды удобно держать рядом
`compose.override.yaml` с `--reload` и монтированием кода `.:/app`; Compose сам
подхватит override поверх базового файла при обычном `up`:

```yaml
services:
  api:
    command: ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000", "--reload"]
    volumes:
      - .:/app
    environment:
      WATCHFILES_FORCE_POLLING: "true"   # на Docker Desktop без этого --reload может не замечать правок
```

После `docker compose up -d` правки в `main.py` применяются без пересборки: в
`docker compose logs api` появится `WatchFiles detected changes in 'main.py'. Reloading...`.

Когда закончили — уберите за собой (том с базой тоже удалится):

```bash
docker compose down -v
```

## Частые ошибки

- **`docker-compose` не найден** — используется старый синтаксис; нужен
  `docker compose` (плагин v2, через пробел).
- **`{"db":false}` в /health** — забыт `condition: service_healthy` или опечатка
  в имени хоста `db` в `DATABASE_URL`. Имя хоста обязано совпадать с именем сервиса.
- **api падает при старте** — стартовал раньше БД; лечится healthcheck +
  `depends_on: {condition: service_healthy}`.
- **«Данные пропали после down»** — забыта секция `volumes:` или том смонтирован не в
  `/var/lib/postgresql/data`; либо случайно сделан `down -v`.
- **Порт занят** (`port is already allocated` или `address already in use`) —
  на хосте уже висит что-то на 8000; поменяйте левую часть
  `ports: ["8001:8000"]` и обращайтесь к `localhost:8001`.
- **`exec` пишет `service "api" is not running`** — контейнер остановлен или
  упал. `docker compose run --rm api sh` не «оживит» его, а создаст новый разовый
  контейнер из того же образа; причину падения ищите в `docker compose logs api`.
- **Правки в yaml не применились** — забыли выполнить `docker compose up -d`
  заново; если менялись `main.py`, `requirements.txt` или `Dockerfile`, образ
  нужно пересобрать: `docker compose up -d --build`.
