## Git – II. Ветки и слияние.

На прошлой паре мы научились делать снимок: индекс, `commit`, объекты в `.git`, `reset`, remote, `push` и `pull`. Там была **одна** ветка – `main` или `master`. Сегодня появляется вторая (и третья) **наклейка** на том же складе снимков: фича параллельно, слияние, конфликт и то, что на самом деле делает `git pull`, когда истории разъехались.

---



## **Сегодня пройдемся по этому плану:**

1. **Ветка уже была** – просто одна, сегодня их несколько.
2. **Зачем вторая ветка** – фича, коллега, не ломая `main`.
3. **Указатели** – `branch`, `switch`, коммит на `feature`.
4. **DAG** – родитель, два родителя, `--graph --all`.
5. **Слияние** – общий предок и четыре исхода: FF, merge-коммит, `--no-ff`, `Already up to date`.
6. **Адресация коммитов** – `HEAD~1`, `HEAD^1`, `HEAD^2` у merge.
7. **Конфликт** – одна строка, `diff`, `add`, `commit` или `--abort`.
8. **Откаты** – `--abort`, `reset --hard`, `revert` на общей ветке.
9. **Remote и ветки** – `origin/main`, `fetch`, `pull`, отказ `push`.
10. **Новая ветка на сервере** – `push -u origin feature`.
11. **Stash** – черновик, `list`, `pop` и `apply`.
12. **Detached HEAD** – посмотреть старый снимок, не потерять коммит.
13. **Сценарии из работы** – hotfix, отстали от `origin`, откат на общей ветке.
14. **Приёмы** – `switch -`, `status -sb`, `diff main...feature`, алиас на граф.

**Что понадобится:** репозиторий с прошлой пары (хотя бы два коммита на `main`). Если стёрли – заведите снова:

```bash
mkdir -p ~/Desktop/devtools-git-2 && cd ~/Desktop/devtools-git-2
git init
echo 'print("v1")' > app.py
git add app.py && git commit -m "C1: v1"
echo 'print("v2")' >> app.py
git add app.py && git commit -m "C2: v2"
```

Дальше все примеры из **этой же папки**, по порядку разделов: не перескакивайте к merge, пока не сделали ветку `feature`, и не удаляйте ветку до слияния.

---



## **Ветка у вас уже была.**

Вы уже жили на ветке. После `git init` и первого `commit` указатель `main` (или `master`) сдвигался вперёд на каждый снимок. `git reset` на прошлой паре **двигал ветку** – вы это помните.

> **Ветка** – подвижное **имя** на коммит. Файл в `.git/refs/heads/main` хранит хеш вершины. Новый `commit` на этой ветке переписывает имя на новый хеш.

> **HEAD** – «где я сейчас». Обычно `.git/HEAD` содержит `ref: refs/heads/main`: вы стоите **на ветке** `main`, а ветка указывает на коммит.

```bash
cat .git/HEAD
# получается: ref: refs/heads/main
# или:        ref: refs/heads/master

git rev-parse HEAD
# rev-parse – покажи хеш, на который сейчас смотрит HEAD

git rev-parse main
# то же число, пока HEAD на main
```

Сегодня заводим **второе** имя – например `feature`. Это не вторая папка проекта и не zip-копия. Это вторая наклейка на графе объектов в `.git`.

Говорим **ветка**, не «линия истории»: в Git важны имена указателей и коммиты, а не метафора линейки.

---



## **Зачем вторая ветка.**

Пока коммиты идут гуськом, вторая ветка не нужна. Она нужна, когда:

1. **Фича** – правите неделю, а `main` должна оставаться рабочей для демо и для `push`.
2. **Два человека** – у каждого своя ветка, потом слияние в общую.
3. **Эксперимент** – можно выбросить имя `experiment`, не трогая `main`.

Без Git снова появляются `project_copy`, `project_final`. С Git – два указателя на **общий** прошлый коммит и разные будущие.

```text
        C1 ──► C2 ──► C3
                      │
                      ├──► D ──► E   (ветка feature)
                      │
                      └── main остаётся на C3, пока вы не сольёте
```

Ловушка: «ветка = папка на диске» – нет. На диске одна рабочая копия. `git switch` **пересобирает** файлы под выбранный снимок.

---



## **Создаём ветку и переключаемся.**

Посмотрим список имён:

```bash
git branch
# branch – список локальных веток
# звёздочка * – на какой ветке стоит HEAD
# получается: * main
```

Создать ветку и сразу встать на неё:

```bash
git switch -c feature
# switch – переключи рабочую копию и HEAD на другую ветку
# -c     – create (создай ветку от текущего коммита и перейди)

git branch
# получается:   main
#            * feature
```

`feature` родилась **от того коммита**, где вы стояли. Пока новых коммитов нет, `main` и `feature` указывают на **один и тот же** хеш. Два имени – одна вершина.

Старый вариант той же операции: `git checkout -b feature` (`checkout` – переключи дерево, `-b` – branch, создай). Сейчас роли разделены: `switch` – ветки, `restore` – файлы (его вы уже умеете).

Сделаем коммит **только** на `feature`:

```bash
echo 'print("feature")' >> app.py
git add app.py
git commit -m "F1: строка только на feature"

git log --oneline --decorate --graph --all
# --oneline  – короткий хеш и сообщение
# --decorate – имена веток у коммитов
# --graph    – ASCII-граф родителей
# --all      – все локальные ветки, не только текущая
# получается что-то вроде:
# * a1b2c3 (HEAD -> feature) F1: строка только на feature
# * d4e5f6 (main) C2: v2
# * ...
```

`HEAD -> feature` – вы на ветке. Коммит сдвинул **только** `feature`. `main` осталась на `C2`.

Переключимся обратно:

```bash
git switch main
# switch – встань на ветку main (пересобери файлы)

cat app.py
# получается: без строки print("feature")
# на диске снимок main, не feature
```

Git не «помнит два проекта». Он подставил tree из коммита, на который указывает `main`.

Ветку `feature` **не удаляем** – на ней висит коммит `F1`, к нему вернёмся в разделе про слияние. Переименовать имя можно в любой момент: `git branch -m feature feature-login` (`-m` – move/rename), но в конспекте дальше остаёмся на имени `feature`.

---



## **История как граф.**

Пока был один указатель, история выглядела как цепочка. Это **частный случай** графа.

> **DAG (directed acyclic graph)** – направленный ациклический граф. Каждый commit хранит ссылку на родителя (или на **двух**, если это merge). Стрелки смотрят **в прошлое**. Коммит не может быть своим предком – циклов нет.

![Ветки как указатели на коммиты](https://git-scm.com/book/en/v2/images/branch-and-history.png)

Схема из [Pro Git – ветвление](https://git-scm.com/book/ru/v2/%D0%92%D0%B5%D1%82%D0%B2%D0%BB%D0%B5%D0%BD%D0%B8%D0%B5-%D0%92%D0%B5%D1%82%D0%BA%D0%B8-%D0%9E-%D0%B2%D0%B5%D1%82%D0%B2%D0%BB%D0%B5%D0%BD%D0%B8%D0%B8): кружки – коммиты, имена `main` / `feature` – наклейки на вершинах.

```text
      o───o───o───o  main
               \
                o───o  feature
```

**Ветка – не ребро графа.** Ребро – «родитель» внутри объекта commit. Ветка – человекочитаемое имя на вершине.

Удалить ветку – снять наклейку. Сами коммиты остаются в базе, пока до них дотягивается хоть одно имя.

### **Ловушка: забыли** `--all`.

```bash
git switch feature
git log --oneline
# видите только предков текущей ветки – main «сбоку» может не попасть в вывод

git log --oneline --graph --all
# --all – все локальные ветки
```

Кажется, что «пропала ветка» – она есть, вы смотрите с одной вершины без `--all`.

Сейчас на графе две наклейки: `main` на `C2`, `feature` на `F1` впереди. Дальше – как их снова свести.

---



## **Слияние веток.**

Фича готова. Нужно, чтобы `main` **включала** коммит с `feature`. Важно: `git merge` всегда вливает **в текущую** ветку (ту, на которой стоит HEAD), а не «в ту, что назвали в команде».

### **Правило: общий предок.**

Прежде чем что-то делать, Git находит **общего предка** двух веток.

> **Общий предок (merge base)** – последний коммит, до которого можно дойти из обеих вершин. Точка, где ветки разошлись.

```bash
git merge-base main feature
# merge-base – покажи хеш общего предка двух веток

git rev-parse main
# вершина main
```

Дальше вся логика сводится к одному сравнению – **совпадает ли общий предок с вершиной текущей ветки**:


| Что видит Git                                                | Что делает                     |
| ------------------------------------------------------------ | ------------------------------ |
| общий предок = вершина `main` (`main` не двигалась)            | **fast-forward**: двигает имя  |
| общий предок не равен ни одной вершине (ветки разъехались)     | **merge-коммит** с 2 родителями |
| общий предок = вершина `feature` (всё уже в `main`)            | `Already up to date`, ничего   |


Разберём по очереди все три.

---

### **Случай 1. Fast-forward.**

Условие: после ответвления в `main` **не появилось** новых коммитов, её вершина так и осталась общим предком.

До слияния:

```text
C1 ──► C2 ──► F1
        ▲      ▲
      main   feature
```

`C2` – предок `F1`. Значит, история `feature` уже содержит всё, что есть в `main`. Соединять нечего: достаточно **передвинуть имя** `main` вперёд.

```bash
git switch main
# main на C2, feature на F1 – это вы видели в log --all

git merge feature
# merge – подтяни коммиты feature в ТЕКУЩУЮ ветку (main)
# получается: Updating c0cdccc..1426534
#             Fast-forward
```

После слияния:

```text
C1 ──► C2 ──► F1
               ▲▲
          main feature
```

> **Fast-forward (перемотка)** – слияние без нового коммита: указатель текущей ветки переставляется на вершину вливаемой.

Шаг вперёд сделан: `main` переехала с `C2` на `F1`. Но **нового узла нет** – коммит `F1` уже лежал в базе, его создали на `feature`. Git лишь переписал `.git/refs/heads/main` и пересобрал файлы на диске.

Почему Git не создаёт узел «на всякий случай»: merge-коммит обязан иметь двух родителей, здесь ими были бы `C2` и `F1`. Но `C2` – предок `F1`, такой узел не добавил бы ни одного изменения. Пустая вершина в графе – шум.

Проверяем, что оба имени смотрят в одну точку:

```bash
git rev-parse --short main
git rev-parse --short feature
# получается: два ОДИНАКОВЫХ хеша
# (--short работает с ОДНОЙ ссылкой за раз, поэтому две команды)

git log --oneline --decorate --graph --all
# получается: * 1426534 (HEAD -> main, feature) F1: строка только на feature
```

Раз имена совпали, `feature` можно снимать:

```bash
git branch -d feature
# -d – delete (удали имя; коммит остаётся в истории main)
```

Так обычно заканчивают короткую фичу: ветка прожила час, влилась перемоткой, имя убрали.

---


### **Случай 2. Merge-коммит.**

Условие: пока жила боковая ветка, на `main` тоже сделали коммит. Теперь общий предок **не равен** ни одной вершине – перемотка невозможна.

Разведём ветки руками:

```bash
git switch main
git switch -c feature-merge
echo 'print("side")' >> app.py
git add app.py && git commit -m "F: правка на feature-merge"

git switch main
echo 'only on main' > extra.txt
git add extra.txt && git commit -m "M1: коммит только на main"
```

Перед слиянием картина такая:

```text
              ┌──► F    (feature-merge)
C1 ── C2 ── F1
              └──► M1   (main)
```

`F1` – общий предок. Ни `M1`, ни `F` не является предком другого: каждая ветка знает то, чего не знает вторая. Чтобы свести их в один снимок, Git обязан создать **новую** вершину.

```bash
git merge feature-merge -m "M: слияние feature-merge в main"
# -m – message (текст merge-коммита, чтобы не открывать редактор)
# получается: Merge made by the 'ort' strategy.
```

После слияния:

```text
              ┌──► F ────┐
C1 ── C2 ── F1            M   (HEAD -> main)
              └──► M1 ───┘
```

Вот это и есть «шаг с новым узлом»: `M` появился только что, и он помнит **обоих** родителей.

```bash
git cat-file -p HEAD
# cat-file – показать объект; -p – pretty (читаемый текст)
# получается: tree ...
#             parent <хеш M1>   <- первый родитель: main до слияния
#             parent <хеш F>    <- второй родитель: вливаемая ветка
#             author ...
#             committer ...
#             M: слияние feature-merge в main
```

Порядок родителей не случайный: **первый** – та ветка, на которой вы стояли; **второй** – та, которую вливали. Дальше пригодится: по ним работают `HEAD^1` и `HEAD^2`.

Правки были в **разных** файлах (`extra.txt` против `app.py`) – поэтому Git собрал всё сам, без вопросов. Что будет при правках в одной строке – отдельный раздел про конфликт.

```bash
git log --oneline --decorate --graph --all
# получается: развилка и сведение линий в узле M

git branch -d feature-merge
# -d – delete, Git проверит, что ветка влита
```

---



### **Случай 3. Флаг** `--no-ff`.

Ситуация как в случае 1: `main` не двигалась, Git по умолчанию сделал бы перемотку. Но команде хочется, чтобы в истории **осталась отметка** «здесь влили фичу» – иначе коммиты фичи растворяются в общей цепочке и потом не видно, что было одной задачей.

```bash
git switch main
git switch -c demo-no-ff
echo 'no-ff marker' >> app.py
git add app.py && git commit -m "коммит только на demo-no-ff"

git switch main
git merge demo-no-ff --no-ff -m "merge: demo-no-ff с узлом"
# --no-ff – no fast-forward: создай merge-коммит, даже если можно перемотать
# получается: Merge made by the 'ort' strategy.
```

Сравните с случаем 1. Там было «двигаем имя, узла нет». Здесь:

```text
без --no-ff:   C2 ──► N            main переехала на N

с --no-ff:     C2 ──► N ──┐
                 └────────► M      main на новом узле M,
                                   N остался виден как ветка
```

```bash
git log --oneline --decorate --graph -3
# получается: * merge-коммит, от него две линии вниз

git rev-parse HEAD^1 HEAD^2
# два разных родителя: main до слияния и вершина demo-no-ff
```

Что выбрать в жизни: `--no-ff` – когда ветка равна задаче и хочется видеть её границы в истории (многие команды включают это правилом для pull request'ов). Обычный merge с перемоткой – когда ветка жила час и отдельная отметка не нужна. Для курса важно знать флаг и уметь прочитать оба графа.

---

### **Случай 4. Уже слито.**

Ветку `demo-no-ff` мы только что влили. Повторим команду:

```bash
git merge demo-no-ff
# получается: Already up to date.

git branch -d demo-no-ff
# имя больше не нужно, коммит уже в истории main
```

Значит, вершина названной ветки **уже является предком** вашей: все её коммиты давно в `main`. Частый повод – ветку влили минуту назад и повторили команду. Это не ошибка и не «Git не увидел ветку».

Обратный случай – когда `merge` вроде бы прошёл, а в другую сторону ничего не появилось. Вспоминаем правило: `merge` меняет **только текущую** ветку. Чтобы `feature` тоже узнала про новые коммиты `main`, нужно встать на `feature` и влить `main` уже туда.

### **Имена веток.**

```bash
git branch -m старое-имя новое-имя
# -m – rename (пока ветка существует)

git branch -d имя
# -d – delete, только если ветка слита в текущую

git branch -D имя
# -D – force delete (снять имя даже без merge; коммиты останутся без ссылки)

git branch -vv
# -vv – upstream (связь с origin/…) после git push -u
```

## **Адреса коммитов:** `HEAD`, `~`, `^`.

Запись `HEAD~1` вы уже использовали в `reset`: «на один коммит назад». Пока история была линейной, этого хватало. После merge у коммита **два** родителя, и появляется вторая запись – `^`.

Сейчас на `main` вершина – merge-коммит из прошлого раздела. Проверим:

```bash
git log --oneline -3
# -3 – три верхние строки истории

git rev-parse --short HEAD
# короткий хеш текущего коммита (merge)

git rev-parse --short HEAD^1
# ^1 – ПЕРВЫЙ родитель: та ветка, В КОТОРУЮ вливали (main до merge)

git rev-parse --short HEAD^2
# ^2 – ВТОРОЙ родитель: вершина ветки, КОТОРУЮ вливали
```

Оба хеша разные – это и есть развилка в графе.

```bash
git show --stat HEAD^2
# show  – покажи коммит
# --stat – только имена файлов и счётчик строк
# получается: тот самый коммит боковой ветки
```

Теперь `~` против `^` на живом примере:

```bash
git log --oneline -1 HEAD~1
# ~1 – на один шаг назад ПО ПЕРВОМУ родителю (то же, что HEAD^1)

pp
# ~2 – два шага назад по первой линии родителей
```


| Запись    | Значение                                          |
| --------- | ------------------------------------------------- |
| `HEAD`    | текущий коммит                                    |
| `HEAD~1`  | на один шаг назад по **первому** родителю         |
| `HEAD~2`  | на два шага назад по первым родителям             |
| `HEAD^1`  | первый родитель (для обычного коммита = `HEAD~1`) |
| `HEAD^2`  | **второй** родитель, есть только у merge-коммита  |
| `a1b2c3d` | конкретный коммит по короткому хешу               |


Ловушка: на обычном коммите второго родителя нет, и Git честно скажет:

```text
fatal: ambiguous argument 'HEAD^2': unknown revision or path not in the working tree.
```

Это не поломка, а «у этого коммита один родитель».

Полезно смотреть историю «как будто без боковых веток»:

```bash
git log --oneline --first-parent -5
# --first-parent – идти только по первым родителям
# получается: линия main без коммитов, приехавших из веток
```

Эти же имена работают везде: `git show HEAD~2`, `git diff HEAD~1`, `git reset --hard HEAD~1`, `git switch --detach HEAD~3`.

---



## **Конфликт.**

Конфликт – не поломка. Это сигнал: **одно и то же место** файла изменили по-разному, и автоматический merge не знает, какую версию оставить.

Условие то же, что в случае 2: ветки должны **разъехаться**. Одной правки на `feature` мало – тогда будет обычная перемотка. Нужны две правки одной строки: своя на каждой ветке.

**Шаг 1. Общая отправная точка.**

```bash
git switch main
printf '%s\n' 'print("A")' > app.py
# printf вместо echo: перезаписываем файл целиком одной строкой
git add app.py && git commit -m "A: общая отправная точка"
```

**Шаг 2. Правка на ветке.**

```bash
git switch -c feature-conflict
# если Git ответит: fatal: a branch named ... already exists,
# значит ветка осталась с прошлого прогона: git branch -D feature-conflict

printf '%s\n' 'print("B")' > app.py
git add app.py && git commit -m "B: версия ветки"

git branch
# проверьте звёздочку: коммит должен уйти в feature-conflict, а не в main
```

**Шаг 3. Правка той же строки на** `main`.

```bash
git switch main
printf '%s\n' 'print("C")' > app.py
git add app.py && git commit -m "C: версия main"
```

Теперь ветки разошлись, и обе поменяли **первую строку одного файла**:

```text
              ┌──► B   (feature-conflict)
C1 ── ... ── A
              └──► C   (main)
```

**Шаг 4. Слияние.**

```bash
git merge feature-conflict
# получается: Auto-merging app.py
#             CONFLICT (content): Merge conflict in app.py
#             Automatic merge failed; fix conflicts and then commit the result.
```

Откройте `app.py`:

```text
<<<<<<< HEAD
print("C")
=======
print("B")
>>>>>>> feature-conflict
```

- `<<<<<<< HEAD` – версия **текущей** ветки (`main`), то есть `C`.
- `=======` – разделитель.
- `>>>>>>> feature-conflict` – версия из вливаемой ветки, то есть `B`.

Сотрите маркеры, оставьте одну правду, например:

```text
print("B")
```

Пока маркеры в файле, merge **не завершён**.

```bash
git status
# получается: Unmerged paths
#             both modified: app.py

git diff
# diff – покажет конфликтные куски относительно merge-основания

git add app.py
# add – отметь: конфликт в этом файле решён

git commit
# без -m Git подставит сообщение вроде Merge branch 'feature-conflict'
# или: git commit -m "merge: взяли B"
```

Если передумали целиком:

```bash
git merge --abort
# --abort – отмени merge, верни состояние до git merge
```

Другие виды конфликтов (удалили файл на одной ветке, переименовали на другой) встречаются в работе; алгоритм тот же: `status` → правка → `add` → `commit` или `--abort`.

## **Откаты:** `--abort`, `reset`, `revert`.

Раньше отмена была одна: `reset` двигал единственную ветку. Теперь вопросов три, и команды **разные**.

**1. Merge ещё идёт, в файле маркеры.** Ничего не решено, хотим выйти:

```bash
git merge --abort
# --abort – отмени незавершённое слияние, верни рабочую копию как до merge
```

Работает **только** пока merge не завершён. После `git commit` та же команда ответит:

```text
fatal: There is no merge to abort (MERGE_HEAD missing).
```

Значит, слияние уже стало коммитом – дальше пункт 2 или 3.

**2. Merge уже закоммитили, но на сервер не отправляли.** Можно двигать ветку:

```bash
git log --oneline -1
# сейчас вершина – merge-коммит

git reset --hard HEAD~1
# --hard  – ветка, индекс и файлы к целевому коммиту
# HEAD~1  – первый родитель, то есть main до слияния

git log --oneline -1
# merge-коммита больше нет в этой ветке
```

Вернуть как было:

```bash
git reset --hard ORIG_HEAD
# ORIG_HEAD – где стояла ветка до последней крупной операции
#             (Git записывает его при merge, pull и reset)
```

Поэтому перед `reset --hard` полезно записать текущий хеш: `git rev-parse --short HEAD`.

**3. Коммит уже на сервере, его забрали коллеги.** Историю не переписываем. Нужен **новый** коммит-антидот:

```bash
echo 'сломали поведение' >> app.py
git add app.py && git commit -m "плохой коммит"

git revert HEAD --no-edit
# revert    – создай НОВЫЙ коммит, который отменяет указанный
# HEAD      – какой коммит отменяем (можно короткий хеш)
# --no-edit – не открывать редактор для сообщения

git log --oneline -2
# получается: Revert "плохой коммит", а под ним сам плохой коммит

cat app.py
# строки «сломали поведение» нет, но история цела
```

Отменить **merge-коммит** сложнее: Git должен знать, какую сторону считать основной.

```bash
git revert -m 1 a1b2c3d --no-edit
# -m 1   – mainline: первый родитель (ветка, в которую вливали)
# a1b2c3d – хеш merge-коммита
```


| Ситуация                                  | Команда                       |
| ----------------------------------------- | ----------------------------- |
| маркеры в файле, merge не завершён        | `git merge --abort`           |
| merge закоммитили, **не** пушили          | `git reset --hard HEAD~1`     |
| промахнулись сбросом                      | `git reset --hard ORIG_HEAD`  |
| коммит уже у коллег                       | `git revert <хеш> --no-edit`  |
| надо отменить merge, который уже у коллег | `git revert -m 1 <хеш merge>` |


Правило простое: **своё и локальное –** `reset`**; общее и отправленное –** `revert`**.**

Локально вы уже умеете сливать `feature` в `main`. На сервере та же механика – только указатели называются `origin/main`.

---



## **Ветки на сервере:** `fetch` **и** `pull`.

На прошлой паре вы пушили коммиты на `origin`. Там тоже есть ветка `main` – это **не** ваш локальный файл, а указатель `origin/main`: «где был `main` на сервере в момент последнего `fetch`».

```text
локально:   main ──► C5
на сервере: origin/main ──► C4   (пока вы не сделали fetch)
```

Коллега запушил `C5` на GitHub. У вас его ещё нет.

### **Три указателя.**

```text
main          ваша локальная ветка (её двигает ваш commit)
origin/main   «каким main был на сервере в момент последнего fetch»
рабочая копия файлы на диске (их пересобирает switch / merge / pull)
```

Ни одна команда не двигает все три сразу «сама по себе»: `fetch` трогает только `origin/main`, `commit` – только `main`, `merge` – `main` и диск.

### **Шаг 1. Смотрим:** `fetch`.

```bash
git fetch origin
# fetch  – скачай новые объекты и обнови origin/*
# origin – имя remote
# файлы на диске и локальный main НЕ меняются

git status -sb
# -s – short (короткий вывод)
# -b – branch (строка про ветку сверху)
# получается: ## main...origin/main [behind 2]
```

`behind 2` – на сервере два коммита, которых у вас нет. `ahead 1` – наоборот. Бывает и `[ahead 1, behind 2]`: истории разъехались.

Если remote ещё нет или ветка с ним не связана, строка будет короткой – просто `## main`. Это нормально: сравнивать не с чем.

Посмотреть **что именно** разъехалось:

```bash
git log --oneline HEAD..origin/main
# что есть на сервере и нет у вас

git log --oneline origin/main..HEAD
# что есть у вас и ещё не отправлено
```

Две точки читаются как «от и до»: `A..B` – коммиты, которые есть в `B` и нет в `A`.

### **Шаг 2. Вливаем:** `pull`.

```bash
git pull origin main
# pull   – fetch + влить в ТЕКУЩУЮ ветку
# origin – откуда
# main   – какую ветку сервера вливаем
# по сути: git fetch origin && git merge origin/main
```

Два важных уточнения.

**Первое: вливается в ту ветку, на которой вы стоите.** Стоите на `feature` и делаете `git pull origin main` – вы влили `main` **в** `feature`, а не наоборот.

```bash
git branch
# сначала проверьте звёздочку: куда именно приедут чужие коммиты
```

**Второе: если истории разъехались,** `pull` **делает merge** – с merge-коммитом и, при невезении, с конфликтом. Отсюда мем «столкновение планет»: не магия, а те же два указателя.

![git pull](https://media1.tenor.com/m/B4NCE9Ujl90AAAAC/git-pull.gif)

Конфликт при `pull` разбирается **точно так же**, как локальный:

```bash
git status
# Unmerged paths: app.py

# правите файл, убираете маркеры
git add app.py
git commit
```

Если после `-u` (`git push -u origin main`) ветка связана с `origin/main`, хватает короткой формы:

```bash
git pull
git push
```

Современный Git при расхождении может попросить выбрать стратегию. На курсе договоримся про merge:

```bash
git config --global pull.rebase false
# pull.rebase false – pull всегда сливает (merge), а не перестраивает историю
```

Вариант `git pull --rebase` (и `pull.rebase true`) существует и в командах встречается – он переписывает ваши коммиты поверх чужих. Разбирать его сегодня не будем.

### **Шаг 3. Отказ** `push`.

```text
! [rejected]        main -> main (fetch first)
```

Смысл: на `origin` есть коммиты, которых нет у вас, и `push` не хочет затирать чужую работу. Порядок всегда один:

```bash
git pull
# разобрать merge или конфликт

git push
```

`git push --force` на общей ветке **не** делаем: он переписывает историю тем, кто уже её забрал.

Сводка:


| Команда                 | Файлы на диске | Локальный `main` | `origin/main`      |
| ----------------------- | -------------- | ---------------- | ------------------ |
| `git fetch origin`      | не трогает     | не трогает       | обновляет          |
| `git merge origin/main` | пересобирает   | двигает вперёд   | не трогает         |
| `git pull`              | пересобирает   | двигает вперёд   | обновляет          |
| `git push`              | не трогает     | не трогает       | двигает на сервере |


Ещё одна полезная уборка:

```bash
git fetch --prune
# --prune – удалить локальные origin/ветки, которых на сервере уже нет
```

## **Отправляем ветку на** `origin`.

Создали локально:

```bash
git switch -c experiment
# ... коммиты ...
git push -u origin experiment
# push – отправь коммиты
# origin – имя remote
# experiment – ветка на сервере
# -u – upstream: запомни связь experiment с origin/experiment
```

После `-u` достаточно `git push` и `git pull` **на этой ветке** без длинного имени.

На другой машине:

```bash
git fetch origin
git switch -c experiment origin/experiment
# -c – создай локальную ветку
# origin/experiment – откуда взять хеш (remote-tracking ветка)
```

`git branch -r` (`-r` – remotes) – список `origin/*` без локальных.

Сеть и права вы настраивали на прошлой паре. Здесь добавился только слой **веток на origin** – те же указатели, другой компьютер.

## **Stash: черновик в сторону.**

Сначала локальная работа без сети – так проще увидеть, зачем stash вообще нужен.

Незакоммиченное мешает переключению: Git не хочет затереть правки снимком другой ветки.

```bash
echo 'черновик' >> app.py
git switch main
# часто: error: Your local changes to the following files would be overwritten by checkout
```

Спрячем на боковую полку:

```bash
git stash push -m "черновик перед switch"
# stash – стек черновиков в .git
# push  – положить сверху (в новых версиях Git можно просто git stash -m "...")
# -m    – message

git status
# получается: working tree clean

git switch main
# теперь можно

git switch -c wip
# -c – короткая ветка, чтобы вернуть черновик не на main

git stash list
# list – все записи stash

git stash pop
# pop – примени верхнюю запись и удали её из stash

# или:
git stash apply
# apply – примени, но оставь копию в stash
```

`git stash push -u -m "..."` (`-u` – untracked) – захватить и неотслеживаемые файлы.

Ловушка: если за это время те же строки поменяли коммитом, `git stash pop` даст обычный конфликт с маркерами. Git тогда пишет `The stash entry is kept in case you need it again` – запись **остаётся** в `git stash list`, пока вы не разберёте конфликт и не уберёте её через `git stash drop`.

Осторожно: `stash` не замена коммита. Не храните там единственную копию работы неделями.

После `pop` можно `git switch main` и при необходимости `git branch -d wip`.

## **Detached HEAD.**

Это не merge и не remote – это **особое положение HEAD**. Разберём по шагам, что именно происходит.

### **Как HEAD работает обычно.**

```bash
cat .git/HEAD
# получается: ref: refs/heads/main
```

HEAD указывает **на имя ветки**, а имя уже указывает на коммит. Цепочка из двух звеньев:

```text
HEAD ──► main ──► F1 (коммит)
```

Поэтому `git commit` двигает сразу всё: создаётся новый коммит, имя `main` переписывается на него, а HEAD едет следом, потому что он привязан к имени.

### **Что делает** `--detach`.

```bash
git switch --detach HEAD~1
# --detach – прицепи HEAD прямо к коммиту, минуя имя ветки
# HEAD~1   – один коммит назад по первому родителю
# получается: HEAD is now at 8010b47 <сообщение того коммита>
```

Среднее звено пропало:

```text
HEAD ──► 8010b47 (коммит)
```

```bash
cat .git/HEAD
# получается: 8010b47...  (голый хеш, без ref: refs/heads/...)

git status
# получается: HEAD detached at 8010b47

git branch
# получается: * (HEAD detached at 8010b47)
#               main
```

> **Detached HEAD** – состояние, когда HEAD указывает на коммит напрямую. Вы «стоите» в истории, но ни на какой ветке не находитесь.

Файлы на диске при этом **полностью** соответствуют тому старому коммиту: можно читать код, запускать тесты, искать, когда всё работало.

### **Чем это опасно.**

Пока вы смотрите – всё безопасно. Проблема появляется, если вы что-то **закоммитите**.

```text
до коммита:   HEAD ──► 8010b47 ◄── (часть истории main)

после:        HEAD ──► X (новый коммит)
                        │
              8010b47 ◄─┘

              на X не указывает НИ ОДНО имя ветки
```

Коммит `X` существует, но на него нет наклейки. Как только вы сделаете `git switch main`, HEAD уедет к `main`, и `X` останется **вообще без ссылок** – в `git log` его не найти. Git об этом честно предупреждает:

```text
Warning: you are leaving 1 commit behind, not connected to
any of your branches
```

Через какое-то время такие коммиты вычищает сборщик мусора Git.

### **Как спасти коммит.**

Прямо в detached, **до** переключения:

```bash
git switch -c rescue-branch
# -c – создай ветку ЗДЕСЬ, на текущем коммите
# теперь на X есть имя, коммит больше не потеряется
```

Если уже уходите и видите предупреждение – в нём указан хеш. Скопируйте его и сделайте ветку:

```bash
git switch -c rescue-branch a1b2c3d
# a1b2c3d – хеш из предупреждения
```

Проще не доводить: заметили, что стоите в detached и хотите писать код, – сразу `git switch -c`.

### **Когда он нужен.**

- посмотреть код проекта на старом коммите или на теге релиза;
- проверить, работала ли программа до конкретного изменения;
- автоматика: CI обычно собирает именно конкретный коммит и потому живёт в detached HEAD.

Вернуться к нормальной работе:

```bash
git switch main
# HEAD снова привязан к имени ветки

cat .git/HEAD
# получается: ref: refs/heads/main
```

Правило простое: **detached – чтобы смотреть; работать – только на ветке.**

## **Сценарии из работы.**

Отдельные команды вы уже знаете. В работе они всегда идут связками. Ниже пять типовых цепочек.

Сценарии написаны для репозитория **с настроенным** `origin` (как настраивали на прошлой паре). Если remote у вас нет, читайте их как алгоритм: все шаги без `push` / `pull` работают локально.

### **Сценарий 1. Начинаю фичу.**

Правило: **никогда не ветвиться от устаревшего** `main`.

```bash
git switch main
# встать на общую ветку

git pull
# подтянуть чужие коммиты (upstream уже настроен через push -u)

git switch -c feature-report
# -c – новая ветка от СВЕЖЕГО main
```



### **Сценарий 2. Коллеги ушли вперёд.**

```bash
git switch feature-report
git add . && git commit -m "черновик метрики"
# сначала свои правки в коммит, чтобы merge было чем сливать

git fetch origin
git status -sb
# ## feature-report...origin/feature-report [ahead 1]

git merge origin/main
# влить свежий main В СВОЮ ветку и решить конфликты у себя,
# а не в общей ветке

git push
```

Конфликт лучше разобрать **в своей ветке**: `main` остаётся рабочей всё это время.

### **Сценарий 3. Фича готова.**

```bash
git switch main
git pull
# ещё раз: main мог уехать, пока вы дорабатывали

git merge feature-report
# FF или merge-коммит – зависит от того, двигался ли main

git push

git branch -d feature-report
# локальное имя больше не нужно

git push origin --delete feature-report
# --delete – убрать ветку и на сервере (если публиковали)
```

На GitHub / GitLab та же операция делается кнопкой **Merge pull request**: ревью, обсуждение, затем тот же `merge` на стороне сервера. Многие команды запрещают прямой `push` в `main` (protected branch) – тогда единственный путь и есть pull request.

### **Сценарий 4. Срочный hotfix.**

```bash
git stash push -m "недоделанная фича"
# черновик в сторону, рабочая копия чистая

git switch main
git pull
git switch -c hotfix-login

# правим ровно одну вещь
git add app.py && git commit -m "hotfix: чиним вход"

git switch main
git merge hotfix-login
git push
git branch -d hotfix-login

git switch feature-report
git stash pop
# черновик вернулся, продолжаем
```



### **Сценарий 5. Плохой коммит в** `main`.

Коммит уже у коллег – историю не переписываем:

```bash
git switch main
git pull

git log --oneline -5
# находим хеш плохого коммита, например a1b2c3d

git revert a1b2c3d --no-edit
# новый коммит-антидот, история цела

git push
```

Если плохим был **merge-коммит**, добавляем `-m 1` (считать первым родителем `main`):

```bash
git revert -m 1 a1b2c3d --no-edit
```

И два «никогда» для общей ветки: `reset --hard` **уже отправленного** и `push --force`. Оба ломают историю тем, кто её уже забрал.

## **Merge и rebase.**

Сегодня руками – `merge`. Кратко, что ещё бывает:


| Подход     | Идея                                          | Минус для новичка                         |
| ---------- | --------------------------------------------- | ----------------------------------------- |
| **merge**  | сохраняет развилку, merge-коммит              | граф с ветвлениями                        |
| **rebase** | переносит ваши коммиты «поверх» чужой вершины | переписывает хеши, опасно на общих ветках |


`cherry-pick` – взять один коммит на другую ветку. `git bisect` – найти коммит, который сломал тест. Это отдельные занятия или самостоятельное чтение Pro Git.

Сначала уверенно: `switch`, `merge`, конфликт, `pull`, `stash`.

## **Полезные приёмы.**

**Алиас на граф.** Смотреть DAG после каждого merge полезнее, чем один раз в конце. Длинную команду сохраняем под коротким именем:

```bash
git config --global alias.lg "log --oneline --decorate --graph --all"
# alias.lg – заведи псевдоним lg в ~/.gitconfig
# в кавычках – сама команда БЕЗ слова git

git lg
# теперь это то же самое, что git log --oneline --decorate --graph --all
```

Убрать псевдоним:

```bash
git config --global --unset alias.lg
# --unset – удалить настройку
```

**Короткий статус с веткой:**

```bash
git status -sb
# -s – short, -b – показать ветку и ahead / behind сверху
```

**Прыгнуть на предыдущую ветку:**

```bash
git switch -
# «-» – та ветка, где вы были до этого (как cd - в терминале)
```

**Что принесёт ветка, если её влить.** Заведём ветку специально для примера:

```bash
git switch main
git switch -c demo-tricks
echo 'tricks' >> app.py && git add app.py && git commit -m "коммит для примеров"
git switch main
```

```bash
git diff --stat main...demo-tricks
# три точки – изменения ветки demo-tricks С МОМЕНТА расхождения с main
# --stat – кратко: файлы и счётчик строк
# (две точки main..demo-tricks сравнили бы просто две вершины)

git log --oneline main..demo-tricks
# список коммитов, которых нет в main
```

**Что улетит на сервер, до** `push` (нужен настроенный `origin`):

```bash
git log --oneline origin/main..HEAD
# пусто – отправлять нечего
```

**Какие ветки уже влиты и их можно удалять:**

```bash
git branch --merged
# --merged – ветки, полностью влитые в текущую

git branch --no-merged
# --no-merged – ещё не влитые, удалять нельзя
```

**Вернуть один файл из старого коммита, не трогая остальные:**

```bash
git restore --source=HEAD~1 app.py
# --source – из какого коммита взять содержимое файла
# файл окажется в рабочей копии, история не двигается
```

**Посмотреть, откуда приехала строка, и открыть тот коммит:**

```bash
git blame app.py
# для каждой строки: хеш, автор, дата

git show a1b2c3d
# полный коммит по хешу из blame
```

## **Команды и частые ошибки.**


| Команда                               | Зачем                                        |
| ------------------------------------- | -------------------------------------------- |
| `git branch`                          | список локальных веток; `*` – текущая        |
| `git branch -vv`                      | upstream и последний коммит                  |
| `git branch --merged` / `--no-merged` | что уже влито, что ещё нет                   |
| `git switch имя` / `git switch -`     | на ветку / на предыдущую                     |
| `git switch -c имя`                   | создать ветку и перейти; `-c` – create       |
| `git merge другая`                    | влить **в текущую** ветку                    |
| `git merge --no-ff`                   | merge-коммит даже при возможном FF           |
| `git merge --abort`                   | отменить незавершённый merge                 |
| `git log --oneline --graph --all`     | весь локальный граф                          |
| `git log --oneline main..feature`     | коммиты ветки, которых нет в `main`          |
| `git diff main...feature`             | что принесёт ветка с момента расхождения     |
| `git rev-parse HEAD^1 HEAD^2`         | родители merge-коммита                       |
| `git reset --hard HEAD~1`             | откатить свой (не отправленный) merge        |
| `git reset --hard ORIG_HEAD`          | вернуть ветку после неудачного reset / merge |
| `git revert <хеш> --no-edit`          | отменить уже отправленный коммит             |
| `git fetch origin` / `--prune`        | обновить `origin/*` / убрать мёртвые         |
| `git status -sb`                      | короткий статус + ahead / behind             |
| `git pull`                            | fetch + влить в текущую ветку                |
| `git push -u origin ветка`            | отправить и запомнить upstream               |
| `git push origin --delete ветка`      | удалить ветку на сервере                     |
| `git stash push -m` / `list` / `pop`  | черновик в сторону                           |
| `git branch -d` / `-D`                | удалить имя ветки                            |
| `git switch --detach`                 | HEAD на коммит, не на ветку                  |


**Сообщения:**

- `Your local changes would be overwritten` – коммит, `stash` или `restore`, потом `switch`;
- `CONFLICT` / `<<<<<<<` – правите файл, `add`, `commit` или `merge --abort`;
- `detached HEAD` – для работы создайте ветку (`switch -c`);
- `Already up to date` – вливать нечего;
- `rejected (fetch first)` – сначала `pull`, потом `push`;
- `error: branch 'X' not fully merged` при `-d` – ветка не влита; `-D` только если уверены;
- `ambiguous argument 'HEAD^2': unknown revision` – коммит не merge, второго родителя нет;
- `There is no merge to abort (MERGE_HEAD missing)` – слияние уже закоммичено, помогут `reset` или `revert`;
- `You have not concluded your merge (MERGE_HEAD exists)` – сначала доведите merge: `add` и `commit` либо `merge --abort`.
