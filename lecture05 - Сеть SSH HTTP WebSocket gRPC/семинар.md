# Семинар к Лекции 5. Сеть: SSH, HTTP, WebSocket, gRPC

Это конспект практического занятия: живая работа в терминале. К концу вы своими
руками сгенерируете SSH-ключ и войдёте по нему, пробросите порт, пощупаете HTTP
через `curl`, увидите разницу polling vs WebSocket и сделаете один gRPC-вызов.

Всё, кроме gRPC, работает на любом Linux/macOS; под Windows — через WSL.

## Что понадобится

- Доступ к серверу для входа по SSH. Варианты: облачная ВМ, машина соседа,
  или **локальный `sshd`** — тогда во всех командах вместо `you@server` пишем
  `$USER@localhost`. Проверить можно заранее: `ssh localhost` должен спрашивать
  пароль.
- Установленные утилиты: `ssh`, `ssh-keygen`, `ssh-copy-id`, `curl`, `jq`,
  `ss` (Linux) или `lsof` (macOS), `python3`.
- Для WebSocket — `websocat` (`brew install websocat` / `cargo install websocat`)
  **или** `npm i -g wscat`. Ниже показаны оба варианта.
- Для gRPC — `grpcurl` (`brew install grpcurl` / из релизов на GitHub). Демо идёт
  на публичный сервер `grpcb.in:9000`, так что нужен интернет.
- Полезно заранее выполнить `echo $USER`, чтобы не путаться в имени пользователя.

## Разминка: порт — это адрес программы

Компьютер один, IP один — а программ, ждущих сеть, много. Как пакет понимает,
какой именно программе он предназначен? Ответ — **порт**.

Посмотрим, кто сейчас слушает порты:
```bash
ss -tlnp            # Linux: T=tcp, l=listening, n=числа, p=процесс
# или на macOS:
lsof -iTCP -sTCP:LISTEN -P -n
```
Каждая строка — программа, «сидящая» на паре IP:порт. Пара «IP + порт» и есть
**сокет**. 80/443 — веб, 22 — SSH, 5432 — Postgres.

Обратите внимание: порт до 1024 («привилегированные») обычный пользователь
занять не может — вот почему сервисы часто вешают на 8080, а не на 80.

## SSH-ключи и вход без пароля — ядро занятия

Сначала посмотрим, «как не надо» — вход по паролю:
```bash
ssh you@server          # или: ssh $USER@localhost
# просит пароль каждый раз; пароль летит на сервер
```
Пароль можно подобрать и подсмотреть. Переходим на ключи.

Генерируем пару ключей:
```bash
ssh-keygen -t ed25519 -C "you@hse"
# Enter на «file» (примет путь по умолчанию ~/.ssh/id_ed25519)
# passphrase можно пустой для демо (в бою — задавайте!)
```
Ожидаемый вывод (сокращённо):
```
Generating public/private ed25519 key pair.
Your identification has been saved in ~/.ssh/id_ed25519
Your public key has been saved in ~/.ssh/id_ed25519.pub
```
Появилось два файла:
```bash
ls -l ~/.ssh/id_ed25519 ~/.ssh/id_ed25519.pub
cat ~/.ssh/id_ed25519.pub     # одна строка: ssh-ed25519 AAAA... you@hse
```
`.pub` — публичный, его можно показывать хоть на экране проектора. Файл без
`.pub` — приватный, **секрет**; его не показываем и не копируем никуда.

Кладём публичный ключ на сервер:
```bash
ssh-copy-id you@server        # или: ssh-copy-id $USER@localhost
```
Команда просто дописала строку из вашего `.pub` в файл `~/.ssh/authorized_keys`
**на сервере**. Убедиться в этом можно так:
```bash
ssh you@server 'tail -n1 ~/.ssh/authorized_keys'
```

Теперь вход — и пароль больше не спрашивают:
```bash
ssh you@server                # входим мгновенно, без пароля
```
Как устроено рукопожатие в двух фразах: сервер даёт клиенту случайную «задачу»;
решить её (подписать) может только владелец приватного ключа; сервер проверяет
подпись публичным ключом из `authorized_keys`. **Секрет по сети не передаётся.**

На что обратить внимание:
- `chmod`: если `~/.ssh` или ключ слишком «открыты», ssh молча откажет. Права
  должны быть `700` на папку и `600` на приватный ключ.
- Первое подключение к новому серверу спрашивает `yes/no` (fingerprint) — это
  защита от подмены сервера, запись уходит в `~/.ssh/known_hosts`.

## Проброс портов

Чтобы было что пробрасывать, заведём на сервере какой-нибудь сервис. Проще всего
— поднять в SSH-сессии простой веб-сервер:
```bash
ssh you@server
python3 -m http.server 8000     # на сервере слушает :8000; оставляем висеть
```
Откройте **второй** терминал у себя. Сервер снаружи закрыт — а мы дотянемся до
него туннелем.

**Local forwarding (`-L`) — «принести удалённый порт к себе»:**
```bash
ssh -L 8080:localhost:8000 you@server
# теперь в ещё одном терминале у СЕБЯ:
curl -s http://localhost:8080/ | head
```
Мы обратились к **своему** `localhost:8080`, а ответил `:8000` **на сервере** —
трафик прошёл внутри шифрованного SSH-канала. Разберём синтаксис
`-L 8080:localhost:8000`: `8080` — где открываем порт (у себя), `localhost:8000` —
куда он ведёт (адрес назначения с точки зрения сервера).

**Remote forwarding (`-R`) — «показать серверу мой локальный порт»:**
```bash
# у себя запущен, скажем, dev-сервер на :3000
python3 -m http.server 3000     # локально
ssh -R 9090:localhost:3000 you@server
# теперь на СЕРВЕРЕ:
ssh you@server 'curl -s http://localhost:9090/ | head'
```
Теперь наоборот — кто-то на сервере, обращаясь к `:9090`, попадает на наш
локальный `:3000`. Так показывают коллеге сервис, который крутится только у вас
на ноутбуке.

**Мнемоника:** `-L` = **L**ocal, порт открывается **L**окально; `-R` =
**R**emote, порт открывается на удалённой стороне.

Здесь легко перепутать числа местами. Правило: **левое число — где слушаем,
правое (после `:`) — куда ведём.**

## Копирование файлов: scp и rsync

```bash
echo "hello" > demo.txt
scp demo.txt you@server:/tmp/          # простое копирование
scp -r ./somedir you@server:/tmp/      # -r — папку целиком
```
`scp` всегда льёт файлы целиком. Для больших/повторяющихся переносов есть
`rsync`:
```bash
rsync -avz ./somedir/ you@server:/tmp/somedir/
# повторяем ту же команду ещё раз:
rsync -avz ./somedir/ you@server:/tmp/somedir/
```
Второй запуск почти мгновенный и печатает `sending incremental file list` без
файлов — `rsync` передаёт **только различия**. `-a` — сохранить атрибуты, `-v` —
подробно, `-z` — сжать в пути. Ещё умеет докачку после обрыва.

Обратите внимание на хвостовой слэш: `src/` и `src` в rsync означают разное
(содержимое папки vs сама папка) — классический источник сюрпризов.

## HTTP через curl

Теперь прикладной уровень. Начнём с «сырого» запроса-ответа:
```bash
curl -v https://httpbin.org/get
```
Разберём вывод построчно по стрелкам:
- строки с `>` — то, что **мы отправили** (request): `GET /get HTTP/1.1`, `Host:`,
  `User-Agent:`, `Accept:`.
- строки с `<` — то, что **вернул сервер** (response): статус `HTTP/1.1 200 OK`
  и заголовки ответа.
- ниже — тело ответа (JSON).

Главная мысль: HTTP — это текст. Запрос = метод + путь + заголовки; ответ =
статус + заголовки + тело. Никакой магии.

Посмотрим только статус (удобно для проверок):
```bash
curl -s -o /dev/null -w "%{http_code}\n" https://httpbin.org/status/200
curl -s -o /dev/null -w "%{http_code}\n" https://httpbin.org/status/404
curl -s -o /dev/null -w "%{http_code}\n" https://httpbin.org/status/500
```
Классы статусов: `2xx` — успех, `3xx` — редирект, `4xx` — виноват клиент (404 —
нет такого), `5xx` — упал сервер. Первую цифру запомнить достаточно.

Разные методы = разные действия над ресурсом:
```bash
curl -s https://httpbin.org/get                                  | jq .
curl -s -X POST https://httpbin.org/post -d '{"name":"Ann"}' \
     -H "Content-Type: application/json"                         | jq .json
```
Это и есть REST-идея — один адрес-ресурс, а `GET`/`POST`/`PUT`/`DELETE` задают
операцию. `-H` добавляет заголовок, `-d` — тело запроса, `jq` делает JSON
читаемым.

Заголовки можно посмотреть отдельно, а заодно проследить редирект:
```bash
curl -I https://httpbin.org/get              # только заголовки (-I = HEAD)
curl -sIL https://httpbin.org/redirect/1     # -L идёт по редиректу; видно 302→200
```
Обратите внимание: `-I` шлёт метод `HEAD` — тело не качается, только заголовки.
Это дёшево и часто используется для health-check.

## Polling vs WebSocket на живом примере

Сначала **short polling** — тупо спрашиваем в цикле:
```bash
while true; do
  date +%T
  curl -s https://httpbin.org/get -o /dev/null -w "  запрос -> %{http_code}\n"
  sleep 2
done
# остановить: Ctrl+C
```
Клиент дёргает сервер каждые 2 секунды, даже когда новостей нет. Половина
(а то и все) запросов — впустую. Задержка обновления — до `sleep`. Так работают
самые простые «обновлялки» и, к слову, Telegram-бот в режиме polling (вернёмся
к этому на теме 9).

Теперь **WebSocket** — одно соединение, данные идут сами. Подключимся к публичному
эхо-серверу:
```bash
# вариант А:
websocat wss://ws.postman-echo.com/raw
# вариант Б:
wscat -c wss://ws.postman-echo.com/raw
```
Наберите несколько строк и жмите Enter — сервер тут же возвращает их обратно
**в том же открытом соединении**, без нового запроса.

Сравним два подхода:
- polling: **N** запросов-ответов, соединение каждый раз новое, куча «пусто».
- WebSocket: **одно** рукопожатие (обычный HTTP с `Upgrade`), дальше канал живёт
  и **обе стороны** шлют, когда есть что сказать (full-duplex).

Убедимся, что рукопожатие — это HTTP:
```bash
curl -v https://ws.postman-echo.com/raw \
     -H "Connection: Upgrade" -H "Upgrade: websocket" 2>&1 | grep -i -E "GET|101|upgrade"
```
Обратите внимание: статус `101 Switching Protocols` — тот самый момент, когда
HTTP-соединение «превращается» в WebSocket-канал.

Когда что использовать: редкие обновления и обычный CRUD — хватает HTTP; чат,
уведомления, живой дашборд — WebSocket.

## Один gRPC-вызов

Убедимся, что RPC — это «вызов удалённого метода». Работаем на публичном тестовом
сервере `grpcb.in` с включённой reflection (схему тянуть не нужно):
```bash
grpcurl grpcb.in:9000 list                          # какие сервисы есть
grpcurl grpcb.in:9000 list hello.HelloService       # какие методы у сервиса
```
Вызовем метод, передав JSON-аргумент:
```bash
grpcurl -d '{"greeting":"HSE"}' grpcb.in:9000 hello.HelloService/SayHello
```
Ожидаемый ответ:
```json
{
  "reply": "hello HSE"
}
```
Мы **вызвали функцию** `SayHello` на удалённой машине, как будто она локальная —
это и есть RPC-парадигма. Контракт описан в `.proto`, поверх — HTTP/2, на проводе
— компактный бинарный protobuf (мы его не видим, `grpcurl` показывает удобный
JSON).

Теперь серверный **стриминг** (много ответов на один запрос):
```bash
grpcurl -d '{"count":3}' grpcb.in:9000 hello.HelloService/LotsOfReplies
```
Пришёл **поток** сообщений в одном вызове — то, что в REST пришлось бы
эмулировать. Это и есть встроенный стриминг gRPC.

Сравнение: REST/JSON — человекочитаемо, отлично для браузера и публичных API;
gRPC/protobuf — компактно и быстро, строгий контракт, идеально для общения
сервисов между собой.

## Частые ошибки

- **`Permission denied (publickey)`** — публичный ключ не попал в
  `authorized_keys`, либо слишком широкие права на `~/.ssh` (нужно `700`/`600`).
- **«скопировал приватный ключ на сервер»** — так делать нельзя; на сервер идёт
  только `.pub`. Скопировать приватный ключ — всё равно что отдать пароль.
- **Путаница с числами в `-L`/`-R`** — вернитесь к мнемонике «левое = где
  слушаем».
- **`curl` без `-s` шумит прогресс-баром** — в скриптах всегда `-s`.
- **`address already in use`** при `python3 -m http.server` — порт занят прошлым
  запуском; сменить порт или убить процесс (`ss -tlnp` → `kill`).
- **WebSocket «не подключается»** — забыли схему `wss://`, или корпоративный
  прокси режет `Upgrade`. Попробуйте другой публичный эхо-сервер.
- **`grpcurl ... server does not support reflection`** — на «боевых» серверах
  reflection часто выключен; тогда нужен `.proto` через `-import-path`/`-proto`.
