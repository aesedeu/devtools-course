## Что понадобится

- Терминал.
- Docker установлен и запущен: `docker version` (должны отвечать и Client, и
  Server). На macOS/Windows — запущен Docker Desktop; на Linux — активен демон.
- Интернет: на первом `docker run` и `pull` образы тянутся из реестра.
- Аккаунт на Docker Hub (или GitHub с доступом к GHCR) — для блока с push.
- VS Code с расширением **Dev Containers** — для финального блока. Без VS Code
  этот блок можно пройти через CLI: `npx @devcontainers/cli` (нужен Node.js).
- Около 2 ГБ свободного места: образ для разработки большой.
- Пустая рабочая папка `~/docker-demo`.

## Разминка: «у меня работает» · слайд 3

Знакомая ситуация: «у меня на ноуте работало, а на сервере упало». Причина почти
всегда в разном окружении.

> Проблема — в разном окружении: версии Python, системных библиотек, переменных.
> Docker упаковывает приложение **вместе с окружением** в образ. Образ запускается
> одинаково и у вас, и на сервере, и у коллеги.

Сразу разведём два ключевых понятия:

> **Образ (image)** — неизменяемый «слепок» файловой системы и метаданных.
> **Контейнер (container)** — запущенный экземпляр образа. Один образ → много
> контейнеров, как класс и объекты.

Проверьте, что демон жив:
```bash
docker version
```
Если отвечает только Client, а Server выдаёт ошибку, значит демон не запущен —
частая причина в том, что не открыт Docker Desktop.

## Тянем и запускаем чужой контейнер · слайды 5–6

Начнём с самого простого — запустим готовый образ, ничего не собирая.
```bash
docker run hello-world
```
Образа локально нет, поэтому Docker сам сделал `pull` из реестра, создал контейнер,
тот напечатал текст и завершился. Строки вывода как раз описывают эти шаги — прочитайте
их, там по пунктам расписан весь процесс.

Теперь интерактивный контейнер — «зайдём внутрь» Linux:
```bash
docker run -it --rm python:3.12-slim bash
```
**Внутри контейнера** видно, что это отдельная система:
```bash
python --version
cat /etc/os-release      # Debian, а не ваша macOS
exit
```
Здесь `-it` — интерактивный терминал, `--rm` — удалить контейнер после выхода
(иначе он остался бы в `docker ps -a`). После `exit` мы снова на хосте.

Посмотрим, что появилось локально:
```bash
docker images           # python:3.12-slim, hello-world
docker ps -a            # завершённые контейнеры
```

## Пишем приложение и Dockerfile — ядро семинара · слайды 8–9

Создаём крошечное веб-приложение.
```bash
mkdir ~/docker-demo && cd ~/docker-demo
```
Файл `app.py` — простой HTTP-сервер на стандартной библиотеке (без зависимостей,
чтобы демо на первом шаге не зависело от pip). Он здоровается и считает визиты,
а счётчик хранит в файле `/data/hits.txt` — это пригодится, когда дойдём до томов:
```python
import os
from http.server import BaseHTTPRequestHandler, HTTPServer

DATA = "/data/hits.txt"
os.makedirs("/data", exist_ok=True)

class H(BaseHTTPRequestHandler):
    def do_GET(self):
        hits = 1
        if os.path.exists(DATA):
            with open(DATA) as f:
                hits = int(f.read()) + 1
        with open(DATA, "w") as f:
            f.write(str(hits))
        who = os.environ.get("WHO", "world")
        self.send_response(200)
        self.end_headers()
        self.wfile.write(f"hello, {who}! визит №{hits}\n".encode())

HTTPServer(("0.0.0.0", 8000), H).serve_forever()
```
Обратите внимание на `"0.0.0.0"`: сервер слушает все интерфейсы контейнера. С
`"127.0.0.1"` он был бы доступен только изнутри самого контейнера, и проброс порта
ниже ничего бы не дал.
`requirements.txt` — пока пустой или с одной строкой (пригодится для кэша):
```bash
echo "" > requirements.txt
```

Теперь **Dockerfile**. Разберём его построчно, по одной инструкции:
```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8000
CMD ["python", "app.py"]
```
**Смысл каждой строки:**
- `FROM` — берём готовый лёгкий образ с Python.
- `WORKDIR /app` — рабочая папка внутри образа.
- `COPY requirements.txt .` — сначала только зависимости (это важно для кэша!).
- `RUN pip install ...` — ставим зависимости на этапе **сборки**.
- `COPY . .` — теперь копируем весь код.
- `EXPOSE 8000` — документируем, какой порт слушает приложение.
- `CMD` — что запустить при старте контейнера.

**Ключевая мысль:** зависимости лежат в отдельном слое ДО кода — сейчас увидим,
зачем это нужно.

## Собираем образ и разбираем слои · слайды 8–9

```bash
docker build -t hello:1 .
```
Docker выполняет инструкции по шагам, каждый шаг — слой. В выводе видны строки
`=> [1/5]`, `=> [2/5]` — это и есть слои.

В конце появляется `naming to docker.io/library/hello:1`, и образ становится
доступен:
```bash
docker images hello
```

## Запускаем с портом и томом · слайды 14–16

Запускаем контейнер, пробрасывая порт наружу:
```bash
docker run -d --name web -p 8080:8000 hello:1
docker ps
```
Здесь `-d` — в фоне, `-p 8080:8000` — порт 8080 хоста → порт 8000 в контейнере.
Проверяем в браузере или через curl:
```bash
curl localhost:8080
# hello, world! визит №1
```
Слева в `-p` — хостовый порт (8080), справа — контейнерный (8000). Их специально
сделали разными, чтобы было видно, что это отображение одного на другой.

Передадим переменную окружения:
```bash
docker rm -f web
docker run -d --name web -p 8080:8000 -e WHO=HSE hello:1
curl localhost:8080
# hello, HSE! визит №1
```
Мы пересоздали контейнер — и приложение подхватило `-e WHO`.

Посмотрим логи и заглянем внутрь работающего контейнера:
```bash
docker logs web
docker exec -it web sh
ls /app          # наш код внутри
exit
```

Теперь **том** — чтобы данные переживали контейнер. Сначала убедимся, что без тома
они не переживают. Сходите на сервер несколько раз и пересоздайте контейнер:
```bash
curl localhost:8080       # визит №2
curl localhost:8080       # визит №3
docker rm -f web
docker run -d --name web -p 8080:8000 -e WHO=HSE hello:1
curl localhost:8080       # снова визит №1 — счётчик пропал вместе с контейнером
```
Файл `/data/hits.txt` жил в изменяемом слое контейнера, а этот слой удаляется
вместе с ним. Теперь то же самое, но с **именованным томом** `hits`:
```bash
docker rm -f web
docker run -d --name web -p 8080:8000 -v hits:/data hello:1
curl localhost:8080       # визит №1
curl localhost:8080       # визит №2
docker rm -f web
docker run -d --name web -p 8080:8000 -v hits:/data hello:1
curl localhost:8080       # визит №3 — счётчик пережил удаление контейнера
docker volume ls          # том hits на месте
```
`-v hits:/data` подключает том `hits` в папку `/data` контейнера. Том живёт
отдельно от контейнера и удаляется только явно: `docker volume rm hits`.

Второй способ — **bind mount**: `-v $PWD:/app` подключает внутрь текущую папку хоста.
Им удобно пользоваться при разработке: правите код на хосте — и он сразу виден в
контейнере.

## Кэш слоёв · слайд 10

Измените **только код** (например, `hello` на `привет` в `app.py`), не трогая
`requirements.txt`, и пересоберите:
```bash
docker build -t hello:2 .
```
В выводе шаги с `FROM`, `COPY requirements.txt`, `RUN pip install` помечены
`CACHED` — Docker не переустанавливал зависимости! Пересобрались только слои от
`COPY . .` и ниже. Сборка заняла доли секунды.

Теперь измените `requirements.txt` (добавьте любой пакет) и пересоберите:
```bash
echo "requests" > requirements.txt
docker build -t hello:3 .
```
Изменился слой с зависимостями — и все слои **выше** него пересобрались заново.
Вот почему в Dockerfile редко меняющееся (зависимости) идёт раньше, а часто
меняющийся код — ниже.

**Главный вывод:** порядок инструкций в Dockerfile — это стратегия кэша.

## Отправляем образ в реестр · слайды 5–6

Логинимся и пушим. Замените `USER` на свой логин Docker Hub. Перед этим уберите
контейнер `web` из прошлого блока, чтобы освободить порт 8080:
```bash
docker rm -f web
docker login
docker tag hello:3 USER/hello:latest
docker push USER/hello:latest
```
`tag` даёт образу «полное имя» с адресом реестра и аккаунтом; `push` отправляет
слои в реестр. После этого образ виден в вашем аккаунте на сайте Docker Hub.

Проверим переносимость — сымитируем «скачаем на другой машине»:
```bash
docker rmi USER/hello:latest hello:3     # удалили локально
docker run -d --name web -p 8080:8000 USER/hello:latest
curl localhost:8080
```
В выводе `docker run` видно `Unable to find image … locally` и затем `Pulling`: образа
на машине не было, Docker скачал его из реестра.
Образ приехал из реестра и запустился без пересборки — ровно то же самое произойдёт
на сервере или у коллеги.

> Если Docker Hub недоступен, используйте GHCR: `docker login ghcr.io`,
> тег `ghcr.io/USER/hello:latest`.

## Открываем dev-контейнер: вся среда разработки — в коде · слайд 24

До сих пор контейнер **запускал** готовое приложение. Теперь сделаем так, чтобы в
контейнере можно было **разрабатывать**: редактор, интерпретатор, зависимости,
линтер, тесты, даже `docker` — всё внутри, всё описано файлами в репозитории.
Новый человек клонирует проект, жмёт одну кнопку — и через пару минут у него ровно
такая же среда, как у вас.

Зависимостями внутри будет управлять **uv** — быстрый менеджер пакетов и окружений
для Python (замена связке `pip` + `venv`). Скрипт при создании контейнера сам
переведёт наш проект с `requirements.txt` на uv.

### Шаг 1. Готовим приложение к тестам

Чуть доработаем `app.py`: путь к данным берём из переменной окружения (в
dev-контейнере папка `/data` недоступна обычному пользователю), а запуск сервера
убираем под `if __name__ == "__main__"`, чтобы модуль можно было импортировать в
тестах. Замените конец файла и строки с `DATA`:
```python
import os
from http.server import BaseHTTPRequestHandler, HTTPServer

DATA_DIR = os.environ.get("DATA_DIR", "/data")
DATA = os.path.join(DATA_DIR, "hits.txt")

class H(BaseHTTPRequestHandler):
    def do_GET(self):
        hits = 1
        if os.path.exists(DATA):
            with open(DATA) as f:
                hits = int(f.read()) + 1
        with open(DATA, "w") as f:
            f.write(str(hits))
        who = os.environ.get("WHO", "world")
        self.send_response(200)
        self.end_headers()
        self.wfile.write(f"hello, {who}! визит №{hits}\n".encode())

if __name__ == "__main__":
    os.makedirs(DATA_DIR, exist_ok=True)
    HTTPServer(("0.0.0.0", 8000), H).serve_forever()
```
В Docker-образе всё работает как раньше: `DATA_DIR` не задан — значит, `/data`.

И первый тест — `tests/test_app.py`. Он поднимает сервер на свободном порту прямо
в процессе теста и проверяет, что счётчик растёт:
```python
import threading
import urllib.request
from http.server import HTTPServer

import app


def test_hits_grow(tmp_path, monkeypatch):
    monkeypatch.setattr(app, "DATA", str(tmp_path / "hits.txt"))
    server = HTTPServer(("127.0.0.1", 0), app.H)
    threading.Thread(target=server.serve_forever, daemon=True).start()
    url = f"http://127.0.0.1:{server.server_port}/"
    try:
        assert "визит №1" in urllib.request.urlopen(url).read().decode()
        assert "визит №2" in urllib.request.urlopen(url).read().decode()
    finally:
        server.shutdown()
```

### Шаг 2. Образ среды: `.devcontainer/Dockerfile` · слайды 20, 24

```dockerfile
FROM mcr.microsoft.com/devcontainers/python:3.12
COPY --from=ghcr.io/astral-sh/uv:0.13.3 /uv /uvx /bin/
```
- `mcr.microsoft.com/devcontainers/python` — официальный образ **для разработки**:
  в нём уже есть git, curl, jq, zsh и обычный пользователь `vscode` (не root).
- Вторая строка — тот самый `COPY --from` из multi-stage сборки: забираем готовые
  бинарники uv из официального образа Astral. Никаких `curl | sh`, версия
  зафиксирована.

### Шаг 3. Описание среды: `.devcontainer/devcontainer.json` · слайд 24

```jsonc
{
  "name": "docker-demo",
  "build": { "dockerfile": "Dockerfile" },
  "features": {
    // Docker-in-Docker: внутри dev-контейнера свой, отдельный демон Docker.
    // Контейнеры хоста отсюда не видны, свои образы и контейнеры — тоже только здесь.
    "ghcr.io/devcontainers/features/docker-in-docker:2": { "moby": false }

    // Альтернатива — Docker-outside-of-Docker: внутрь ставится только клиент docker,
    // а к нему подключается сокет демона ХОСТА (/var/run/docker.sock).
    // Тогда docker ps показывает контейнеры хоста, а docker run создаёт их на хосте.
    // Легче (нет второго демона), но доступ к сокету хоста = права root на хосте.
    // "ghcr.io/devcontainers/features/docker-outside-of-docker:1": { "moby": false }
  },
  "remoteUser": "vscode",
  "containerEnv": {
    "WHO": "devcontainer",
    "DATA_DIR": "/home/vscode/.data",
    "UV_PROJECT_ENVIRONMENT": "/home/vscode/venv",
    "UV_LINK_MODE": "copy"
  },
  // Аргументы для docker run: публикуем порт 8000 на ВСЕХ интерфейсах машины
  // (0.0.0.0) — приложение откроется и с других компьютеров в сети.
  // Не "appPort": [8000] — VS Code публикует appPort только на 127.0.0.1.
  "runArgs": ["-p", "0.0.0.0:8000:8000"],
  // Подпись для порта 8000 во вкладке Ports.
  "portsAttributes": {
    "8000": { "label": "hello app", "onAutoForward": "notify" }
  },
  // Остальные порты, которые VS Code находит в контейнере (служебные порты
  // vscode-server, dockerd и т.п.), не пробрасывать и не показывать уведомления.
  "otherPortsAttributes": { "onAutoForward": "ignore" },
  "postCreateCommand": "bash .devcontainer/post-create.sh",
  "postAttachCommand": "echo '👋 Запуск: uv run python app.py · тесты: uv run pytest'",
  "customizations": {
    "vscode": {
      "extensions": ["ms-python.python", "charliermarsh.ruff"],
      "settings": {
        // Если порт пробрасывает сам VS Code (вкладка Ports, "forwardPorts"), его туннель
        // слушает только localhost. Чтобы он слушал все интерфейсы, нужна настройка
        // VS Code НА ВАШЕЙ МАШИНЕ (здесь она не действует):
        // добавьте в свой settings.json (Cmd/Ctrl+Shift+P → Preferences: Open User Settings (JSON))
        // "remote.localPortHost": "allInterfaces",
        "python.defaultInterpreterPath": "/home/vscode/venv/bin/python",
        "python.testing.pytestEnabled": true,
        "[python]": {
          "editor.defaultFormatter": "charliermarsh.ruff",
          "editor.formatOnSave": true
        }
      }
    }
  }
}
```
Что здесь важно:
- **`build`** — среда собирается из нашего Dockerfile, а не из готового образа.
- **Комментарии** — `devcontainer.json` пишется в формате JSONC: обычный JSON, но с
  комментариями `//`. Это удобно, чтобы объяснять настройки прямо в файле.
- **`features`** — готовые «надстройки» к образу. `docker-in-docker` ставит внутрь
  **отдельный демон Docker**: изнутри dev-контейнера можно собирать и запускать
  контейнеры, и они живут внутри него, не мешая хосту. Для этого dev-контейнер
  запускается с `--privileged` — фича включает это сама. Закомментированная
  альтернатива `docker-outside-of-docker` вместо своего демона подключает сокет
  Docker хоста — подробности в комментариях в файле. Опция `"moby": false` ставит
  официальный Docker: базовый образ собран на Debian 13, а пакетов Moby (вариант по
  умолчанию) для этой версии нет — без опции сборка упадёт.
- **`containerEnv`** — переменные окружения. `UV_PROJECT_ENVIRONMENT` кладёт
  виртуальное окружение **вне папки проекта**: папка проекта примонтирована с вашей
  машины, и `.venv`, собранный в Linux-контейнере, не перепутается с `.venv` на
  macOS/Windows. `UV_LINK_MODE=copy` убирает предупреждение uv о том, что кэш и
  окружение лежат на разных дисках.
- **`runArgs`** — аргументы, которые VS Code добавит к `docker run` при создании
  контейнера. `-p 0.0.0.0:8000:8000` — обычная публикация порта из лекции, с явным
  адресом: слушать на всех интерфейсах машины. Адрес здесь важен — подробнее в шаге 6.
- **`portsAttributes` и `otherPortsAttributes`** — как VS Code показывает порты:
  подпись для 8000 и «не трогать» для всех остальных.
- **`postCreateCommand`** — что выполнить **один раз** после создания контейнера.
  **`postAttachCommand`** — при каждом подключении редактора.
- **`customizations.vscode`** — расширения и настройки редактора: интерпретатор из
  нашего окружения, ruff как форматтер при сохранении, тесты через pytest.

### Шаг 4. Что делать при создании: `.devcontainer/post-create.sh`

```bash
#!/usr/bin/env bash
set -euo pipefail

echo "▶ $(uv --version), $(docker --version)"

if [ ! -f pyproject.toml ]; then
  echo "▶ pyproject.toml нет — переводим проект на uv"
  uv init --bare --name docker-demo --python 3.12
  uv add -r requirements.txt
fi
uv add --dev pytest ruff
if ! grep -q 'tool.pytest' pyproject.toml; then
  printf '\n[tool.pytest.ini_options]\npythonpath = ["."]\n' >> pyproject.toml
fi

# терминал сразу «внутри» окружения: python, pytest, ruff — без uv run
for rc in ~/.bashrc ~/.zshrc; do
  grep -q 'venv/bin/activate' "$rc" 2>/dev/null || echo 'source /home/vscode/venv/bin/activate' >> "$rc"
done

echo "▶ линтер";  uv run ruff check .
echo "▶ тесты";   uv run pytest -q

echo "✅ Среда готова. Запуск: uv run python app.py"
```
Это обычный bash-скрипт из лекции 4: строгий режим, проверка условия, команды по
шагам. Если линтер или тесты упадут, создание контейнера покажет ошибку — сломанная
среда не притворится рабочей. Строка с `activate` в `~/.bashrc` и `~/.zshrc`
включает окружение в каждом новом терминале. Секция `[tool.pytest.ini_options]` с
`pythonpath = ["."]` говорит pytest искать модули в корне проекта — иначе тест не
найдёт `import app`. Ruff, кстати, придирчив: он проверяет порядок импортов
и требует открывать файлы через `with` — поэтому в `app.py` выше так и сделано.

### Шаг 5. Открываем

В VS Code: палитра команд (`Cmd/Ctrl+Shift+P`) → **Dev Containers: Reopen in
Container**. Первая сборка займёт несколько минут: образ для разработки большой
(около 1,7 ГБ). В логе сборки видно всё по порядку: сборку Dockerfile, установку
фичи `docker-outside-of-docker`, затем вывод нашего скрипта:
```
▶ uv 0.13.3, Docker version …
▶ pyproject.toml нет — переводим проект на uv
▶ линтер
All checks passed!
▶ тесты
.                                                    [100%]
1 passed in 0.03s
✅ Среда готова. Запуск: uv run python app.py
```
В папке проекта появились `pyproject.toml` и `uv.lock` — их нужно закоммитить:
`uv.lock` фиксирует **точные** версии всех пакетов, и у коллег поставится ровно то же.

### Шаг 6. Работаем внутри

Терминал VS Code теперь открыт **внутри контейнера**:
```bash
whoami                     # vscode — не root
which python               # /home/vscode/venv/bin/python — наше окружение
pytest -q                  # 1 passed — инструменты доступны напрямую
python app.py              # сервер на 8000 (то же, что uv run python app.py)
```
Откройте `http://localhost:8000` в браузере на машине, где запущен dev-контейнер:
`hello, devcontainer! визит №1`. Переменная `WHO` пришла
из `containerEnv`.

Добавим зависимость — uv сам поставит пакет и обновит `pyproject.toml` и `uv.lock`:
```bash
uv add httpx
grep -A4 '^dependencies' pyproject.toml     # httpx появился в списке
```
Сохраните `app.py` с лишними пробелами — ruff выровняет файл при сохранении.
Панель **Testing** (колба слева) найдёт `tests/test_app.py` и запустит тест кнопкой.

А теперь Docker внутри dev-контейнера. У него свой демон — это видно сразу:
```bash
docker ps                  # пусто: контейнеров хоста отсюда не видно
docker build -t hello:dev .
docker run --rm -d -p 8081:8000 --name devtest hello:dev
docker ps                  # devtest — единственный контейнер
curl localhost:8081        # hello, world! визит №1
docker rm -f devtest
```
Здесь `-p 8081:8000` публикует порт на «хосте» внутреннего демона, то есть **внутри
dev-контейнера**, поэтому `curl localhost:8081` изнутри работает. А вот с вашей
машины `http://localhost:8081` не откроется: dev-контейнер — отдельная сеть (net
namespace из лекции 6), и наружу торчит только то, что опубликовано для него
самого (`-p 0.0.0.0:8000:8000` в `runArgs`). Контейнеры внутри — это «матрёшка»
второго уровня.

Проверьте и на хосте: `docker ps` в обычном терминале покажет dev-контейнер, но не
`devtest` — у двух демонов свои списки контейнеров и свои образы.

### Порт 8000 с другого компьютера в сети · слайд 16

Частая ситуация: dev-контейнер поднят на виртуалке или сервере, а открыть
приложение хочется с ноутбука по сети — `http://<IP машины>:8000`. Сработает ли это,
зависит от того, **на каком адресе** слушает порт на этой машине:
```bash
docker ps --format '{{.Names}}  {{.Ports}}'
sudo ss -tlnp | grep 8000       # без sudo ss не покажет, чей это процесс
```
- **`0.0.0.0:8000`, процесс `docker-proxy`** — порт опубликован Docker на всех
  интерфейсах (наш `runArgs`). С ноутбука по IP машины откроется, если не мешает
  файрвол: `sudo ufw allow 8000/tcp`.
- **`127.0.0.1:8000`, процесс `docker-proxy`** — Docker опубликовал порт, но только
  на `localhost`. Так выходит, например, с `"appPort": [8000]`: VS Code публикует его
  как `-p 127.0.0.1:8000:8000`. В `docker ps` это видно сразу —
  `127.0.0.1:8000->8000/tcp`. Снаружи не достучаться.
- **`127.0.0.1:8000`, процесс `code`** — туннель самого VS Code (`forwardPorts` или
  кнопка **Add Port** во вкладке Ports). Тоже только `localhost`. Чтобы туннель
  слушал все интерфейсы, нужна настройка `"remote.localPortHost": "allInterfaces"` в
  settings.json VS Code на этой машине — в `devcontainer.json` она лежит в
  комментарии с подсказкой.

Итог: важно не только **какой** порт открыт, но и **на каком адресе** — ровно то, что
мы разбирали в лекции 5 про `127.0.0.1` и `0.0.0.0`. Если открывать порт наружу не
хочется — пробросьте его SSH-туннелем с ноутбука, как в лекции 5:
`ssh -L 8000:localhost:8000 user@<IP машины>`.

### Вкладка Ports

Во вкладке **Ports** внизу окна VS Code видно все порты dev-контейнера и куда они
выведены:
- **hello app (8000)** — наш порт: подпись взялась из `portsAttributes`.
- Пометка **Auto Forwarded** — порт, который VS Code нашёл сам: по умолчанию он
  пробрасывает всё, что начинает слушать любой процесс в контейнере. Без
  `otherPortsAttributes` здесь появляются служебные порты `vscode-server` и
  внутреннего `dockerd` со случайными номерами (36983, 42867 и т.п.) — они безвредны,
  но засоряют список. С нашей настройкой VS Code их игнорирует.

### Шаг 7. Меняем среду

Поменяли `devcontainer.json`, `Dockerfile` или скрипт — пересоберите:
**Dev Containers: Rebuild Container**. Всё, что лежит в папке проекта, сохранится
(она примонтирована с вашей машины), а окружение пересоздастся с нуля по описанию.
В этом и смысл: среда — это код, её можно удалить и получить заново за минуты.

Без VS Code то же самое делает официальный CLI (нужен Node.js):
```bash
npx @devcontainers/cli up --workspace-folder .
npx @devcontainers/cli exec --workspace-folder . uv run pytest -q
```
Его используют в CI, чтобы тесты шли ровно в той же среде, что у разработчиков.

Файлы `.devcontainer/`, `pyproject.toml`, `uv.lock` и `tests/` — в git, а служебное —
мимо него:
```bash
printf '__pycache__/\n.venv/\n.pytest_cache/\n.ruff_cache/\n' > .gitignore
```
Новый человек клонирует репозиторий, жмёт «Reopen in Container» — и получает ровно то же
окружение: тот же Python, те же пакеты, те же расширения редактора. Ноль «у меня не
ставится».

## Частые ошибки · слайды 22–23

- **«Cannot connect to the Docker daemon»** — не запущен Docker Desktop / демон.
- **«порт недоступен в браузере»** — забыли `-p`, или перепутали порядок
  `-p ХОСТ:КОНТЕЙНЕР`, или приложение слушает `127.0.0.1` вместо `0.0.0.0`.
- **«изменил код, а в контейнере старое»** — забыли пересобрать образ
  (`docker build`) или контейнер запущен из старого тега.
- **«кэш не срабатывает»** — `COPY . .` стоит до установки зависимостей, поэтому
  любой правкой кода инвалидируется слой с pip.
- **«docker build тянет весь проект долго»** — нет `.dockerignore`, в контекст
  сборки уходят `.git`, `.venv`, данные.
- **«push: denied»** — не сделали `docker login` или тег без своего аккаунта.
- **«данные пропали после docker rm»** — не примонтировали том; данные были
  только в эфемерном слое контейнера.
- **«Feature … failed to install»** при сборке dev-контейнера — у фичи
  `docker-in-docker` не указано `"moby": false`, а базовый образ на Debian 13.
- **dev-контейнер не стартует: «port is already allocated»** — порт 8000 из
  `runArgs` на машине уже занят. Поменяйте левую часть (`0.0.0.0:8001:8000`) или
  остановите то, что его держит.
- **с другого компьютера порт не открывается** — смотрите `docker ps` и
  `sudo ss -tlnp`: если там `127.0.0.1:8000`, порт опубликован только на localhost
  (см. «Порт 8000 с другого компьютера в сети»).
- **поменял `devcontainer.json`, а ничего не изменилось** — среду нужно пересобрать:
  **Dev Containers: Rebuild Container**.
- **`ModuleNotFoundError: No module named 'app'` в тестах** — нет
  `pythonpath = ["."]` в `[tool.pytest.ini_options]`.
- **«port is already allocated»** — порт 8080 занят другим контейнером: посмотрите
  `docker ps` и удалите старый (`docker rm -f web`).
