# Первичная настройка и защита Debian/Ubuntu-сервера

> ⚠️ **Важно про порядок SSH.** Ключ нужно добавить и **проверить вход по ключу** до того, как ты запретишь вход по паролю и под root и сменишь порт. Иначе есть риск заблокировать себе доступ к серверу.
>
> **Не закрывай текущую SSH-сессию**, пока не проверишь вход в **новом** окне терминала. Уже открытое соединение не рвётся ни при смене порта, ни при включении файрвола — это твоя страховка.
>
> 💡 На виртуалке в Parallels страховка двойная: даже если SSH сломался, остаётся консоль самой ВМ в окне Parallels.

---

## 0. Подготовка: root и переменные

```bash
sudo -i
```
Открывает оболочку **root**. Все команды ниже выполняются от root, поэтому `sudo` перед ними не нужен.
- Почему не `sudo` перед каждой командой: в строках вида `echo ... > /etc/файл` перенаправление `>` делает твоя оболочка, а не команда после `sudo`, — и без root запись в `/etc` не пройдёт.

```bash
NEWUSER=ivanov      # <-- подставь своё имя пользователя (латиница, без точек)
SSH_PORT=2223       # новый порт SSH
```
Переменные, чтобы не переписывать имя и порт в каждой команде.
- Живут только в текущей сессии: если переоткрыл терминал или заново сделал `sudo -i` — задай их ещё раз.
- Проверить: `echo $NEWUSER $SSH_PORT`.

## 1. Пакеты (apt)

```bash
apt update && apt upgrade -y
```
- `apt update` — обновляет список доступных пакетов из репозиториев (не сами пакеты, только «каталог»).
- `&&` — выполнить следующую команду, только если предыдущая завершилась успешно.
- `apt upgrade -y` — обновляет уже установленные пакеты до свежих версий.
  - `-y` — автоматически отвечать «да» на все вопросы (без интерактива).

```bash
apt install -y curl gnupg lsb-release jq fail2ban ufw
```
Устанавливает набор пакетов:
- `curl` — HTTP-клиент для скачивания/запросов из командной строки.
- `gnupg` — работа с GPG-ключами (нужно, например, для добавления сторонних репозиториев).
- `lsb-release` — утилита, которая сообщает название/версию дистрибутива.
- `jq` — парсер и обработчик JSON в командной строке.
- `fail2ban` — блокирует IP после множества неудачных попыток входа.
- `ufw` — упрощённый интерфейс к firewall (iptables/nftables).

## 2. Новый пользователь и вход по ключу

```bash
adduser "$NEWUSER" --gecos "" --disabled-password
```
Создаёт пользователя.
- `--gecos ""` — пропускает интерактивные вопросы (полное имя, телефон и т.д.), оставляя их пустыми.
- `--disabled-password` — создаёт аккаунт без пароля (пока пароль не задан, войти по паролю нельзя).

```bash
usermod -aG sudo "$NEWUSER"
```
Добавляет пользователя в группу `sudo` (право повышать привилегии).
- `-a` — **append**, добавить к уже имеющимся группам (без `-a` группы перезапишутся — важный флаг!).
- `-G sudo` — какую группу добавить.

```bash
passwd "$NEWUSER"
```
Задаёт пароль пользователю (интерактивно). Пароль понадобится один раз — чтобы скопировать ключ командой `ssh-copy-id` ниже.

### Добавляем SSH-ключ

**Способ А (проще) — с твоего компьютера**, не с сервера. Если ключа ещё нет — создай его: `ssh-keygen -t ed25519`. Затем:
```bash
ssh-copy-id -i ~/.ssh/id_ed25519.pub ivanov@10.211.55.5   # свои имя и IP сервера
```
- Спросит пароль пользователя (тот, что задали через `passwd`) и сам положит ключ на сервер с правильными правами.
- IP сервера — на сервере: `hostname -I`.

**Способ Б — вручную на сервере**, если `ssh-copy-id` недоступен:
```bash
mkdir -p /home/$NEWUSER/.ssh
nano /home/$NEWUSER/.ssh/authorized_keys     # вставь строку из ~/.ssh/id_ed25519.pub своего компьютера
chmod 700 /home/$NEWUSER/.ssh
chmod 600 /home/$NEWUSER/.ssh/authorized_keys
chown -R $NEWUSER:$NEWUSER /home/$NEWUSER/.ssh
```
- `mkdir -p` — создать папку (и не ругаться, если она уже есть).
- В `authorized_keys` кладём **публичный** ключ (файл `.pub`) — одна строка вида `ssh-ed25519 AAAA… user@host`.
- `chmod 700` на папку и `600` на файл — только владельцу. SSH требователен к правам и откажется пускать, если они слишком открыты.
- `chown -R $NEWUSER:$NEWUSER` — владельцем должен быть сам пользователь, а не root, под которым ты всё создавал.

### ✅ Проверяем вход по ключу — обязательно

**В новом окне терминала** на своём компьютере:
```bash
ssh -o PasswordAuthentication=no ivanov@10.211.55.5
```
- `-o PasswordAuthentication=no` — запрещаем клиенту даже пытаться войти по паролю: пустит только если работает ключ.
- Вошёл без вопроса о пароле → ключ работает, можно двигаться дальше.
- Получил `Permission denied (publickey)` → **дальше не иди**: проверь, что в `authorized_keys` лежит именно `.pub`-ключ и права стоят как выше.

### sudo без пароля

```bash
echo "$NEWUSER ALL=(ALL) NOPASSWD:ALL" > /etc/sudoers.d/$NEWUSER
chmod 440 /etc/sudoers.d/$NEWUSER
visudo -cf /etc/sudoers.d/$NEWUSER
```
Разрешает пользователю выполнять `sudo` **без ввода пароля**.
- Строка `… ALL=(ALL) NOPASSWD:ALL` — «с любого хоста, от любого пользователя, любые команды, без пароля».
- `/etc/sudoers.d/` — отдельный файл правил, чтобы не трогать основной `/etc/sudoers`.
- `chmod 440` — права, которые ожидает sudo: только чтение, только root.
- `visudo -cf` — **проверяет синтаксис** файла. Должно быть `parsed OK`. Если видишь ошибку — сразу удали файл (`rm /etc/sudoers.d/$NEWUSER`): ошибка в sudoers ломает `sudo` целиком.

> 🔐 `NOPASSWD:ALL` удобно, но снижает безопасность: любой, кто попал в сессию этого пользователя, получает root без пароля. Для боевого сервера стоит подумать, нужно ли это.

## 3. Логи (journald)

```bash
sed -i -E 's/^#*SystemMaxUse=.*/SystemMaxUse=100M/' /etc/systemd/journald.conf
grep SystemMaxUse /etc/systemd/journald.conf     # должно быть: SystemMaxUse=100M
```
Ограничивает размер системного журнала до 100 МБ, чтобы логи не съели диск.
- `sed -i` — редактировать файл **на месте** (in-place); `-E` — расширенные регулярные выражения.
- `s/шаблон/замена/` — команда замены.
- `^#*SystemMaxUse=.*` — строка с этим параметром: закомментированная или нет (`#*` — ноль или больше `#`) и с любым значением после `=` (`.*` — в том числе пустым, как в файле по умолчанию: `#SystemMaxUse=`).
- `grep` — убеждаемся, что замена действительно произошла. Если `grep` ничего не нашёл — строки в файле не было, допиши её в секцию `[Journal]` руками.

```bash
systemctl restart systemd-journald
journalctl --disk-usage
```
Перезапускает службу журналирования, чтобы настройка вступила в силу, и показывает, сколько журнал занимает сейчас.

## 4. Firewall (ufw)

Настраиваем **до** смены порта SSH: новый порт должен быть открыт заранее.

```bash
ufw default deny incoming
ufw default allow outgoing
```
Политика по умолчанию: **запрещать** все входящие соединения (кроме разрешённых явно) и **разрешать** все исходящие.

```bash
ufw allow 22/tcp
ufw allow $SSH_PORT/tcp
```
Разрешает SSH на **обоих** портах: текущем `22` (через него ты сейчас подключён) и будущем `2223`.
- `/tcp` — только протокол TCP.
- Порт `22` закроем в конце, когда убедимся, что вход по новому порту работает.

```bash
ufw allow 80/tcp
ufw allow 443/tcp
```
Открывают порты веб-сервера: `80` (HTTP) и `443` (HTTPS).

```bash
ufw --force enable
ufw status verbose
```
Включает firewall и показывает правила.
- `--force` — не спрашивать подтверждения «соединение может прерваться» (уже открытая сессия не рвётся).
- В `status` должны быть `22/tcp`, `2223/tcp`, `80/tcp`, `443/tcp` — все `ALLOW IN`.

## 5. SSH

Свои настройки кладём **отдельным файлом**, а не правим `/etc/ssh/sshd_config`:

```bash
cat > /etc/ssh/sshd_config.d/00-hardening.conf <<EOF
Port $SSH_PORT
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
EOF
```
- `cat > файл <<EOF … EOF` — **heredoc**: всё между `EOF` и `EOF` записывается в файл (`>` перезаписывает целиком). `$SSH_PORT` внутри подставится значением.
- `Port` — новый порт SSH (снижает шум от автоматических сканеров, но это не полноценная защита).
- `PermitRootLogin no` — запрет входа под root.
- `PasswordAuthentication no` и `KbdInteractiveAuthentication no` — вход только по ключу.
- **Почему отдельный файл и почему `00-`.** В начале `sshd_config` стоит `Include /etc/ssh/sshd_config.d/*.conf`, а sshd берёт **первое** встреченное значение каждого параметра. Во многих образах там уже лежит, например, `50-cloud-init.conf` с `PasswordAuthentication yes` — и правка основного файла молча ничего бы не дала. Файлы читаются по алфавиту, поэтому `00-…` оказывается первым и побеждает.

```bash
mkdir -p /run/sshd
sshd -t && echo "конфиг OK"
sshd -T | grep -iE '^(port|permitrootlogin|passwordauthentication) '
```
Проверяем **до** перезапуска.
- `sshd -t` — проверка синтаксиса. Ошибка здесь → не перезапускай SSH, сначала исправь файл.
- `mkdir -p /run/sshd` — служебная папка, без которой `sshd -t` на некоторых Ubuntu ругается `Missing privilege separation directory`.
- `sshd -T` — итоговые настройки, какими их увидит sshd. Ожидаем: `port 2223`, `permitrootlogin no`, `passwordauthentication no`.

```bash
systemctl disable --now ssh.socket
systemctl enable ssh.service
systemctl restart ssh.service
```
Переключаем SSH на обычный сервис и перезапускаем.
- В новых Ubuntu SSH запускается через `ssh.socket` (сокет держит порт `22` и будит sshd по запросу) — и тогда смена порта может не примениться. Поэтому **сначала** отключаем сокет, потом включаем и перезапускаем `ssh.service`.
- `disable --now` — убрать из автозапуска и сразу остановить; `enable` — добавить в автозапуск.
- В Debian `ssh.socket` по умолчанию не используется — первая команда может ответить, что юнит не найден или уже выключен. Это нормально.

```bash
systemctl status ssh.service --no-pager
ss -tlnp | grep sshd
```
- `status` — служба `active (running)`. Строки `Found left-over process … sshd: <имя>` — это твоя текущая SSH-сессия: systemd её не тронул, так и должно быть.
- `ss -tlnp` — кто слушает порты: должна быть строка с `:2223` (и больше **нет** `:22`).

### ✅ Проверяем новый вход — обязательно

**В новом окне** на своём компьютере (старую сессию не закрывай!):
```bash
ssh -p 2223 ivanov@10.211.55.5      # должен пустить по ключу
ssh -p 2223 root@10.211.55.5        # должен отказать: Permission denied
```
Всё работает → закрываем старый порт `22`:
```bash
ufw delete allow 22/tcp
ufw status
```
Не пустило → в старой сессии смотри `journalctl -u ssh -n 30` и `sshd -T`, исправь файл `00-hardening.conf` и перезапусти `ssh.service`.

> Для удобства на своём компьютере можно добавить в `~/.ssh/config` блок
> `Host myvm` / `HostName 10.211.55.5` / `User ivanov` / `Port 2223` — и входить просто `ssh myvm`.

## 6. Fail2ban

```bash
cat > /etc/fail2ban/jail.local <<EOF
[DEFAULT]
ignoreip = 127.0.0.1/8 ::1 10.211.55.0/24
banaction = ufw
maxretry = 3
findtime = 3600
bantime  = 86400

[sshd]
enabled = true
port    = $SSH_PORT
backend = systemd
EOF
```
Создаёт локальный конфиг fail2ban (`jail.local` — правильное место для своих настроек, его не перезапишут при обновлении).

Секция `[DEFAULT]` (применяется ко всем «тюрьмам»):
- `ignoreip` — «белый список»: эти адреса никогда не банятся. `127.0.0.1/8` и `::1` — сам сервер; `10.211.55.0/24` — сеть Parallels (Shared Network), чтобы не забанить собственный компьютер. **Подставь свою сеть**: первые три числа из `hostname -I` и `.0/24`.
- `banaction = ufw` — банить через ufw (согласовано с нашим firewall).
- `maxretry = 3` — сколько неудачных попыток допускается.
- `findtime = 3600` — за какое окно времени считаются попытки (3600 сек = 1 час).
- `bantime = 86400` — на сколько банить (86400 сек = 24 часа).

Секция `[sshd]` (защита SSH):
- `enabled = true` — «тюрьма» включена.
- `port = $SSH_PORT` — какой порт закрывать при бане: наш новый порт, а не стандартный `22`.
- `backend = systemd` — читать попытки входа из журнала systemd. Файла `/var/log/auth.log` в Debian 12 и минимальных образах просто нет, и с ним fail2ban не запустился бы.

```bash
systemctl restart fail2ban
sleep 3
systemctl status fail2ban --no-pager
fail2ban-client status sshd
```
- `sleep 3` — fail2ban стартует не мгновенно. Если спросить его сразу после `restart`, получишь `ERROR Failed to access socket path … Is fail2ban running?` — это не поломка, просто повтори команду через пару секунд.
- `status` — `active (running)`.
- `fail2ban-client status sshd` — тюрьма работает: видно счётчики попыток и список забаненных.
- Если fail2ban не стартует с ошибкой про `systemd` — доставь модуль: `apt install -y python3-systemd` и перезапусти.

## 7. DNS (systemd-resolved) — необязательно

Этот шаг нужен, только если DNS от провайдера или сети работает плохо. На учебной виртуалке его можно **пропустить**: в некоторых сетях (например, университетских) внешние DNS-серверы закрыты, и после этого шага перестанут открываться сайты и работать `apt`.

```bash
cp /etc/systemd/resolved.conf /etc/systemd/resolved.conf.bak
```
Резервная копия конфига DNS (`.bak`) — чтобы можно было откатиться.

```bash
cat > /etc/systemd/resolved.conf <<EOF
[Resolve]
DNS=9.9.9.9 8.8.8.8 1.1.1.1
EOF
systemctl restart systemd-resolved
```
- `DNS=…` — основные DNS-серверы: Quad9, Google, Cloudflare.
- Резервные серверы (`FallbackDNS`) оставляем по умолчанию — они подстрахуют, если эти недоступны.

```bash
resolvectl query github.com
```
Проверка: должен вернуть IP-адреса. Не вернул — откатываемся:
```bash
cp /etc/systemd/resolved.conf.bak /etc/systemd/resolved.conf && systemctl restart systemd-resolved
```

## 8. Управление банами

```bash
tail -n 20 /var/log/fail2ban.log
```
Последние строки лога fail2ban (видно, кого банило/разбанивало).
- `tail -n 20` — последние 20 строк; `-f` — следить в реальном времени (Ctrl-C — выход).

```bash
fail2ban-client set sshd unbanip 203.0.113.5
```
Разбанивает конкретный адрес.
- `sshd` — имя «тюрьмы».
- `unbanip <IP>` — вместо `203.0.113.5` подставь реальный адрес.

## Короткий чек-лист безопасного порядка

1. `sudo -i`, задать `NEWUSER` и `SSH_PORT`.
2. Создать пользователя, добавить SSH-ключ, **проверить вход по ключу** в новом окне.
3. Настроить ufw и **открыть оба порта** (`22` и `2223`), потом включить.
4. Только потом менять SSH-порт, запрещать root и пароли (`00-hardening.conf`), проверить `sshd -t`, перезапустить SSH.
5. **Не закрывать текущую сессию** — открыть новую и убедиться, что вход по `2223` работает, а root не пускает.
6. После проверки закрыть порт `22`: `ufw delete allow 22/tcp`.
