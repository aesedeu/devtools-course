## Bash. Скрипты.

На первой паре команды мы набирали руками. На второй и третьей Git запомнил снимок проекта.

Сегодня будем писать скрипты: команды, собранные в файл. Его запускают ещё раз, и время экономите вы и коллега. Не надо заново вспоминать, в каком порядке всё набирали.

## **Сегодня пройдемся по этому плану:**

1. **Зачем файл** – одна и та же последовательность не должна жить только в истории терминала.
2. **Bash и первый файл** – что это за программа и как она читает скрипт.
3. **Кавычки и переменные** – где строка разваливается и кому её видно.
4. **Где скрипт ищет файлы** – текущая папка и `$0`.
5. **Временный файл** – `mktemp`, чтобы два запуска не писали в одно имя.
6. **Код возврата и строгий режим** – `$?`, `set -e`, `set -u`, `pipefail`.
7. **Аргументы** – слова после имени скрипта.
8. **Команда `[[ ]]`** – вопрос к файлу, строке или числу. Ответ – код возврата.
9. **Условие, цикл, функция** – скрипт выбирает ветку и не копирует одни и те же строки.
10. **Два бытовых скрипта** – заметка на день и окружение, которое остаётся в терминале.
11. **Трассировка** – `bash -n` и `bash -x`.

**Что понадобится:** терминал, в котором есть bash. На macOS окно часто открыто в zsh или fish: примеры этой пары запускайте командой `bash файл`.

Дальше все примеры из **одной папки**, по порядку разделов. Строку `set -e` в живом терминале не набирайте: что она делает, будет в строгом режиме. Неудачная команда после неё закроет сессию. В файле скрипта она как раз нужна.

```bash
mkdir -p ~/Desktop/devtools-bash && cd ~/Desktop/devtools-bash
# mkdir – make directory
# -p    – parents (создай промежуточные папки, если их нет)
```

## **Зачем скрипт, если команды уже работают.**

Команды из истории терминала остаются в одном окне на одной машине. Файл можно отдать коллеге и запустить завтра: порядок проверок записан, а не вспомнен по стрелке вверх.

> **Скрипт** – текстовый файл с командами. Shell читает его сверху вниз и выполняет так же, как если бы вы вводили строки сами.

Скрипт – это `echo`, `cd`, `ls`, записанные в файл. Истории команд у него нет. `~/.bashrc`, который читает ваш терминал, он тоже не читает: видит только то, что передали при запуске, и то, что родитель положил в окружение. Дальше соберём такой файл с нуля.

## **Что такое bash.**

На первой паре оболочка была программой между вами и ядром: вы пишете строку, она запускает другие программы. Таких программ несколько. Сегодня берём одну и называем её точно.

> **Bash (Bourne Again Shell)** – конкретная оболочка. Bourne – фамилия автора старой оболочки `sh`, Стивена Борна. Again – «ещё раз»: bash умеет то, что умел `sh`, и сверх того. Это файл на диске, обычно `/bin/bash` или `/usr/bin/bash`. Запускают его как любую другую программу: пишете `bash`.

> **sh** – имя более простой оболочки. На Ubuntu `/bin/sh` часто указывает не на bash, а на другую программу, dash. Скрипт с первой строкой `#!/bin/sh` читает она.

> **zsh** – ещё одна оболочка. На macOS в терминале часто открыта именно она.

> **fish** – ещё одна оболочка, Friendly Interactive Shell. Её ставят, когда в терминале нужны другие подсказки.

Их объединяет работа, не формат файла. Каждая читает текст, строку с клавиатуры или строки из файла, и просит ядро запустить процесс: программа, аргументы, текущая папка, переменные окружения, три потока. Суффикс `.sh` только имя. Кто читает файл, решает первая строка `#!` или команда, которой файл отдали.

Расходятся они в правилах этого текста. Скрипты пары написаны для bash. Если окно открыл `zsh` или `fish`, запускайте `bash файл`: тогда текст читает bash.

```bash
which bash
# which – какой файл выполнится, если написать это имя
# получается: /bin/bash или /usr/bin/bash

bash --version
# --version – напечатай версию и сразу выйди
```

Вы набрали `ls`. Уже запущенный bash нашёл файл `ls` и попросил ядро его стартовать. Вы набрали `bash` и имя файла. Тот же bash стартует **второй** bash, и уже второй читает файл сверху вниз. Скрипт – список команд для этой программы.

`ls` и `wc` – отдельные программы, файлы на диске. `cd`, `export` и `set` – команды самого bash: отдельного файла у них нет. Какая перед вами, говорит `type`. Спросить надо у bash: в zsh у `ls` часто алиас, и ответ будет про него.

```bash
bash -c 'type ls'
# -c   – выполнить строку в кавычках и выйти, файл не нужен
# type – файл это или команда самого bash
# получается: ls is /bin/ls
# путь может быть /usr/bin/ls

bash -c 'type cd'
# получается: cd is a shell builtin
```

## **Первый файл.**

Новый файл, `start.sh`. Внутри две команды: сначала печать строки, потом печать текущей папки. Bash выполнит их в этом порядке, как если бы вы набрали обе сами.

Записать файл из терминала: `cat` читает текст, `>` кладёт его в файл, слово после `<<` говорит, где текст кончается. Кавычки у `EOF` значат одно: пока мы **записываем** файл, знаки `$` не подставлять. Зачем кавычки устроены именно так, разберём следующим разделом. Здесь они только берегут текст.

```bash
cat > start.sh << 'EOF'
#!/usr/bin/env bash
echo 'файл читается сверху вниз'
pwd
EOF
# cat     – вывести то, что пришло на stdin
# >       – этот вывод записать в файл (старое содержимое стереть)
# <<      – stdin брать не с клавиатуры, а из следующих строк
# 'EOF'   – стоп-слово: строка EOF заканчивает текст
```

Первая строка файла по частям:

- `#!` – shebang. Ядро читает её и кормит файл указанной программой. Строка обязана быть первой: пустая строка или пробел перед ней, и ядро её не увидит.
- `/usr/bin/env` – программа `env`. Она берёт следующее слово и ищет такой файл в `PATH`. Так же `#!/usr/bin/env python3` ищет `python3`, а не путь, зашитый на одной машине.
- `bash` – кого искать. Жёсткое `#!/bin/bash` тоже работает, пока bash лежит именно там. `env` переживает другое место установки.

Две команды ниже shebang: `echo` печатает слова в stdout, `pwd` печатает текущую папку. Вторая выполняется только после первой.

Два способа запустить. Смысл разный.

```bash
bash start.sh
# bash    – запусти программу bash
# start.sh – аргумент: какой файл ей прочитать
# получается: файл читается сверху вниз
#             .../devtools-bash
# бит исполнения файлу не нужен: исполняется bash, файл ему отдают как текст

chmod +x start.sh
# chmod – change mode (смени режим доступа)
# +x    – добавить execute (исполнение)

./start.sh
# ./ – файл из текущей папки, не из PATH
# получается то же самое
# здесь +x нужен, иначе Permission denied
# ядро само читает shebang и зовёт bash
```

Без точки, голое `start.sh`, shell ищет имя в `PATH`. Файла там нет, будет `command not found`, хотя `ls` его только что показал.

Файл на месте, а `./start.sh` всё равно не стартует и ругается на интерпретатор. Так бывает, если его сохранили на Windows:

```text
/usr/bin/env: ‘bash\r’: No such file or directory
```

В конце строки shebang невидимый `\r`. `env` ищет интерпретатор с именем `bash\r`. Убрать возвраты каретки:

```bash
sed -i 's/\r$//' start.sh
# sed – stream editor; -i – править файл на месте
# s/\r$// – убрать \r в конце строки
```

Так пишет GNU `sed` на Linux. На macOS тот же флаг требует пустой суффикс: `sed -i '' 's/\r$//' start.sh`.

## **Кавычки.**

Файл запускается. Как только в нём появится путь с пробелом, shell прочитает строку не так, как её читаете вы.

Папка `devtools bash` для вас одно имя. Пробел для shell – граница между словами, пока его не защитили кавычками. Режет он строку **до** того, как команда её увидит.

Если терминал у вас zsh, как часто на macOS, ту же проверку запускайте через `bash файл`. В zsh некавыченная переменная на слова сама не режется, и поломки вы не увидите.

```bash
cat > split.sh << 'EOF'
#!/usr/bin/env bash
name='devtools bash'
# одна переменная, внутри пробел
# вокруг = пробелов нет: name = '...' – это уже другая команда

mkdir "$name"
# mkdir с кавычками создаёт одну папку

cd $name
# cd получил два слова: devtools и bash
echo 'скрипт идёт дальше: ошибка cd его не остановила'
EOF

bash split.sh
# скрипт идёт дальше: ошибка cd его не остановила
# папка «devtools bash» не открылась
```

Текст ошибки зависит от версии bash. На bash 4 и новее, как на Ubuntu, будет `cd: too many arguments`: команда увидела два слова. Системный bash macOS часто версии 3.2: он берёт только первое слово и пишет `cd: devtools: No such file or directory`. В обоих случаях одно имя с пробелом до `cd` не дошло.

Та же папка, кавычки на месте:

```bash
cat > split.sh << 'EOF'
#!/usr/bin/env bash
name='devtools bash'
cd "$name"
pwd
EOF

bash split.sh
# получается: .../devtools-bash/devtools bash

rm -r "devtools bash"
# -r – убрать папку, которую создали для примера
```

> **Двойные кавычки** – один аргумент, но `$переменная` внутри раскрывается.

> **Одинарные кавычки** – один аргумент и никакой подстановки. Знак `$` остаётся знаком доллара.

```bash
name=port
echo '$name'
# получается: $name

echo "папка: $name"
# получается: папка: port
```

Одинарные кавычки мы уже использовали в `<< 'EOF'`, когда писали файл: иначе shell подставил бы переменные **в момент записи**, а не когда скрипт потом запустят.

Ловушка, из-за которой ломаются скрипты: переменная без кавычек. Путь `My Project` станет двумя аргументами, `rm` и `cd` увидят не то имя. Дальше в конспекте переменные в двойных кавычках.

## **Переменная скрипта и переменная окружения.**

Присваивание вы только что видели: `имя=значение`, без пробелов вокруг `=`. Прочитать – `$имя`.

К имени часто приклеивают хвост: не `port`, а `port_log`. Без фигурных скобок shell ищет другую переменную, с этим хвостом в имени.

```bash
name=port
echo "$name_log"
# пусто: переменной name_log нет, это не name и текст _log

echo "${name}_log"
# получается: port_log
# ${name} – то же значение, скобки отделяют имя от _log
```

`export` с первой пары отдаёт переменную **дочерним** процессам. `./скрипт` – такой процесс. Присваивание без `export` остаётся в вашем терминале: скрипт на этом месте увидит пустоту.

Проверка на живом файле:

```bash
cat > envdemo.sh << 'EOF'
#!/usr/bin/env bash
echo "внутри скрипта BOBA=$BOBA"
EOF

chmod +x envdemo.sh
BOBA=123
./envdemo.sh
# получается: внутри скрипта BOBA=
# 123 есть в терминале, в дочерний процесс её не отдали

export BOBA
./envdemo.sh
# получается: внутри скрипта BOBA=123

unset BOBA
# unset – убрать переменную из этой сессии
```

`export` отдаёт копию процессам, которые вы запустите **после** этой команды из этого окна. Второе окно терминала – не ребёнок этой сессии. Там `echo "$BOBA"` пустое, пока `export` не сделан в том окне.

Скрипт не читает `~/.bashrc`. Туда вы могли дописать `PATH` или алиас – интерактивный терминал это видит, `./envdemo.sh` нет. Алиас в скрипте тоже не раскрывается: скрипт ищет команду в `PATH` или среди встроенных команд shell.

Постоянство «на всегда» через правку `~/.bashrc` сегодня не делаем. Для одной проверки хватает переменной в файле скрипта или `export` в той сессии, которая скрипт запускает.

## **Где скрипт ищет файлы.**

Запуск и текущая папка – разные вещи. Скрипт получает ту папку, **из которой вы его вызвали**, а не ту, где лежит файл.

```bash
cat > where.sh << 'EOF'
#!/usr/bin/env bash
pwd
# pwd – print working directory
EOF

chmod +x where.sh
./where.sh
# получается: .../devtools-bash
```

Вызовем тот же файл из другого места:

```bash
cd /tmp
~/Desktop/devtools-bash/where.sh
# получается: /tmp

cd ~/Desktop/devtools-bash
```

`pwd` внутри скрипта показал `/tmp`. Файл лежит в `devtools-bash`, процесс стоит там, откуда его вызвали.

Открыть файл рядом со скриптом по текущей папке нельзя: вы только что видели, что она бывает `/tmp`. Нужно имя, которым скрипт вызвали, и каталог от этого имени.

> **`$0`** – имя скрипта так, как его вызвали: `./where.sh` или полный путь. На первой паре в `awk` тот же знак был всей строкой. Здесь его читает bash, и это имя файла.

> **Подстановка команды** – `$(команда)`. Shell выполняет команду и подставляет её stdout на место этой записи. В двойных кавычках она раскрывается, в одинарных нет.

> `dirname` – от пути оставляет каталог. От `./where.sh` останется `.`

Кавычки вокруг `"$0"` держат путь одним словом. Это тот же приём, что с папкой `devtools bash`.

Перепишем `where.sh`: три строки, откуда смотреть.

```bash
cat > where.sh << 'EOF'
#!/usr/bin/env bash
echo "сейчас стоим: $(pwd)"
echo "вызвали как: $0"
echo "файл лежит в: $(dirname "$0")"
EOF

./where.sh
# сейчас стоим: .../devtools-bash
# вызвали как: ./where.sh
# файл лежит в: .

cd /tmp
~/Desktop/devtools-bash/where.sh
# сейчас стоим: /tmp
# вызвали как: полный путь к where.sh
# файл лежит в: каталог этого пути, не /tmp

cd ~/Desktop/devtools-bash
```

`cd` внутри скрипта меняет папку **этого** процесса. Ваш терминал после `./where.sh` остаётся на месте.

## **Временный файл.**

`echo 'заметка' > kept.txt` создаёт обычный файл. Имя выбрали вы, файл лежит в папке урока, пока вы сами его не сотрёте. Такой файл хранят: заметку, лог, скрипт.

Черновик – не другой тип файла. Это тоже обычный файл, только имя ему выдаёт система, и к концу работы его стирают. Фиксированное `/tmp/work` для этого плохо: второй запуск попадёт в тот же путь и сотрёт то, что ещё нужно первому.

> `mktemp` – создать обычный пустой файл с именем, которого ещё нет, и напечатать этот путь.

```bash
echo 'заметка' > kept.txt
# имя наше, файл остаётся

tmp="$(mktemp)"
# mktemp – make temporary
# $(...) – подстановка, как в where.sh: на место записи встаёт путь
# печатает что-то вроде /tmp/tmp.Ab12cd и создаёт пустой файл

echo 'черновик' > "$tmp"
ls -l kept.txt "$tmp"
# -l – long: у обоих обычный файл, отличаются путь и имя

cat "$tmp"
# получается: черновик

rm "$tmp" kept.txt
```

Кавычки вокруг `"$tmp"` те же, что у пути с пробелом. Повторите `mktemp` ещё раз: путь другой. Два запуска больше не делят один файл.

Несколько черновиков кладут в каталог. Отдельной команды `mktempdir` нет: каталог создаёт тот же `mktemp` с флагом `-d`.

```bash
dir="$(mktemp -d)"
# -d – directory: создать каталог, не файл

echo 'черновик' > "$dir/note.txt"
ls "$dir"
rm -r "$dir"
# -r – убрать каталог вместе с тем, что внутри
```

Ловушка одна: `mktemp` файл создаёт, но сам не удаляет. Нет `rm` в конце – файл остаётся в `/tmp`. Файл, который нужно хранить, через `mktemp` не заводят: у него не будет вашего имени, и следующий проход его не найдёт.

## **Код возврата.**

Команда что-то напечатала. Для скрипта этого мало: надо знать, удалась она или нет. Текст на экране и успех идут разными путями. Успех – число, которое shell помнит, пока не запущена следующая команда.

> **Код возврата** – целое число. `0` значит «эта команда считает, что всё вышло». Любое другое число – неуспех. Это не текст ошибки: текст уходит в stderr, число остаётся у shell.

```bash
ls
echo $?
# $? – код возврата предыдущей команды
# получается: 0
# перед нулём ls напечатает имена файлов; на число это не влияет

ls /no/such/dir
echo $?
# сообщение No such file – это stderr
# число выбирает сама программа ls, не bash
# GNU ls, обычно Linux: 2
# ls из macOS: 1
```

Ловушка: `$?` затирается сразу.

```bash
ls /no/such/dir
echo 'я всё стер'
echo $?
# получается: 0
# это код echo, не код ls
```

Нужно число – читайте `$?` следующей же командой или сохраняйте: `code=$?`.

Завершить **весь скрипт** своим числом:

```bash
cat > stop-ok.sh << 'EOF'
#!/usr/bin/env bash
echo 'ухожу с 0'
exit 0
# exit – закончить скрипт с этим кодом
echo 'сюда не дойдём'
EOF

bash stop-ok.sh
echo $?
# получается: 0
```

```bash
cat > stop-bad.sh << 'EOF'
#!/usr/bin/env bash
echo 'не вышло' >&2
# >&2 – этот echo писать в stderr, не в stdout
exit 1
EOF

bash stop-bad.sh
echo $?
# получается: 1
# строка «не вышло» – на экране ошибки
```

`exit` в интерактивном терминале закроет сессию. Его пишем в файле.

Ноль и не ноль понадобятся в `if`. До него ещё два шага. Сейчас shell сам не останавливает скрипт из-за чужого неуспеха: после `ls /no/such` следующая строка всё равно выполнится. Остановка – следующий раздел.

## **Строгий режим.**

По умолчанию bash идёт дальше, даже если команда в середине упала. Для скрипта, который должен остановиться на ошибке, это плохо: он напечатает «всё хорошо» после команды, которая не нашла файл.

Три независимых выключателя. Потом одна строка, которая включает все.

### **Остановка на ошибке:** `set -e`.

```bash
cat > errexit.sh << 'EOF'
#!/usr/bin/env bash
set -e
# set -e – errexit: ненулевой код останавливает скрипт

ls /no/such/dir
echo 'сюда не дойдём'
EOF

bash errexit.sh
echo $?
# ls пишет ошибку, скрипт обрывается, код ненулевой
# строки «сюда не дойдём» нет
```

Не включайте `set -e` в живой сессии. Демонстрация – только `bash errexit.sh`.

Одно исключение будет сразу после условий: проверка в `if` имеет право вернуть не ноль, и скрипт от этого не оборвётся. Иначе ветки «иначе» не получится. Пока `if` ещё нет, не прячьте ошибку, чтобы скрипт дошёл до конца: строгий режим тогда молчит, и падение снова не видно.

### **Незаданная переменная:** `set -u`.

Опечатка в имени молча раскрывается в пустую строку. Команда, которая ждала путь, получает пустоту и задевает не то место. `set -u` делает такое ошибкой.

```bash
cat > nounset.sh << 'EOF'
#!/usr/bin/env bash
set -u
# set -u – nounset: обращение к незаданной переменной останавливает скрипт

echo "$BACKUP_DIR"
echo 'сюда не дойдём'
EOF

bash nounset.sh
# получается: nounset.sh: line ...: BACKUP_DIR: unbound variable
```



### **Конвейер:** `pipefail`.

Конвейер – несколько команд через `|`. Слева направо stdout одной становится stdin следующей. Сначала запустите падение и посмотрите, остановит ли его `set -e`.

```bash
cat > pipe.sh << 'EOF'
#!/usr/bin/env bash
set -e
ls /no/such/dir | wc -l
echo 'дошли, хотя каталога не было'
EOF
# wc – word count
# -l – lines: сколько строк пришло на stdin

bash pipe.sh
# на экране ошибка ls: каталога нет
# число 0 – ответ wc, сколько строк он получил, не код возврата
# перед нулём wc может поставить пробелы: так он выравнивает число
# затем «дошли, хотя каталога не было»
```

`ls` упал, текст ошибки на экране, а скрипт пошёл дальше. `set -e` конвейер не остановил.

Код возврата считается у каждой команды отдельно. По умолчанию bash от всего конвейера запоминает только код **последней**. `wc` отработал и вернул 0, код `ls` выброшен. Для `set -e` ошибки не было.

`pipefail` меняет это правило: ненулевой код любого участника становится кодом всего конвейера.

```bash
cat > pipefail.sh << 'EOF'
#!/usr/bin/env bash
set -e
set -o pipefail
# -o pipefail – код конвейера ненулевой, если упал любой участник

ls /no/such/dir | wc -l
echo 'сюда не дойдём'
EOF

bash pipefail.sh
echo $?
# ошибка ls на экране по-прежнему есть
# строка 0 от wc тоже есть: wc успел посчитать пустой stdin
# «сюда не дойдём» нет, код ненулевой: set -e остановил скрипт после конвейера
```



### **Одна строка в начале файла.**

Дальше каждый скрипт, который что-то проверяет, начинается так:

```bash
set -euo pipefail
# -e        – остановиться на ошибке
# -u        – незаданная переменная – ошибка
# -o pipefail – падение в любом месте конвейера
```

Три флага, которые вы только что включили по отдельности. `set -euo pipefail` – короткая запись тех же трёх.

## **Аргументы.**

Имя и путь к файлу не должны быть зашиты в текст скрипта. Их передают при запуске.

> **Позиционный параметр** – слово после имени скрипта. `$1` – первое, `$2` – второе. `$#` – сколько их передали. В `awk` на первой паре `$1` было первым полем строки. В скрипте это слово, которое написали после имени файла.

```bash
cat > args.sh << 'EOF'
#!/usr/bin/env bash
set -euo pipefail
echo "число: $#"
echo "первый: $1"
EOF

chmod +x args.sh
./args.sh 8000
# получается:
# число: 1
# первый: 8000

./args.sh
# получается:
# число: 0
# args.sh: line ...: $1: unbound variable
# первая строка успела напечататься; на $1 скрипт остановился
```

Пустой запуск доходит до `$1` и падает, хотя `$#` уже показал 0. Дружелюбную проверку «сколько аргументов пришло» напишем после команды, которая умеет сравнить два числа. Пока скрипт, который читает `$1`, запускайте с аргументом.

`$1` внутри функции – аргумент **функции**, не скрипта. Это отдельная полка, до неё ещё дойдём.

## **Команда `[[ ]]`.**

Код возврата уже есть. Теперь нужна команда, которая сама отвечает нулём или нет: файл на месте, строка пустая, два числа равны. Искать файл через `ls` для этого шумно: `ls` печатает текст, а нам нужно только число.

> **`[[ ]]`** – команда bash. Между скобками проверка. Код `0` – проверка прошла. Код `1` – не прошла. Отдельного файла `[[` на диске нет.

```bash
bash -c 'type [['
# получается: [[ is a shell keyword
```

`shell keyword` – ключевое слово самого bash. `cd` был builtin, отдельной программой тоже не был. `[[` bash разбирает как синтаксис: скобки и проверка внутри одной команды. Поэтому пробелы обязательны. `[[` – начало, `-f` – какой вопрос, путь – к чему вопрос, `]]` – конец. Запись `[[-f note.txt]]` без пробелов – одно слово. Ключевого слова `[[` bash в ней не видит.

Проверки ниже читает bash. Если окно открыл zsh или fish, перед ними выполните `bash`: в этом же окне откроется второй bash. После последней проверки раздела – `exit`. Он закроет только этот второй bash и вернёт прежнее окно. `exit` без второго bash закроет сессию, как в разделе про код возврата.

Сначала вопрос про обычный файл. `note.txt` в папке урока ещё нет.

```bash
[[ -f note.txt ]]
echo $?
# -f – file: это обычный файл, не каталог
# получается: 1
# единицы хватает. Текст «нет такого файла» эта команда не печатает

echo 'черновик' > note.txt
[[ -f note.txt ]]
echo $?
# получается: 0
```

Тот же путь, другой вопрос. `-d` спрашивает, каталог ли это.

```bash
mkdir box
[[ -d box ]]
echo $?
# -d – directory
# получается: 0

[[ -f box ]]
echo $?
# получается: 1
# box есть, но это каталог, не обычный файл

rm note.txt
rmdir box
# rmdir – убрать пустой каталог
```

Пустая строка – отдельный вопрос, не про файл.

```bash
name=''
[[ -z "$name" ]]
echo $?
# -z – zero length: в строке нет символов
# получается: 0

name='devtools'
[[ -n "$name" ]]
echo $?
# -n – nonzero: символы есть
# получается: 0
```

Кавычки у `"$name"` – та же привычка, что у пути с пробелом. Где они меняют ответ `[[ ]]`, видно на сравнении текста ниже.

Числа сравнивают другими словами. `==` для этого не берут: он сравнивает текст.

```bash
[[ 2 -ne 1 ]]
echo $?
# -ne – not equal: числа не равны
# получается: 0

[[ 2 -eq 2 ]]
echo $?
# -eq – equal
# получается: 0

[[ 2 -lt 3 ]]
echo $?
# -lt – less than
# получается: 0

[[ '02' == '2' ]]
echo $?
# == – два текста совпали
# получается: 1
# символы разные: ноль и двойка против одной двойки

[[ 02 -eq 2 ]]
echo $?
# получается: 0
# -eq смотрит на число: 02 и 2 для него одно и то же
```

У `==` есть вторая ловушка. Правая часть без кавычек – шаблон: звёздочка значит «любые символы дальше». В кавычках звёздочка – обычный символ.

```bash
[[ 'app.py' == a* ]]
echo $?
# получается: 0
# справа шаблон: буква a и что угодно после неё

[[ 'app.py' == 'a*' ]]
echo $?
# получается: 1
# в кавычках a* – буква a и звёздочка
```

Единица от `[[ ]]` в терминале просто печатается следующим `echo $?`. В скрипте этот код читает `if`: ноль – одна ветка, единица – другая. Это следующий раздел.

Отдельной страницы нет. `man '[['` отвечает `No manual entry for [[`: кавычки нужны, иначе оболочка прочитает скобки как начало команды `[[`. Короткая справка печатается так. Как открыть длинную страницу `man bash` и найти в ней абзац, в конце пары.

```bash
bash -c 'help [['
# help – короткая справка по этой команде bash
# [[ – имя; кавычки, чтобы скобки не прочла текущая оболочка
```

В `sh` команды `[[` нет. Скрипт с `[[` и первой строкой `#!/bin/sh` на Ubuntu читает dash и останавливается ещё на синтаксисе. Файлы этой пары поэтому начинаются с `#!/usr/bin/env bash`.

## **Условие – тоже команда.**

Ноль и не ноль уже есть, и `[[ ]]` уже отвечает таким числом. Теперь скрипт выбирает, что делать. `if` смотрит на код команды сразу после себя: ноль – ветка `then`, другое число – ветка `else`, если она написана.

Проверка файла, которую только что запускали отдельно:

```bash
cat > choose.sh << 'EOF'
#!/usr/bin/env bash
set -euo pipefail

if [[ -f app.py ]]; then
  echo 'app.py есть'
else
  echo 'app.py нет' >&2
  exit 1
fi
EOF

chmod +x choose.sh
./choose.sh
echo $?
# получается: app.py нет, код 1
# код поставила ветка exit 1
# скрипт дошёл до неё: [[ стоял в if, set -e его не оборвал

echo 'print("v1")' > app.py
./choose.sh
# получается: app.py есть
```

В `if` ставят и чужую команду. Следующий файл спрашивает `ls`: ноль – каталог есть, другое число – нет.

`then`, `else` и `fi` – части одного `if`. `fi` закрывает его. Забытый `fi` – синтаксическая ошибка ещё до запуска команд; её ловит `bash -n` в разделе про трассировку.

### **Проверка в `if` и `set -e`.**

Неуспех в условии – не авария строгого режима. Иначе ветки `else` не было бы.

> `/dev/null` – файл, который выбрасывает всё, что в него записали. Сюда уводят вывод, когда нужен только код возврата.

```bash
cat > errexit-if.sh << 'EOF'
#!/usr/bin/env bash
set -euo pipefail

if ls /no/such/dir >/dev/null 2>&1; then
  echo 'каталог есть'
else
  echo 'каталога нет, и скрипт жив'
fi
echo 'после if'
EOF
# >/dev/null – stdout выбросить
# 2>&1       – stderr туда же, куда сейчас смотрит stdout

bash errexit-if.sh
# получается:
# каталога нет, и скрипт жив
# после if
```

Переписываем `args.sh`: та же проверка числа аргументов, уже без `unbound variable`. Сначала `$#`, и только потом `$1`:

```bash
cat > args.sh << 'EOF'
#!/usr/bin/env bash
set -euo pipefail

if [[ $# -ne 1 ]]; then
  echo 'запуск: ./args.sh ИМЯ' >&2
  exit 1
fi
# -ne – то же сравнение чисел, что выше; $# против 1

name="$1"
echo "имя: $name"
EOF

./args.sh
echo $?
# получается: запуск: ./args.sh ИМЯ
# код 1, скрипт до $1 не дошёл

./args.sh Mira
# получается: имя: Mira
```

## **Цикл по аргументам.**

Один файл мы уже проверяем в `if`. Несколько имён незачем копировать отдельными блоками: то же действие повторяют для каждого аргумента.

> `"$@"` – все аргументы скрипта. Каждый остаётся отдельным словом, пробел внутри аргумента ничего не режет.

> **`for`** – повторить тело для каждого слова из списка. `do` начинает тело, `done` заканчивает.

```bash
cat > list.sh << 'EOF'
#!/usr/bin/env bash
set -euo pipefail

if [[ $# -lt 1 ]]; then
  echo 'запуск: ./list.sh ФАЙЛ ФАЙЛ' >&2
  exit 1
fi

for name in "$@"; do
  if [[ -f "$name" ]]; then
    echo "файл: $name"
  else
    echo "нет: $name" >&2
  fi
done
EOF
# -lt – less than (аргументов меньше одного)

chmod +x list.sh
./list.sh app.py missing.txt
# получается:
# файл: app.py
# нет: missing.txt
```

`app.py` в папке уже есть: его создал `choose.sh`. `missing.txt` там нет, поэтому вторая строка – «нет».

Цикл не останавливает скрипт из-за `missing.txt`: внутри стоит `if`, не голый `ls`. Если нужно «первый отсутствующий файл – конец», в ветке `else` ставьте `exit 1`.

Звёздочка справа от `==` спрашивала, похожа ли строка. В `for name in *.log` shell делает другое: подставляет имена файлов. Если ни одного нет, в `name` попадёт буквальный текст `*.log`. Мы так не пишем. Имена приходят аргументами, и `"$@"` не выдумывает слово, когда аргументов ноль: тело цикла просто не выполняется.

## **Функция.**

Одинаковые пять строк в двух местах скрипта разъезжаются. Функция – эти строки под именем, в том же файле.

```bash
cat > fn.sh << 'EOF'
#!/usr/bin/env bash
set -euo pipefail

die() {
  echo "$1" >&2
  exit 1
}
# die – имя; скобки () обязательны в объявлении, даже без параметров в этой строке
# тело – до закрывающей }

if [[ $# -ne 1 ]]; then
  die 'запуск: ./fn.sh ИМЯ'
fi

echo "привет, $1"
EOF

chmod +x fn.sh
./fn.sh
# получается: запуск: ./fn.sh ИМЯ
# код 1; до echo скрипт не дошёл, потому что die вызывает exit
```



### **`$1` функции и `$1` скрипта.**

В `die` параметр `$1` – слово, которое передали **в функцию** (`die 'запуск: ...'`). Снаружи `$1` – аргумент скрипта. Имена совпали, это разные полки.

```bash
cat > slots.sh << 'EOF'
#!/usr/bin/env bash
set -euo pipefail

show() {
  echo "внутри функции: $1"
}

show 'от функции'
echo "у скрипта: $1"
EOF

chmod +x slots.sh
./slots.sh 'от скрипта'
# получается:
# внутри функции: от функции
# у скрипта: от скрипта
```

Обычная переменная внутри функции видна. Полка `$1` скрипта – нет, её туда не передали. Имя, записанное до вызова, функция читает как любое другое:

```bash
cat > seen.sh << 'EOF'
#!/usr/bin/env bash
set -euo pipefail

show() {
  echo "полка функции: $1"
  echo "запомнили: $kept"
}

kept="$1"
show 'своё слово'
EOF

chmod +x seen.sh
./seen.sh 'от скрипта'
# получается:
# полка функции: своё слово
# запомнили: от скрипта
```



### **`local` и `return`.**

Без `local` присваивание внутри функции меняет переменную всего скрипта.

```bash
cat > leak.sh << 'EOF'
#!/usr/bin/env bash
set -euo pipefail

set_n() {
  n=2
}

n=1
set_n
echo "$n"
EOF

bash leak.sh
# получается: 2
```

Снаружи стало `2`: функция записала в переменную всего скрипта. `local` оставляет присваивание внутри вызова:

```bash
cat > leak.sh << 'EOF'
#!/usr/bin/env bash
set -euo pipefail

set_n() {
  local n=2
  # local – переменная только на этот вызов
  echo "внутри: $n"
}

n=1
set_n
echo "снаружи: $n"
EOF

bash leak.sh
# получается:
# внутри: 2
# снаружи: 1
```

`exit` заканчивает весь скрипт. Из функции, которая только проверяет, нужен `return`: код возврата функции, скрипт жив.

```bash
cat > ret.sh << 'EOF'
#!/usr/bin/env bash
set -euo pipefail

has_file() {
  # return – выйти из функции с этим кодом, не из скрипта
  # 0 – файл есть, 1 – нет
  if [[ -f "$1" ]]; then
    return 0
  fi
  return 1
}

if has_file 'app.py'; then
  echo 'да'
else
  echo 'нет'
fi
echo 'скрипт дошёл до конца'
EOF

bash ret.sh
# получается:
# да
# скрипт дошёл до конца
```

`die` выше специально вызывает `exit`: сообщение и конец программы. `has_file` делает `return`: скрипт жив, и `if` сам выбирает ветку. Сейчас `app.py` ещё лежит в папке, его создал `choose.sh`, поэтому на экране «да».

## **Два скрипта, которые пригождаются.**

Два файла на обычный день. Один создаёт заметку, второй включает папку проекта в текущем терминале. Новых приёмов в них нет, только то, что уже разобрали.

### **Заметка на сегодня.**

Каждый день одна и та же папка руками: дата, каталог, пустой файл. Дата в имени нужна без пробелов: год, месяц и день через дефис.

```bash
date +%F
# date – напечатать дату и время
# +%F  – формат год-месяц-день
# получается: дата дня запуска, например 2026-10-06
```

Скрипт берёт эту строку и один аргумент – заголовок. Файл кладёт в `~/Desktop/notes/дата/`. `~` внутри двойных кавычек shell не раскрывает, поэтому домашний каталог берём из `$HOME`: это та же папка.

```bash
cat > note.sh << 'EOF'
#!/usr/bin/env bash
set -euo pipefail

if [[ $# -ne 1 ]]; then
  echo 'запуск: ./note.sh ЗАГОЛОВОК' >&2
  exit 1
fi

day="$(date +%F)"
dir="$HOME/Desktop/notes/$day"
mkdir -p "$dir"
# -p – создай папку и родителей, если их ещё нет

path="$dir/${1}.txt"
# ${1} – первый аргумент; скобки отделяют его от .txt

if [[ -f "$path" ]]; then
  echo "уже есть: $path"
  exit 0
fi

echo "$1" > "$path"
echo "записал: $path"
EOF

chmod +x note.sh
./note.sh 'черновик пары'
# получается: записал: $HOME/Desktop/notes/ГГГГ-ММ-ДД/черновик пары.txt
# дата в пути – строка, которую только что напечатал date +%F

./note.sh 'черновик пары'
# получается: уже есть: .../черновик пары.txt
```

Второй запуск файл не затирает: проверка `-f` стоит до `>`. Заголовок с пробелом передают одним аргументом, в кавычках, иначе shell разрежет его на два слова и сработает ветка `$# -ne 1`.

### **Окружение, которое остаётся.**

В терминале часто нужно одно и то же: переменная проекта и `cd` в его папку. Если записать это в обычный скрипт и запустить через `bash`, оба изменения умрут вместе с дочерним процессом. `export` и `cd` мы это уже видели.

Файл ниже поэтому не запускают как программу. Его читает уже открытый shell.

> `source` – выполнить файл в текущем shell, не в дочернем. То же делает точка: `. ./dev.sh`. Shebang такому файлу не нужен: `#!` читает ядро, когда файл запускают сами, а `source` просто читает строки.

```bash
cat > dev.sh << 'EOF'
export DEVTOOLS="$HOME/Desktop/devtools-bash"
cd "$DEVTOOLS"
EOF

cd /tmp
bash ~/Desktop/devtools-bash/dev.sh
pwd
echo "после bash: [$DEVTOOLS]"
# получается: /tmp и пустые скобки
# дочерний bash унёс и cd, и export

source ~/Desktop/devtools-bash/dev.sh
pwd
echo "после source: $DEVTOOLS"
# получается: .../devtools-bash и тот же путь в переменной

unset DEVTOOLS
```

`set -e` в этот файл не кладём. `source` включил бы его в живой терминал, и первая неудачная команда закрыла бы сессию. Скрипт, который должен отработать и закончиться, запускайте через `./скрипт` или `bash скрипт`, не через `source`.

## **Прочитать, что скрипт делает.**

Скрипт либо не запускается из-за кавычки или забытого `fi`, либо запускается и делает не то. Это разные поломки. Первую видно, не выполняя файл. Вторую видно, если попросить shell печатать команды уже после подстановки. Файлы проекта при этом не меняются.

```bash
bash -n fn.sh
# -n – syntax: прочитать файл и не выполнять
# тишина – синтаксис принят
```

Забытый `fi` или незакрытая кавычка всплывут здесь, до `./fn.sh`.

```bash
bash -x fn.sh Mira
# -x – xtrace: печатать команды так, как shell их выполнил
# строки с плюсом – трассировка, не вывод echo
```

Плюс в начале строки – команда после подстановки переменных. Так видно, что `$1` стал `Mira`, а не что «скрипт какой-то странный».

Тот же след изнутри файла даёт `set -x`. Удобно на время отладки, в готовый скрипт его не оставляем: след смешается с настоящим ответом.

Чужой разбор стиля, если пакет стоит: `shellcheck fn.sh`. Это не bash и не обязательная часть пары. Он подсказывает кавычки и `set -e`. Нет команды – не ставим сегодня ради одного прогона.

## **Команды и частые ошибки.**

Ниже те же команды, которыми сегодня пользовались.


| Команда             | Зачем                                              |
| ------------------- | -------------------------------------------------- |
| `bash файл`         | выполнить скрипт; `+x` не нужен                    |
| `./файл`            | выполнить файл из этой папки; нужен `+x` и shebang |
| `bash -n файл`      | только синтаксис                                   |
| `bash -x файл`      | печать команд после подстановки                    |
| `type имя`          | файл на диске или встроенная команда bash          |
| `man имя`           | страница руководства; выход `q`                    |
| `help имя`          | короткая справка команды самого bash               |
| `dirname "$0"`      | каталог, где лежит скрипт, от способа вызова       |
| `mktemp` / `mktemp -d` | пустой файл или каталог с новым именем          |
| `$?`                | код предыдущей команды; читают сразу               |
| `exit 1`            | закончить скрипт с неуспехом                       |
| `set -euo pipefail` | ошибка, пустая переменная, конвейер                |
| `$1`, `$#`, `"$@"`  | аргументы                                          |
| `[[ -f путь ]]`     | обычный файл; код 0 или нет                        |
| `[[ -d путь ]]`     | каталог                                            |
| `[[ -z строка ]]`   | строка пустая                                      |
| `[[ a -eq b ]]`     | числа равны; рядом `-ne` и `-lt`                   |
| `source файл`       | выполнить файл в текущем shell                     |
| `local`, `return`   | переменная функции; выход из функции, не из скрипта |


**Сообщения:**

- голое `файл` без `./` даёт `command not found`: shell искал имя в `PATH`. Запуск – `./файл` или `bash файл`;
- `Permission denied` на `./файл` – нет бита `x`, смотрите `ls -l` и `chmod +x`;
- `bad interpreter` / `bash\r` – в shebang перевод строки Windows; на Linux `sed -i 's/\r$//' файл`, на macOS `sed -i '' 's/\r$//' файл`;
- `unbound variable` – `set -u` и пустое имя или пустой `$1`;
- `[[-f файл]]` без пробелов – bash не видит команду `[[`;
- `[[ текст == a* ]]` – справа шаблон. Кавычки `'a*'` сравнивают символы как есть;
- `No manual entry for [[` – отдельной страницы нет. Короткая справка: `bash -c 'help [['`. Длинный текст: `man bash` и поиск, ниже. Команду набирайте как `man '[['`.

## **Дополнительно почитать.**

С первой пары страница открывается командой `man имя` и закрывается клавишей `q`. У программы-файла, у команды самого bash и у короткой справки тексты разные.

У программы-файла страница своя. У `man ls`, `man cd` и `man bash` в блоке одна команда: строка следом попала бы уже внутрь открытой страницы.

```bash
man ls
```

Листалка та же, что `less` с первой пары. Закрыть её клавишей `q`.

Короткий текст, не открывая страницу, у многих программ GNU печатает `имя --help`. У `ls` на macOS такого флага нет: команда заканчивается с ошибкой. Остаётся `man ls`.

Команда самого bash в свою страницу не вынесена.

```bash
man '[['
# кавычки, чтобы скобки не прочла текущая оболочка
# получается: No manual entry for [[
```

```bash
man cd
```

На macOS откроется страница `builtin`: список имён и отсылка к руководству оболочки. Разбора, что делает `cd`, там нет. Закройте её через `q`.

На другой системе `man cd` может называться иначе. Если в открытом тексте нет разбора `cd`, он в одной длинной странице на весь bash:

```bash
man bash
```

Эта страница описывает bash, который стоит на машине. На macOS это часто версия 3.2. Сайт внизу описывает текущий bash. Если абзацы разошлись, для команды на вашей машине верна локальная страница.

Искать место, не читая с начала. Клавиши уже открытой страницы, не новые команды shell:

- `/`, сразу текст, например `pipefail`, затем Enter – первое совпадение;
- `n` – следующее такое же место;
- `q` – закрыть страницу.

Короткая справка без этой страницы – `help`. Для `[[` её уже вызывали.

```bash
bash -c 'help cd'
# help – текст встроенной команды
# cd   – о какой
# из zsh и fish снова через bash -c: в них help может быть другим
```

Та же книга в браузере, уже разбитая на главы:

- [Руководство Bash](https://www.gnu.org/software/bash/manual/bash.html) – кавычки, `set` и параметры. Открывайте главу, которую сегодня уже прошли в терминале.
- [Условные выражения](https://www.gnu.org/software/bash/manual/bash.html#Conditional-Expressions) – что проверяет `[[ ]]`.
