# Семинар к Лекции 4. Bash-скрипты и отладка сервера

Этот конспект — практическое руководство по теме: живая работа в терминале.
Цель — своими руками написать рабочий скрипт, увидеть его трассировку через
`bash -x`, а затем продиагностировать «заболевший» сервер стандартными
командами (top / df / ss / journalctl). Все примеры стоит повторять у себя в
терминале по ходу чтения — так материал закрепляется гораздо лучше, чем при
простом просмотре.

## Что понадобится

- Bash ≥ 4 (`bash --version`), установлены `curl`, `tar`, `htop`, `shellcheck`.
- Учебный Linux с systemd (виртуалка с Ubuntu; WSL — с включённым systemd) и
  `nginx` — на него мы будем «нападать» в блоке диагностики. Как его поставить и
  запустить — в начале второй половины, раздел «Подготовка».
- Пустая рабочая папка `~/demo-bash`. Начинайте с чистого листа.
- Удобно открыть вторую вкладку терминала: в одной льём нагрузку, в другой смотрим.

---

## Разминка: зачем это всё

Вспомните, приходилось ли вам копировать одни и те же 5 команд из заметки,
чтобы задеплоить проект? Если да — вы уже чувствуете, зачем нужны скрипты.
Главная идея простая:

> Всё, что вы делаете руками больше двух раз, — кандидат в скрипт. Скрипт не
> устаёт, не забывает шаг и делает одинаково в 9 утра и в 3 ночи.

Вторая половина занятия — про сервер:

> Скрипты запускаются на серверах. Когда сервер «лёг», надо быстро понять,
> что случилось. Во второй части научимся ставить серверу диагноз.

## Первый скрипт: анатомия

Создадим файл и разберём каждую строку:

```bash
mkdir ~/demo-bash && cd ~/demo-bash
nano hello.sh    # или ваш редактор
```

Наберём следующий скрипт:

```bash
#!/usr/bin/env bash
name="Мир"
echo "Привет, $name!"
echo 'а тут литерал: $name'
exit 0
```

Разберём по строкам:
- `#!/usr/bin/env bash` — «шебанг»: какой интерпретатор запускает файл. Без него
  система не знает, чем выполнять скрипт.
- `name="Мир"` — переменная. Обратите внимание: никаких пробелов вокруг `=`.
  `name = "Мир"` — ошибка, bash решит, что `name` это команда.
- Двойные кавычки `"$name"` подставляют значение, одинарные `'$name'` — нет.
- `exit 0` — код выхода. 0 — успех, любое другое число — ошибка.

Делаем исполняемым и запускаем:

```bash
chmod +x hello.sh
./hello.sh
echo "код выхода: $?"     # 0
```

В первой строке вывода подставилось «Мир», во второй — нет: одинарные кавычки
не раскрывают переменные. `$?` показал 0 — скрипт отработал успешно.

Частая ошибка: `bash: ./hello.sh: Permission denied` — забыли `chmod +x`. Либо
запускайте через `bash hello.sh` (тогда chmod не нужен).

## Аргументы, условия, цикл

Усложним задачу: пусть скрипт делает бэкап папки, переданной аргументом. Создаём
`backup.sh` и наполняем постепенно.

```bash
#!/usr/bin/env bash
src="$1"
dst="/tmp/backup"

if [ -z "$src" ]; then
  echo "usage: ./backup.sh <папка>"
  exit 1
fi

mkdir -p "$dst"
for f in "$src"/*.txt; do
  echo "копирую $f"
  cp "$f" "$dst"
done
echo "готово, файлов: $#"
```

Разберём по частям:
- `$1` — первый аргумент. `$#` — сколько их. `$@` — все скопом.
- `if [ -z "$src" ]` — если аргумент пустой, печатаем подсказку и `exit 1`
  (ненулевой код = «я не выполнил задачу»).
- `for f in "$src"/*.txt` — цикл по файлам. Обратите внимание на кавычки вокруг
  `"$src"` — иначе путь с пробелом развалится.

Готовим данные и запускаем:

```bash
mkdir data && echo "a" > data/a.txt && echo "b" > data/b.txt
./backup.sh data
./backup.sh            # без аргумента — увидим usage и код 1
echo $?
```

Обратите внимание, как скрипт по-разному завершается: с данными — код 0, без
аргумента — код 1. Это и есть контракт скрипта с внешним миром.

Частая ошибка: `[ -z $src ]` без кавычек падает, если переменная пустая.
Всегда кавычьте переменные в условиях.

## Надёжность: set -euo pipefail и trap

Посмотрим на коварство bash по умолчанию:

```bash
cat > bad.sh <<'EOF'
#!/usr/bin/env bash
cd /nesuschestvuet      # ошибка!
rm -rf ./*              # выполнится в ТЕКУЩЕЙ папке!
EOF
```

Не запускайте этот скрипт! Смысл в том, что `cd` упал, но скрипт пошёл дальше и
`rm -rf` отработал не там, где вы думали — в текущей папке. Вот почему нужен
строгий режим.

Добавляем защиту первой строкой:

```bash
#!/usr/bin/env bash
set -euo pipefail
```
- `-e` — выйти при первой же ошибке (ненулевом коде команды).
- `-u` — падать, если используется необъявленная переменная (ловит опечатки).
- `-o pipefail` — если упала команда в середине пайпа `a | b | c`, весь пайп
  считается упавшим.

Теперь `trap` — гарантированная уборка:

```bash
cat > safe.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
tmp=$(mktemp)
trap 'echo "убираю $tmp"; rm -f "$tmp"' EXIT
echo "работаю с $tmp"
false            # имитируем ошибку
echo "эта строка не выполнится"
EOF
bash safe.sh; echo "код: $?"
```

Несмотря на падение на `false`, `trap ... EXIT` сработал и удалил временный файл.
Строка после `false` не выполнилась — спасибо `set -e`.

## Отладка скрипта: bash -x — ключевой навык

Намеренно посадим баг в `backup.sh` — например, опечатку в переменной:

```bash
# внутри цикла заменили "$src" на "$scr" (опечатка)
./backup.sh data      # молчит или копирует не то
```

Глазами баг не всегда видно. Включаем трассировку — bash покажет каждую команду
ПОСЛЕ подстановки переменных:

```bash
bash -x backup.sh data
```

Разберём вывод построчно. Строки с `+` — это то, что реально выполняется.
Увидим `+ cp /*.txt ...` — путь пустой, потому что `$scr` не существует
(а с `set -u` вообще упало бы сразу). Вот он, баг.

Можно включить точечную трассировку только куска:

```bash
set -x           # включить трассировку прямо в сессии
./hello.sh
set +x           # выключить
```

В большом скрипте оборачивайте подозрительный участок в `set -x ... set +x`,
чтобы не тонуть в выводе. И самый простой инструмент — `echo "DEBUG: src=$src"`
в нужном месте, никто не отменял.

Бонус — линтер:

```bash
shellcheck backup.sh
```
Shellcheck сам подсказывает про некавыченные переменные и типичные грабли.
Прогоняйте его до запуска в бою.

## cron: запуск по расписанию

Разберём формат строки по полям:

```
0 3 * * 1   /home/user/backup.sh
│ │ │ │ │
│ │ │ │ └── день недели (0–6, 0=вс)
│ │ │ └──── месяц (1–12)
│ │ └────── день месяца (1–31)
│ └──────── час (0–23)
└────────── минута (0–59)
```

Так, `0 3 * * 1` = «в 0 минут 3-го часа, каждый понедельник». Звёздочка =
«любое значение».

Попробуем живьём — безопасный пример: писать дату в файл каждую минуту:

```bash
crontab -e
# добавляем строку:
* * * * * date >> /tmp/cron.log
```
Подождите минуту, затем:
```bash
cat /tmp/cron.log        # появились строки с датой
crontab -l               # посмотреть свои задачи
```
Не забудьте убрать учебную задачу из `crontab -e`, иначе лог будет расти.

Частая ошибка: в cron нет вашего `$PATH` и переменных окружения. Пишите полные
пути к скриптам и командам, иначе «у меня в терминале работает, а в cron — нет».

## Диагностика «сервер лёг» — вторая половина

Переходим на учебный сервер. Идея: пройти по дереву «симптом → команда → вывод».

### Подготовка: ставим и запускаем nginx

Чтобы было что диагностировать, нужен живой сервис. Возьмём **nginx** — веб-сервер,
который отдаёт страницы по HTTP на 80-м порту. Он лёгкий, ставится одной командой
и управляется через systemd — ровно то, что нам нужно.

```bash
sudo apt update                  # обновить список пакетов
sudo apt install -y nginx        # установить nginx
```
На Ubuntu/Debian после установки сервис **сам запускается** и добавляется в
автозагрузку. Проверяем, что он жив:
```bash
systemctl status nginx           # ищем active (running); q — выход
systemctl is-enabled nginx       # enabled — поднимется и после перезагрузки
curl -I localhost                # HTTP/1.1 200 OK, Server: nginx/...
curl localhost                   # сама страница: «Welcome to nginx!»
```
Если статус `inactive (dead)` — запускаем руками:
```bash
sudo systemctl start nginx       # запустить сейчас
sudo systemctl enable nginx      # включить автозапуск (оба сразу: enable --now)
```

**Где что лежит** — пригодится при разборе поломок:

| Путь | Что там |
|---|---|
| `/etc/nginx/nginx.conf` | главный конфиг |
| `/etc/nginx/sites-enabled/default` | настройки сайта по умолчанию |
| `/var/www/html/` | файлы, которые отдаёт сайт |
| `/var/log/nginx/access.log` | кто и что запрашивал |
| `/var/log/nginx/error.log` | ошибки самого nginx |

Убедимся, что сервер отдаёт именно наши файлы, — подменим главную страницу:
```bash
echo '<h1>Привет от моего сервера</h1>' | sudo tee /var/www/html/index.html
curl localhost                   # теперь видим наш заголовок
sudo tail -n 3 /var/log/nginx/access.log   # и наши запросы в журнале доступа
```
`sudo tee` нужен потому, что `sudo echo ... > файл` не сработает: перенаправление
`>` выполняет ваш shell без прав root, а не `echo`.

Правите конфиг — всегда сначала проверяйте его, потом перечитывайте:
```bash
sudo nginx -t                    # syntax is ok / test is successful
sudo systemctl reload nginx      # применить конфиг без остановки сервиса
```

**Открыть страницу из браузера на своём компьютере.** Узнайте IP виртуалки:
```bash
hostname -I                      # например 10.211.55.5
```
и откройте `http://<этот IP>/`. Если страница не грузится, а `curl localhost` внутри
ВМ работает — порт закрыт файрволом (`ufw` мы включали при настройке ВМ):
```bash
sudo ufw allow 80/tcp            # разрешить HTTP снаружи
sudo ufw status                  # 80/tcp ALLOW
```

> **Нет systemd?** Команды `systemctl` и `journalctl` работают только там, где
> система запущена через systemd: обычная ВМ с Ubuntu — да. В WSL его нужно
> включить (`/etc/wsl.conf`: секция `[boot]`, строка `systemd=true`, затем
> `wsl --shutdown`). В Docker-контейнере systemd нет — для этого блока он не подойдёт.

### Нагрузка: CPU и память

Создаём нагрузку во второй вкладке:

```bash
# вкладка 1 — грузим CPU
yes > /dev/null &
yes > /dev/null &
```
В первой вкладке смотрим:
```bash
uptime           # load average: три числа
top              # интерактивно; q — выход
```
Как читать top: `load average` — очередь к процессору; если больше числа ядер
(`nproc`) — перегрузка. Столбец `%CPU` — кто виноват. Процессы `yes` окажутся
вверху списка.

```bash
htop             # то же, но нагляднее (если установлен)
kill %1 %2       # снять фоновые задачи yes
```
Нашли обжору по PID — можно `kill <PID>`. Не убивайте вслепую.

### Диск

Классика «внезапно всё сломалось» — кончилось место:

```bash
df -h            # использование по разделам; смотрим Use%
```
Если где-то `Use% = 100%` — вот причина. Ищем, что заняло:
```bash
du -sh /var/log/*        # размеры внутри папки
du -sh /var/* | sort -h  # отсортировать по размеру
```
`df` отвечает «какой раздел забит», `du` — «чем именно». Частый виновник —
распухшие логи в `/var/log`.

### Порты и процессы

Симптом «сайт не открывается»:

```bash
ss -tulpn        # кто слушает какие порты
ss -tulpn | grep :80     # слушает ли кто-то 80-й порт
curl -I localhost        # отвечает ли сервер локально
```
Если в `ss` нет строки с `:80` — сервер просто не запущен или слушает не тот
порт. `ss` — современная замена устаревшему `netstat`.

### Сервисы и логи

Ломаем nginx по-настоящему и чиним по логам:

```bash
sudo systemctl stop nginx        # имитируем падение
curl -I localhost                # Connection refused
systemctl status nginx           # inactive (dead)
```
Статус показал, что сервис не работает. Смотрим, что он писал:
```bash
journalctl -u nginx -n 30        # последние 30 строк логов nginx
journalctl -p err -b             # все ошибки с момента загрузки
journalctl -f                    # следить в реальном времени (Ctrl-C выход)
```
Поднимаем обратно:
```bash
sudo systemctl start nginx
systemctl status nginx           # active (running)
curl -I localhost                # 200 OK
```
Запомните цикл диагностики: `status` (что с сервисом) → `journalctl` (почему) →
`restart`/`start` (чиним) → снова `status`/`curl` (проверяем).

## Частые ошибки

- **«Permission denied»** — забыли `chmod +x` (или запускайте `bash file.sh`).
- **«bad interpreter»** — Windows-переносы строк (CRLF). Лечится `dos2unix`.
- **`name = "x"` не работает** — пробелы вокруг `=` в присваивании недопустимы.
- **Некавыченные переменные** — путь с пробелом или пустое значение ломают
  скрипт; всегда `"$var"`.
- **«В терминале работает, в cron — нет»** — в cron другой $PATH; пишите полные пути.
- **Убили не тот процесс** — сначала `top`/`ss` найдите PID, потом `kill`.
- **`rm -rf` без проверки пути** — показательный пример, зачем `set -euo pipefail`.
