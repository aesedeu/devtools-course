## **Зачем нужен Git.**

Вы правите скрипт. Завтра ломается метрика. Хочется ответить на три вопроса:

1. *Что* было в проекте вчера в 18:00?
2. *Кто* поменял эту строку и зачем?
3. Как откатиться, не восстанавливая zip с рабочего стола?

Папки `lab_copy`, `lab_final`, `lab_final_точно` эту задачу не решают. Нет общей истории. Нет сообщения «зачем». Нет способа аккуратно слить работу двух людей.

> **Система контроля версий (VCS)** – инструмент, который хранит историю проекта: набор зафиксированных состояний и способ двигаться между ними.

Раньше часто жили централизованные системы: один сервер, без сети почти ничего нельзя. Git устроен иначе: **полная история лежит у вас на диске**. Большинство операций локальные. Самолёт, поезд, VPN отвалился – коммитить можно. Когда сеть появится, синхронизируетесь.

Практическая польза на курсе и в работе одна и та же: код живёт в репозитории, правки приходят pull request'ом, сервер собирает конкретный коммит, а не «последнюю папку с флешки».

Нейронка напишет команду, которой мы ещё не учили. Сегодня наша работа – понимать обычный `commit`: объект, индекс, хеш. Иначе «откат» снесёт работу.

## **Снимки, не различия.**

Большинство старых VCS думают так: вот файл, вот список правок к нему. Хранят **дельты**.

> **Дельта** – описание различия: что вычесть и что прибавить, чтобы из версии A получить версию B.

Git на уровне модели думает иначе. Каждый коммит – **снимок всего проекта** в этот момент: как выглядел каждый файл.

Один файл, два коммита:

```text
коммит 1:  app.py = print("a")     README = "курс"
коммит 2:  app.py = print("a")     README = "курс, пара 2"
           тот же объект            новый объект
```

`app.py` не копируют второй раз: в новом снимке лежит **ссылка** на старый объект. Поменялся только README.

Если файл не менялся, Git не копирует его байты заново. Получается поток снимков, а не стопка патчей к каждому файлу.

```text
другие VCS:   файл v1, потом патч, потом патч

Git:          снимок, потом снимок, потом снимок
              (файл тот же – одна ссылка, не вторая копия байтов)
```

Откат – «встать на другой снимок».

Ловушка на потом: *внутри* упакованного репозитория Git умеет сжимать похожие объекты дельтами (pack-файлы). Это экономия места, не модель в голове. Для нас коммит – снимок.

## **Репозиторий.**

> **Репозиторий** – проект под Git: рабочие файлы плюс скрытый каталог `.git` с базой объектов и ссылками.

> **Рабочая копия (working tree)** – то, что вы видите и правите: `.py`, `README`, папки. Обычное дерево файлов, как на прошлой паре.

> **Каталог Git** – `.git`. Метаданные и объекты. При `clone` копируется именно эта база, а рабочие файлы потом распаковываются из неё.

Пока нет `.git` – это просто папка. Git её не видит. Склад появится на `git init`. Клон чужого проекта – позже, когда будет remote.

Не кладите один репозиторий внутрь другого без нужды. Вложенный `.git` – отдельная история, и вы запутаетесь, *какой* Git на команду отвечает.

`.git` руками лучше не чистить. Это склад, не черновик.

## **Настройка:** `git config`.

Сначала Git должен знать, *чьё* имя писать в коммит. Это не аккаунт GitHub. Это поля автора внутри объекта commit.

```bash
which git
git --version
# --version – версия программы

git config --global user.name "Ivan Ivanov"
# config   – configuration (настройка)
# --global – глобально (для вашего пользователя, файл ~/.gitconfig)

git config --global user.email "ivan@example.com"

git config --global -l
# -l – list (покажи настройки)
```

`--global` (global) – все репозитории вашего пользователя. Без флага – только текущий репозиторий (файл `.git/config`). `--system` (system) – на всю машину, редко нужно.

```bash
git config --global init.defaultBranch main
# init.defaultBranch – как назвать первую ветку при git init

git config --global core.editor "nano"
# core.editor – каким редактором открывать сообщение коммита, если не передали -m
```

Имя и почта – не сахар: без них `commit` часто откажется.

## **Инициализация:** `git init`.

Работать лучше в своей папке, не в `/`.

```bash
cd ~
mkdir -p ~/Desktop/devtools-git && cd ~/Desktop/devtools-git
# mkdir  – make directory
# -p     – parents

git init
# init – initialize: заведи каталог .git здесь

ls -lah
# -l -a -h – long, all, human-readable (скрытый .git станет виден)
```

`git init` не загружает файлы на GitHub. Он говорит: «эта папка теперь репозиторий». Дальше команды ищут `.git` **вверх** от текущей папки. Поэтому `cd` внутрь проекта – нормальный старт.

## **Имя первой ветки.**

После `init` у вас уже есть ветка. Пока она одна. Это не особый тип, а привычное имя.

- `master` – историческое имя по умолчанию в Git. В старых репозиториях до сих пор оно.
- `main` – нынешняя договорённость GitHub и свежего `git init` (если задали `init.defaultBranch`). Смысл тот же: ветка, которую показывают по умолчанию.
- `trunk` – слово из SVN: «ствол». В Git это снова просто имя, если команда так назвала.

```bash
git branch
# branch – список веток; звёздочка – текущая
# получается: * main
# или:        * master
```

Ловушка: нейронка напишет `main`, а у вас `master`. Смотрите звёздочку, не заучивайте одно слово.

Вторую ветку (`feature`) заведём на следующей паре. Сегодня работаем на этой одной.

## **Первый цикл:** `status`, `add`, `commit`.

Создадим файл и спросим Git, что он видит.

```bash
echo 'print("hello")' > app.py

git status
# status – состояние рабочей копии и индекса
```

`app.py` будет **untracked**. Git вежлив: новый файл сам в историю не тащит. Иначе в коммит улетели бы логи и секреты.

```bash
git add app.py
# add – добавь в индекс (на полку следующего коммита)

git status
# получается: Changes to be committed
```

Теперь файл **staged**. Готов войти в снимок.

```bash
git commit -m "Первый снимок: появился app.py"
# commit – зафиксируй индекс как новый commit
# -m     – message (текст сообщения прямо в команде)
```

Сообщение – часть объекта commit. Пишите *зачем*, не «правки». Через полгода `fix` не спасёт.

Без `-m` Git откроет редактор (`core.editor` или vim). Выйти как на прошлой паре: в vim `Esc`, затем `:wq`.

```bash
git log
# log – журнал коммитов, новые сверху
# получается: commit a1b2c3d...
#             Author: Ivan ...
#             Первый снимок: появился app.py

git log --oneline
# --oneline – один коммит = одна строка (короткий хеш + сообщение)
# получается: a1b2c3d Первый снимок: появился app.py
```

Хеш в шапке – идентификатор снимка. Его можно дать коллеге вместо «ну там вчерашнее». Откуда он берётся – следующий раздел, уже на живом коммите.

## **Три зоны и статусы файла.**

Без этой картинки `add` кажется лишней командой. Вы только что её прожили: untracked, потом полка, потом чисто.

<img src="https://git-scm.com/book/en/v2/images/areas.png" width="500" alt="Working Directory, Staging Area, .git directory" style="display: block; margin: 0.75em 0;" />

```text
рабочая копия          индекс (staging)         каталог .git
то, что правите        снимок «что войдёт       зафиксированная
в редакторе            в следующий коммит»      история
```

> **Индекс (staging area)** – промежуточная полка: какие файлы *в какой версии* попадут в следующий коммит. Технически это файл `.git/index`.



Файл в конкретный момент может быть:

- **изменён (modified)** – в рабочей копии не как в последнем коммите, в индекс ещё не брали;
- **индексирован (staged)** – версия с полки, готовая к коммиту;
- **зафиксирован (committed)** – эта версия уже есть объектом в `.git`.

> **untracked** – файл есть на диске, Git его ещё ни разу не брал в индекс. История про него молчит.

Базовый конвейер:

1. Правите файлы в рабочей копии.
2. Кладёте на индекс то, что должно войти в *этот* коммит (`git add`).
3. `git commit` забирает *индекс*, собирает tree и новый commit, двигает указатель текущей ветки (`main`).

Ловушка: вы поправили файл *после* `add`. В индексе старая версия, в рабочей копии новая. Коммит возьмёт то, что на полке.

Ещё раз те же слова Git, уже после первого коммита:

```bash
echo 'print("b")' >> app.py

git status
# получается: Changes not staged for commit
```

Диск новее полки. Три зоны – не три папки на рабочем столе. Это три *версии одного файла*, которые Git сравнивает.

## **Хеш – имя содержимого.**

Прежде чем Git что-то сохранит, он считает от содержимого **хеш**. Дальше объект лежит в базе *под этим хешем*, не под именем файла.

> **Хеш** – короткая фиксированная «подпись» данных. Одинаковые байты дают один хеш. Другие байты дают другой хеш.

> **Content-addressable storage** – склад, где адрес объекта равен хешу содержимого. Одинаковое содержимое – один адрес, лежит один раз.

Git классически использует SHA-1: 40 шестнадцатеричных символов. Это и адрес, и контроль целостности.

Посчитать адрес, даже без файла:

```bash
echo 'hello' | git hash-object --stdin
# hash-object – посчитай хеш объекта Git
# --stdin     – стандартный ввод (не путь к файлу)
# получается: ce013625030ba8dba906f756967f9e9ca394464a

echo 'Hello' | git hash-object --stdin
# одна буква другая – другой адрес, не «почти тот же»
```

Одинаковая строка `hello` у всех на паре даст один хеш.

Имя файла `app.py` может быть одним и тем же вчера и сегодня. Содержимое другое – другой объект, другой хеш. Поэтому историю нельзя незаметно подменить: любой правкой ломается цепочка адресов.

Короткий префикс хеша часто хватает: `git show a1b2c3d`. Если префикс неоднозначный, Git попросит длиннее.

## **Четыре типа объектов.**

Теперь есть живой коммит. Можно открыть склад.

Почти всё в `.git/objects` – один из четырёх типов.

> **blob** – содержимое файла (байты). Имя файла здесь не хранится.

> **tree** – снимок каталога: список «имя + тип + хеш». Папка в Git – tree, не blob.

> **commit** – снимок проекта как событие: ссылка на tree корня, родитель, автор, время, сообщение.

> **tag** – именованная этикетка на коммит: «версия 1.0». На этой паре можно не трогать.

Связка:

```text
commit смотрит на tree (корень проекта)

tree содержит имена:
  README.md   (blob)
  app.py      (blob)
  src/        (ещё один tree)

commit знает родителя: предыдущий commit
```

Файл `app.py` в двух коммитах с одним содержимым – **один** blob. Имя живёт в tree, как на прошлой паре имя жило в каталоге, а данные – в inode.

Маршрут, когда вы спрашиваете: «что лежит в HEAD?»

**Шаг 1. Ссылка.** Git читает `HEAD`. Обычно там написано: «я на ветке `main`». Идёт в `refs/heads/main`, берёт хеш коммита.

**Шаг 2. Объект commit.** По хешу достаёт commit: сообщение, автор, хеш tree, хеш родителя.

**Шаг 3. Tree.** По хешу tree читает список имён в корне.

**Шаг 4. Blob.** По хешу blob достаёт байты файла – это уже содержимое `app.py`.

**Шаг 5. Рабочая копия.** Если вы стоите на этом коммите, эти байты лежат в файлах на диске.

Цепочка: имя ветки `main`, затем commit, затем tree, затем blob. Скачков «файл сам по себе в истории» нет.

```bash
git rev-parse HEAD
# rev-parse – разверни имя в полный хеш
# HEAD      – текущий коммит этой ветки

git cat-file -p HEAD
# cat-file – покажи объект из базы
# -p       – pretty (человекочитаемо)
```

Для первого коммита увидите что-то в таком духе (хеши у вас другие):

```text
tree 9c1e...
author Ivan ...
committer ...

Первый снимок: появился app.py
```

У второго коммита сверху появится ещё `parent ...` – ссылка в прошлое.

```bash
git ls-tree HEAD
# ls-tree – имена в корневом tree
# получается: 100644 blob ce0136...  app.py
```

Имя файла здесь, содержимое – в blob. `100644` – обычный файл, не исполняемый.

> **HEAD** – «где я сейчас». Обычно файл `.git/HEAD` говорит: «я на ветке `main`» (или `master`), а это имя указывает на хеш коммита.

## **Смотрим разницу:** `diff`.

Пока файл только в рабочей копии и не в индексе:

```bash
echo 'print("hello")' >> app.py

git diff
# diff – покажи различия
# получается: строка с плюсом – появилось на диске, на полке этого ещё нет
```

`git diff` без аргументов: **рабочая копия против индекса**. То, что ещё не на полке.

```bash
git add app.py

git diff --staged
# --staged – сравни индекс с последним коммитом (что войдёт в commit)
# получается: тот же плюс, но уже «поедет в commit»

git diff
# пусто: диск и полка совпали
```

Два разных вопроса – две команды. Путают постоянно.

```bash
git show
# show – покажи последний коммит: сообщение плюс патч
```

Портянка на весь проект неудобна. Дальше тот же `diff`, но уже *куда смотреть*.

**Один файл.** Двоеточия нет: путь в конце. `--` значит «дальше не ревизия, а путь».

```bash
git diff -- app.py
# -- – отдели флаги от пути
```

Так же: `git diff --staged -- app.py` – что с этого файла уже на полке. `git show HEAD -- app.py` – как этот файл выглядел в последнем коммите (патч только по нему).

**Одна функция в Python.** Git умеет найти `def имя`. Флаг `-L` (line – диапазон строк или функция).

Пусть в `app.py` две функции, а правили только первую:

```python
def greet():
    print("hello")
    print("again")

def leftover():
    print("x")
```

```bash
git diff -L :greet:app.py
# -L      – line: покажи только этот кусок
# :greet: – имя функции; для Python Git ищет строку def greet
```

Ловушка: пишете `:greet:`, не `def greet`. Второй файл и функция `leftover` в этот вывод не попадут, даже если их тоже трогали – для них другой вызов `-L`.

**Номера строк.** Тот же `-L`, но цифрами: с какой по какую в этом файле.

```bash
git diff -L 1,4:app.py
# 1,4 – строки 1–4 файла app.py
```

Сначала файл, потом функция или строки. Без пути Git покажет весь проект – вы уже это видели сверху.

## **Зачем нужен индекс.**

Зачем полка, если можно сразу «сохранить всё»?

Потому что в рабочей копии часто смешаны две задачи: починили баг и заодно переименовали переменную. Индекс позволяет собрать коммит **из части** изменений.

```bash
git add -p
# -p – patch (покажи куски файла, спроси, брать ли в индекс)
```

Ответы в диалоге: `y` (yes) взять кусок, `n` (no) пропустить, `s` (split) разрезать ещё мельче, `q` (quit) выйти.

Весь каталог:

```bash
git add .
# . – текущая папка и всё внутри (что не в .gitignore)
```

`git add -A` (`-A` – all) ещё и подхватит удаления. На старте достаточно `git add файл` и понимать полку.

## **Unstage: снять с полки.**

Положили на индекс лишнее – коммит ещё не делали. Нужно убрать файл *с полки*, текст на диске оставить.

```bash
echo 'print("лишнее")' >> app.py
git add app.py

git status
# получается: Changes to be committed

git restore --staged app.py
# restore  – восстанови
# --staged – только индекс: полка как в HEAD, файл в рабочей копии не трогай

git status
# получается: Changes not staged for commit

cat app.py
# строка «лишнее» на месте
```

Старый синоним (тот же вопрос «сбрось индекс у этого пути»):

```bash
git reset HEAD app.py
# reset – сдвинь; здесь с путём файла, без --hard:
#         это unstage, ветка main не прыгает
```

Другой вопрос – «перестань следить за файлом, который уже был в коммите»:

```bash
echo 'черновик' > notes.txt
git add notes.txt
git commit -m "случайно notes"

git rm --cached notes.txt
# rm       – remove (убери имя)
# --cached – только из индекса, файл на диске оставь

git status
# получается: notes.txt уехал из индекса, на диске файл жив

cat notes.txt
```

Чтобы Git его больше не предлагал – строка в `.gitignore` (скоро). Это не unstage правки, а «выписать файл из проекта».

## **Отмены.**

Три разных желания. Их нельзя закрыть одним «undo».

**1. Файл в рабочей копии испортили, в индексе и в коммите ещё старое.**

```bash
echo 'ой' >> app.py

git restore app.py
# restore – верни файл в рабочей копии к индексу / HEAD

cat app.py
# строки «ой» нет
```

**2. Unstage.** На полку положили лишнее – вы уже умеете: `git restore --staged app.py`. Текст остаётся.

**3. Последний коммит ещё не отправляли, забыли файл.**

```bash
echo 'забыли' > forgotten.py
git add forgotten.py

git commit --amend --no-edit
# --amend   – перепиши последний коммит (новый объект, новый хеш)
# --no-edit – сообщение оставь как было
```

`--amend` (amend – поправь) создаёт **другой** commit. Старый хеш пропадает из текущей ветки. Если коммит уже улетел на сервер и его забрали люди – переписывать историю нельзя без договорённости. Локальный «только что» – можно.

## **Reset: двигаем ветку.**

`git reset` двигает **текущую ветку** (`main`) на другой коммит. Три режима – три ответа: что сделать с индексом и рабочей копией.

Представьте три полки: диск, индекс, вершина ветки.

Сначала договоримся, как **называть** нужный коммит. Запись одна и та же в `reset`, `show`, `diff`, `log`:

```bash
git log --oneline -1 HEAD
# HEAD – текущий коммит

git log --oneline -1 HEAD~1
# HEAD~1 – родитель, на один снимок назад

git log --oneline -1 HEAD~2
# HEAD~2 – на два снимка назад
```

Вместо `HEAD~1` всегда можно подставить короткий хеш из `git log --oneline`.

Один учебный коммит, три исхода. Сначала сделайте коммит, который потом «распустите»:

```bash
echo 'R1' >> app.py
git add app.py
git commit -m "R1"
```

`--soft` – распустили коммит, полка полная:

```bash
git reset --soft HEAD~1
# --soft – только указатель ветки назад

git status
# получается: Changes to be committed: app.py
```

Верните коммит, чтобы сравнить следующий режим:

```bash
git commit -m "R1 снова"
```

`--mixed` (это `git reset` без флага) – правки на диске, не на полке:

```bash
echo 'R2' >> app.py
git add app.py
git commit -m "R2"

git reset HEAD~1

git status
# получается: Changes not staged for commit
```

`--hard` – пила, незакоммиченное пропадёт:

```bash
echo 'R3' >> app.py
git add app.py
git commit -m "R3"

git reset --hard HEAD~1
# --hard – ветка, индекс и файлы как у целевого коммита

git status
# чисто

cat app.py
# строки R3 нет
```


| Режим                    | Ветка | Индекс                  | Рабочая копия   | Когда                            |
| ------------------------ | ----- | ----------------------- | --------------- | -------------------------------- |
| `--soft`                 | назад | как был (правки staged) | как была        | «пересобрать коммит»             |
| `--mixed` (по умолчанию) | назад | как у целевого коммита  | правки на диске | «вынести коммит обратно в файлы» |
| `--hard`                 | назад | как у целевого          | как у целевого  | «забыть всё после той вершины»   |


`--hard` (hard) – пила. Незакоммиченные правки после неё не вернуть: делайте её только тогда, когда точно не жалко.

Unstage файла – это `reset` *пути*, не всей ветки: `git reset HEAD файл` не двигает `main`, только снимает путь с полки. Путать с `git reset HEAD~1` нельзя: второе двигает историю.

## **Файл** `.gitignore`.

До remote и `push` договоримся, что в историю не кладём. Файл `.gitignore` в корне: список масок. Git не предлагает такие пути как untracked и не берёт их через `git add .`.

Уже попавшее в индекс правило само не выкинет – сначала `git rm --cached`.

Один живой прогон, потом маски:

```bash
echo 'TOKEN=not-a-secret' > .env

git status
# получается: Untracked: .env

echo '.env' > .gitignore

git status
# .env пропал из списка; .gitignore – новый untracked

git add .gitignore
git commit -m "игнорируем .env"

git check-ignore -v .env
# check-ignore – каким правилом путь отфильтрован
# -v           – verbose
# получается: .gitignore:1:.env
```

Это **не** полноценный regexp как в Python. Это glob – маски в духе shell.

Как устроена одна строка:

- пустая строка и `# комментарий` – ничего не игнорируют;
- обычное имя – точное совпадение в любой папке: `.env`;
- `/` в конце – только каталог: `build/`;
- `/` в начале – от корня репозитория: `/dist` не тронет `src/dist`;
- `!` в начале – исключение: «игнорируй вот это, но вот этот файл верни».

Коротко про маски:

| Шаблон          | Смысл                                  |
| --------------- | -------------------------------------- |
| `*`             | любое число символов, кроме `/`        |
| `?`             | один символ, не `/`                    |
| `[abc]`         | один символ из скобок; `[0-9]` – цифра |
| `**`            | любое число каталогов                  |
| `*.pyc`         | все `.pyc`                             |
| `logs/**/*.txt` | `.txt` на любой глубине под `logs/`    |


Пример файла:

```gitignore
# секреты и окружение
.env
.env.*

# Python
__pycache__/
*.pyc
.venv/

# всё в data/, кроме схемы
data/*
!data/schema.sql

# от корня репозитория
/dist
```

`*.pyc` – «любое имя + `.pyc`». Это `*`, не regexp-звёздочка «повтори предыдущее». Кванторы `{2,5}`, `\d`, группы `(ab)+` сюда не носите.

Правило с прошлого занятия: токены, ключи, `.env` – не часть исходника. Если секрет уже попал в коммит, удалить файл из следующего снимка мало: он останется в истории. На этой паре проще – не класть.

## **Удалённый репозиторий.**

Локальный `.git` – полный склад. Чтобы работал кто-то ещё (и чтобы был запасной диск), нужен второй экземпляр.

### **GitHub, GitLab, Bitbucket.**

**Git** – программа в терминале: коммиты, объекты, `.git` на диске.

**GitHub, GitLab, Bitbucket** – сайты, где лежит *копия* репозитория: права, веб-интерфейс, иногда CI и тикеты. У всех трёх для нас одна роль: `origin` с URL, `clone`, `push`, `pull`. На курсе примеры чаще на GitHub, на работе может быть GitLab или внутренний сервер – команды те же.

**Когда про них говорим:**


| Когда                   | Что                                                                                                      |
| ----------------------- | -------------------------------------------------------------------------------------------------------- |
| **Сегодня, конец пары** | Завести или привязать remote, `clone` / `remote add`, `push` и `pull`, public / private, SSH-ключ        |
| **Позже**               | Pull request, code review, Issues, Actions / CI, ветки в команде (следующие пары)                        |


![They don't know I have 38 GitHub followers](https://i.programmerhumor.io/2024/02/programmerhumor-io-linux-memes-backend-memes-319cbc0cac523b5.png)

Соцсеть разработчика – отдельная вселенная. Для сдачи домашки достаточно: репозиторий на хостинге, вы пушите коммиты, преподаватель клонирует или смотрит историю. Звёзды и подписчики к `git commit` не относятся.

> **remote** – сохранённый адрес другого репозитория. Обычно имя `origin` – откуда клонировали.

Два склада. Локальный – ваш ноутбук. `origin` – тот же склад на GitHub (или GitLab / Bitbucket). Коммиты сначала появляются у вас, потом `push` копирует объекты и двигает наклейку на сервере.

```text
ноутбук:  main на коммите C3
origin:   main на коммите C2     ещё не знает про C3

git push -u origin main
# push – отправь новые коммиты
# -u    – upstream (запомни связь этой ветки с origin/main)

ноутбук:  main на C3
origin:   main на C3
```

```bash
git remote -v
# remote – список удалённых
# -v     – verbose (покажи URL)
```

Пока remote не добавляли – список пустой. Это нормально.

`git pull` (pull – тяни) = забери чужие коммиты и обнови текущую ветку. Часто это `fetch`, затем влить в `main`. Как именно сливают *две* ветки – следующая пара.

```bash
git fetch
# fetch – скачай объекты и обнови origin/main, файлы на диске не трогай

git log --oneline --decorate
# --decorate – покажи имена рядом с хешем

git pull
```

`origin/main` – «где был `main` на origin в момент последнего fetch». Это указатель, не магия сети.

Первый раз на GitHub заводят пустой репозиторий на сайте, затем либо `clone`, либо локальный `init` и `git remote add origin URL` (`add` здесь – добавить remote, не файл в индекс).

```bash
git clone https://github.com/org/repo.git
# clone – скачай .git и распакуй рабочую копию

git remote add origin git@github.com:YOU/devtools-git.git
git push -u origin main
```

Имя на сайте смотрите: `main` или `master`. Не угадывайте.

## **Публичный и приватный.**

Хостинг (GitHub, GitLab, внутренний Git) хранит тот же `.git`, плюс права: кто может смотреть и кто может писать.

> **Публичный (public)** – историю может клонировать кто угодно. Код как на витрине.

> **Приватный (private)** – клон и просмотр только у тех, кого пустили (вы, команда, коллабораторы).

`push` – всегда с проверкой личности. Даже в публичный чужой репозиторий вы так просто не запишете: смотреть можно, полки двигать – нет.

```text
чужой public:   clone да     push нет (вас не звали писать)
свой private:    clone да     push да  (ключ / токен)
чужой private:   clone нет    push нет
```

Домашка и учебный форк часто public. Боевой сервис, ключи, данные студентов – private. Секрет, попавший в public, считайте утекшим: `.gitignore` после `push` его не вычистит.

Клонировать public:

```bash
git clone https://github.com/org/repo.git
```

Приватный без доступа даст `Repository not found` или отказ в правах – вас не пустили, не «Git сломался».

## **SSH: вход по ключу.**

HTTPS в адресе `https://github.com/...` при `push` часто просит логин и токен. Второй путь – SSH.

> **SSH (secure shell)** – защищённый вход на другую машину по ключу. Для GitHub «другая машина» – их сервер: вы не открываете чужой shell как на паре с Linux, а Git ходит тем же протоколом.

Две половинки ключа:

- **приватный** (`id_ed25519`) – остаётся у вас в `~/.ssh`, никому не слать, в git не класть;
- **публичный** (`id_ed25519.pub`) – текст, который вставляете в настройки GitHub. Им вас узнают.

Как подключиться, примитивно.

**Шаг 1.** Создать ключ, если ещё нет `~/.ssh/id_ed25519.pub`:

```bash
ls ~/.ssh

ssh-keygen -t ed25519 -C "ivan@example.com"
# ssh-keygen – сгенерируй пару ключей
# -t         – type (тип: ed25519)
# -C         – comment (подпись, обычно почта)
```

Enter на файле по умолчанию. Пароль на ключ – по желанию.

**Шаг 2.** Показать публичную половину и скопировать целиком одну строку:

```bash
cat ~/.ssh/id_ed25519.pub
# concatenate – выведи; отправляете .pub, не файл без .pub
# получается: ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAA... ivan@example.com
```

**Шаг 3.** GitHub: Settings, затем SSH and GPG keys, затем New SSH key – вставить. GitLab – тот же смысл в настройках профиля.

**Шаг 4.** Проверить, что сервер вас узнаёт:

```bash
ssh -T git@github.com
# -T – без интерактивного shell, только проверка входа
# получается что-то вроде: Hi, username! You've successfully authenticated
```

Первый раз спросит: trust host? `yes`. Это отпечаток сервера, не пароль репозитория.

**Шаг 5.** Клонировать и пушить по SSH-адресу (не `https://`):

```bash
git clone git@github.com:org/repo.git

git remote -v
# origin = git@github.com:...
```

Уже есть клон с HTTPS – сменить URL:

```bash
git remote set-url origin git@github.com:org/repo.git
# set-url – смени адрес remote
```

Туннели и свой сервер по `ssh user@ip` – позже. Сегодня достаточно: ключ, `.pub` на сайт, адрес `git@...`.

## **Полезные приёмы.**

**Кто трогал строку:**

```bash
git blame app.py
# blame – для каждой строки: хеш, автор, когда
```

Это не суд. Это «с какого коммита читать `git show`».

**Только имена файлов, которые менялись:**

```bash
git diff --name-only
# --name-only – только пути, без патча
```

Перед `commit` всегда `git status` и `git diff --staged`. Коммит – снимок полки, не «всех файлов, которые открыты в IDE».

В чат кидаете короткий хеш, не «последний»:

```bash
git rev-parse --short HEAD
# rev-parse – разверни имя в хеш
# --short   – короткий префикс (обычно 7 символов)
# получается: a1b2c3d
```

**Посмотреть один коммит целиком:**

```bash
git show HEAD
# show – сообщение, автор и патч этого коммита

git show --stat HEAD
# --stat – только файлы и счётчик строк, без полного патча
```

## **Команды и частые ошибки.**


| Команда                                   | Зачем                                 |
| ----------------------------------------- | ------------------------------------- |
| `git status`                              | где файл: диск / индекс / коммит      |
| `git add`                                 | на полку                              |
| `git commit -m`                           | снимок с полки, `-m` – message        |
| `git log --oneline`                       | лента хешей                           |
| `git diff` / `git diff --staged`          | диск против полки / полка против HEAD |
| `git diff -- файл` / `git diff -L`        | один файл; `-L` – функция или строки  |
| `git restore --staged`                    | unstage: снять с полки                |
| `git reset --soft` / `--mixed` / `--hard` | подвинуть ветку; три глубины          |
| `git restore`                             | вернуть файл                          |
| `git push` / `git pull`                   | отдать / забрать с remote             |
| `ssh-keygen -t ed25519`                   | пара ключей; `-t` type                |
| `ssh -T git@github.com`                   | проверка входа, `-T` без shell        |


Сообщения первого дня:

- `not a git repository` – нет `.git` выше по дереву, `cd` в проект или `init`;
- `Please tell me who you are` – нет `user.name` / `user.email`;
- `nothing to commit` – индекс совпадает с HEAD; правки либо не сделаны, либо не в `add`;
- `failed to push` / `rejected` – на origin есть коммиты, которых у вас нет: сначала `pull`, потом снова `push`;
- `Repository not found` на private – нет доступа, не «репозиторий удалили»;
- `Permission denied (publickey)` – GitHub не видит ваш SSH-ключ: нет пары или не добавили `.pub`.
