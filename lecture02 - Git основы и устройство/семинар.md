# Семинар к Лекции 2. Git: основы и устройство

Это конспект для самостоятельного разбора в терминале. Цель — своими глазами
увидеть три состояния, объектную модель и граф истории. Все команды ниже стоит
не просто прочитать, а набрать у себя и сравнить вывод с тем, что описано.

## Что понадобится

- Терминал.
- Установленный Git: проверьте командой `git --version` (нужна версия ≥ 2.30).
- Пустая рабочая папка, например `~/demo`. Начинайте с чистого листа.
- Аккаунт GitHub с настроенным SSH/HTTPS-доступом (понадобится в самом конце).
- Удобно завести алиас `alias gl='git log --oneline --graph --all --decorate'`,
  но сначала разберитесь с полной командой, а алиас подключите потом.

---

## Разминка: зачем это всё

Подумайте, как вы сейчас храните версии кода. Обычно это папки с именами вроде
`_final`, `_v2`, копии проекта «на всякий случай». Всё это заменяет Git.

Сразу разведём частую путаницу:
> **Git ≠ GitHub.** Git — программа у вас на компьютере. GitHub — сайт, где
> удобно хранить git-репозитории. Первые почти две трети этого разбора GitHub
> нам вообще не нужен.

---

## Создаём репозиторий и первый коммит

Наберите по шагам, вдумываясь в каждый:

```bash
mkdir ~/demo && cd ~/demo
git init
```
После `git init` появляется скрытая папка `.git` — это и есть весь репозиторий.
Удалите её — и вся история пропадёт. Больше git ничего вашего не трогает.

```bash
ls -la          # видно .git
```

Настройте автора — эта подпись уходит в каждый коммит:
```bash
git config user.name "Демо Пользователь"
git config user.email "you@example.com"
```
Без `--global` настройка действует только для этой репы; с `--global` — для всех
ваших репозиториев. Если автора не настроить, коммит либо не создастся, либо
уйдёт под чужим именем.

Создаём файл и смотрим статус:
```bash
echo "print('hello')" > app.py
git status
```
Файл `app.py` показан как «Untracked». Git его видит, но пока не следит за ним.

```bash
git add app.py
git status
```
Теперь файл в **индексе** (staging) — в разделе «Changes to be committed». Индекс —
это черновик следующего коммита. Три состояния — рабочая директория → индекс →
репозиторий — ключевая идея всей темы, держите её в голове.

```bash
git commit -m "add hello script"
git status          # nothing to commit, working tree clean
git log             # хеш, автор, дата, сообщение
```
Длинный хеш (SHA) слева в `git log` — это имя коммита. Запомните его первые
4 символа, они ещё пригодятся.

## Заглядываем ВНУТРЬ git — самое важное

Здесь снимается «магия»: видно, что коммит — это просто набор объектов.

```bash
git cat-file -p HEAD
```
Разберите вывод построчно: `tree ...` (снимок дерева файлов), `author`,
`committer`, а внизу — сообщение коммита. У самого первого коммита нет строки
`parent`, потому что до него ничего не было.

Посмотрите на дерево и blob:
```bash
git cat-file -p HEAD^{tree}     # список файлов → их хеши
git cat-file -p <хеш-blob>      # подставьте хеш app.py — увидите его содержимое
```
Blob — это чистое содержимое файла, даже без имени. Имя хранится отдельно, в
tree. Так устроено content-addressable хранилище: объект адресуется по своему
содержимому.

Убедитесь, что адрес = хеш содержимого:
```bash
echo 'hello' | git hash-object --stdin
echo 'hello' | git hash-object --stdin     # тот же хеш!
echo 'hello!' | git hash-object --stdin    # другой символ → другой хеш
```
Вывод: одинаковое содержимое всегда даёт один и тот же хеш и хранится один раз.
Изменили хоть байт — изменился адрес. Именно поэтому историю нельзя подделать
незаметно: любая правка меняет хеши.

## История как граф

Сделаем второй и третий коммит, чтобы появилась цепочка.

```bash
echo "print('bye')" >> app.py
git add app.py && git commit -m "add bye line"
echo "# notes" > README.md
git add README.md && git commit -m "add readme"

git log --oneline --graph --decorate
```
В выводе — три коммита в столбик, а у верхнего стоит `HEAD -> main`.

Теперь убедитесь, что ветка — это всего лишь указатель:
```bash
cat .git/HEAD                  # ref: refs/heads/main
cat .git/refs/heads/main       # хеш последнего коммита — 41 байт!
```
Вся «ветка main» — это файл с одним хешом. Вот почему ветвление в git почти
бесплатное (подробнее — на следующей лекции).

Сравните состояния командой diff:
```bash
echo "print('extra')" >> app.py   # меняем, но не добавляем
git diff                           # рабочая директория vs индекс
git add app.py
git diff --staged                  # индекс vs последний коммит
```
`git diff` без флагов показывает разницу между рабочей директорией и индексом,
а `git diff --staged` — между индексом и последним коммитом. Это те же три
состояния, только теперь видно, что лежит между ними.

## .gitignore

Сначала посмотрите на проблему, потом на решение:
```bash
mkdir __pycache__ && touch __pycache__/app.cpython.pyc
echo "SECRET_KEY=123" > .env
git status          # git предлагает добавить и мусор, и секрет!
```
Кэши и секреты в git — плохо: первое засоряет историю, второе опасно. Создаём
`.gitignore`:
```bash
printf "__pycache__/\n*.pyc\n.env\n" > .gitignore
git status          # мусор пропал, git видит только сам .gitignore
```
Файл `.env` с секретами не должен попадать в репозиторий никогда — ни в этот
коммит, ни в какой-либо другой.

## Удалённый репозиторий

Только теперь подключаем GitHub. Создайте на сайте пустой приватный репозиторий,
затем:
```bash
git remote add origin <URL>
git push -u origin main
```
Обновите страницу репозитория в браузере — те же коммиты появились на GitHub.
Коротко про четыре команды: `clone` — скопировать репозиторий целиком, `push` —
отправить свои коммиты на удалённый, `pull` — забрать чужие и слить со своими,
`fetch` — забрать чужие, но пока не сливать. Детали совместной работы — на
семинаре 3.

Проверьте клонирование в другую папку:
```bash
cd ~ && git clone <URL> demo-clone && cd demo-clone && git log --oneline
```
`clone` скачал ВЕСЬ репозиторий вместе с историей, а не только текущие файлы —
поэтому в клоне сразу доступен полный `git log`.

## Частые ошибки

- **«commit не создаётся»** — не настроены `user.name` / `user.email`.
- **«я добавил файл, но коммит пустой»** — забыли `git add` после правки,
  изменения так и не попали в индекс.
- **«запушил .env с паролем»** — удалить секрет из истории сложно, поэтому проще
  сразу настроить `.gitignore` и на всякий случай сменить сам секрет.
- **«git и GitHub — одно и то же?»** — вернитесь к разнице из раздела «Разминка».
- **Путаница между add и commit** — держите перед глазами три состояния: рабочая
  директория → индекс → репозиторий.
