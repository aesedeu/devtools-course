# Семинар к Лекции 6. Контейнеризация и виртуализация

Этот конспект — практический разбор в терминале. Цель — увидеть своими глазами,
что **контейнер — это изолированный процесс**, а не «маленькая виртуальная
машина». Мы соберём контейнер руками из namespaces и cgroups, а затем сравним
скорость старта VM и контейнера.

## Что понадобится

- **Linux-хост** (Ubuntu 22.04+ или аналог). Namespaces, cgroups и `unshare`
  есть только в Linux. Если вы на macOS/Windows, выполняйте всё внутри Linux-VM.
  Это, кстати, живая иллюстрация темы: «сейчас мы сидим внутри виртуальной
  машины».
- Права `sudo` (создание namespaces и cgroups требует root).
- **cgroup v2** (в современных дистрибутивах — по умолчанию). Проверить:
  ```bash
  stat -fc %T /sys/fs/cgroup     # ожидаем: cgroup2fs
  ```
- Пакет `util-linux` (в нём `unshare`) — обычно уже стоит: `unshare --version`.
- Установленный `python3` (нужен для «прожорливого» процесса).
- Для последнего блока: установленный `docker` и, по желанию, `multipass` или
  любой гипервизор (VirtualBox), чтобы запустить настоящую VM.
- Удобно держать два открытых терминала рядом: **T1** (внутри namespace /
  cgroup) и **T2** (хост) — так наглядно видно «внутри vs снаружи».

---

## Разминка: «а у меня всё работает»

Знакомая ситуация: код падал на сервере, хотя локально работал. Причины обычно
одни и те же — другая версия Python, нет CUDA, не та библиотека.

Вокруг этой боли крутится вся тема. Два ключевых слова:
> **Изоляция** — у каждого приложения своё окружение, не мешающее соседям.
> **Воспроизводимость** — «собрал раз, работает везде».

Добиться этого можно двумя способами — виртуализацией и контейнеризацией.
Разберём оба на уровне ОС, до всякого Docker.

## VM против контейнера на пальцах

Сравним два стека рядом:

```
   Виртуальная машина            Контейнер
   ┌───────────────┐             ┌──────────┐
   │  Приложение   │             │Приложение│
   │  Гостевая ОС  │  ← лишнее   └──────────┘
   ├───────────────┤             ┌──────────┐
   │  Гипервизор   │             │  Ядро ОС │  ← общее!
   ├───────────────┤             ├──────────┤
   │    Железо     │             │  Железо  │
   └───────────────┘             └──────────┘
```

**Ключевая мысль.** У VM в каждой машине — **своя ОС со своим ядром**, поэтому
она весит гигабайты и грузится десятки секунд. Контейнер **делит ядро хоста**,
поэтому это просто процесс: мегабайты и миллисекунды.

**Главное заблуждение, которое нужно снять сразу:**
> **Контейнер — это НЕ мини-VM.** Внутри контейнера нет второго ядра, нет
> загрузчика, нет «своей ОС». Это ваш обычный процесс, которому ядро хоста
> показывает урезанную картину мира. Дальше мы это докажем руками.

## Изоляция вживую: namespaces через unshare

Здесь снимаем «магию» контейнера. Убеждаемся, что изоляция — это функция ядра.

### PID namespace — «своё дерево процессов»

В **T1** выполните:
```bash
sudo unshare --pid --fork --mount-proc bash
```
Мы попросили ядро дать новому `bash` свой PID-namespace (`--pid`), форкнуть
дочерний процесс (`--fork`) и перемонтировать `/proc` (`--mount-proc`), чтобы
`ps` показывал только наши процессы.

Флаги - то что НЕ РАЗДЕЛЯТЬ:

--pid — новый PID namespace
Просим ядро дать процессам свою отдельную нумерацию PID. Внутри счёт пойдёт с 1, и процессы снаружи будут не видны. Это изоляция дерева процессов.

--fork — почему без него не работает
Тонкость: процесс, который создаёт PID namespace, сам в него не попадает — он остаётся в старом. В новый namespace попадает только его потомок. Поэтому unshare должен форкнуться, и уже дочерний bash становится PID 1 внутри. Без --fork bash запустился бы снаружи namespace, и вся затея не сработала бы.

--mount-proc — почему ps врёт без него
Главный сюрприз для студентов: ps не спрашивает ядро о процессах напрямую — он читает псевдо-файловую систему /proc, где ядро раскладывает процессы по папкам (/proc/1, /proc/1234, ...).

Проблема: новый PID namespace у нас есть, но /proc остался старый, унаследованный от хоста. В нём лежат все процессы хоста. Поэтому ps показал бы всё подряд, хотя namespace уже изолирован.

--mount-proc перемонтирует /proc заново изнутри нового namespace. Теперь ядро заполняет его только нашими процессами, и ps показывает правду — два-три процесса.

Теперь внутри:
```bash
ps -e
```
Ожидаемый вывод:
```
  PID TTY          TIME CMD
    1 pts/0    00:00:00 bash
    2 pts/0    00:00:00 ps
```
Обратите внимание: наш `bash` — это **PID 1**! Как будто мы только что загрузили
систему. Проверим:
```bash
echo $$          # 1 (текущий процесс)
```
А в **T2** (хост) в это же время:
```bash
ps aux | grep unshare      # тот же bash виден как обычный процесс с PID, скажем, 40213
```
Вывод: это один и тот же процесс. Снаружи — PID 40213, внутри — PID 1. Ядро
одно, но `namespace` показывает разный «срез». Изоляция — это не копия системы,
а точка зрения.

**На что обратить внимание.** Без `--mount-proc` команда `ps` показала бы
процессы хоста (она читает `/proc`, а он остался хостовый). Без `--fork` PID 1
получил бы сам `unshare`, а не `bash`, — было бы менее наглядно.

Выйдите: `exit`.

### UTS namespace — «своё имя хоста»

```bash
sudo unshare --uts bash
hostname container-demo
hostname                    # container-demo
```
А в **T2**:
```bash
hostname                    # имя хоста НЕ изменилось
```
Внутри namespace поменяли hostname — снаружи он прежний. Именно так у каждого
контейнера свой `hostname`. Выйдите: `exit`.

### NET namespace — «своя сеть»

```bash
sudo unshare --net bash
ip link

ip link set lo up
```
Ожидаемо: только интерфейс `lo`, и тот в состоянии `DOWN`:
```
1: lo: <LOOPBACK> mtu 65536 ... state DOWN
```
Новый сетевой namespace пуст — ни ethernet-интерфейсов хоста, ни его IP. У
контейнера — своя изолированная сеть (как её «прокидывают» наружу, разберём в
темах про сеть и Docker). Выйдите: `exit`.

**Итог блока.** Контейнер = процесс + набор namespaces (pid, net, mnt, uts, ipc,
user). Docker просто включает их все разом за вас.

## Лимиты ресурсов: cgroups v2

Namespaces отвечают на вопрос **«что процесс видит»**. Но они **не ограничивают
ресурсы**: процесс в своём namespace может съесть всю память хоста. За лимиты
отвечают **cgroups**. Докажем это.

### Готовим группу

```bash
CG=/sys/fs/cgroup/demo
sudo mkdir $CG
# убедимся, что контроллер памяти доступен потомкам:
cat /sys/fs/cgroup/cgroup.controllers          # среди них должен быть memory

ls /sys/fs/cgroup/demo
```
cgroup v2 — это просто дерево каталогов в `/sys/fs/cgroup`. Создали папку —
создали группу. Управление — через запись в её файлы.

### Лимит памяти и OOM-killer

```bash
echo 2M | sudo tee $CG/memory.max
# запускаем «прожорливый» процесс прямо в группе:
sudo bash -c "echo \$\$ > $CG/cgroup.procs; exec python3 -c \"x = 'a' * 10**9\""
```
Что здесь происходит построчно: ставим потолок 2 МБ. Затем запускаем shell,
который записывает свой PID в `cgroup.procs` (входит в группу) и через `exec`
превращается в Python, просящий гигабайт памяти.

Ожидаемый вывод:
```
Killed
```
Посмотрим, кто убил процесс:
```bash
dmesg | tail -n 3          # строки про "Memory cgroup out of memory" и "Killed process ..."
```
Вывод: процесс попросил больше лимита — **ядро его убило** (OOM-killer), при этом
остальная система даже не заметила. Вот что делает `docker run -m 50m` под
капотом.

### Лимит CPU

```bash
echo "50000 100000" | sudo tee $CG/cpu.max
sudo bash -c "echo \$\$ > $CG/cgroup.procs; exec python3 -c 'while True: pass'"
```
В **T2** запустите `top` (или `htop`): процесс держит **~50% одного ядра**, а не
100%. Формат `cpu.max` — «quota period» в микросекундах: `50000/100000` =
половина CPU-времени каждые 100 мс. Остановите: `Ctrl+C`.

period = 100000 — окно учёта, 100000 мкс = 100 мс. Ядро нарезает время такими окнами.
quota = 50000 — сколько CPU-времени группе разрешено потратить в каждом окне, 50000 мкс = 50 мс.

Итог: 50 мс из каждых 100 мс → 0.5 ядра. Отсюда ~50% в top.

Как это выглядит физически: процесс крутит бесконечный цикл, честно жрёт CPU 50 мс, потом ядро его тормозит (throttle) до конца окна — остальные 50 мс он простаивает. Так в каждом окне. В top усреднённо видно 50%.

**Уберите за собой:**
```bash
sudo rmdir $CG
```
**На что обратить внимание.** Удалить группу можно, только когда в ней нет живых
процессов. Если `rmdir` ругается — сначала завершите процессы группы.

## Скорость старта: VM против контейнера

Теперь измерим то, о чём говорили выше, — вживую, с секундомером.

### Контейнер — миллисекунды

Самый честный вариант «без Docker» — namespaces создаются мгновенно:
```bash
time sudo unshare --pid --fork --mount-proc --uts --net bash -c 'echo "привет из контейнера"'
```
Ожидаемо: `real ~0.02s`. Запустить контейнер = запустить процесс. Никакой
загрузки ОС.

Если установлен Docker — сравните и его (это заодно тизер следующей темы):
```bash
docker run --rm alpine echo hi     # первый раз — скачает образ
time sudo docker run --rm alpine echo hi    # теперь образ в кэше
```
Ожидаемо: `real ~0.4s` (почти всё — накладные расходы Docker, не «загрузка»).

### Виртуальная машина — десятки секунд

Запуск настоящей VM. Пример с `multipass` (Ubuntu):
```bash
time multipass launch --name demo 22.04     # первый запуск: real ~40–60s
# ... либо перезапуск уже созданной:
time multipass start demo                    # real ~10–20s
```
Нет `multipass` — запустите любую VM в VirtualBox/QEMU и **засеките
секундомером**: от кнопки «Старт» до приглашения логина. Всегда десятки секунд:
грузится BIOS/UEFI, ядро гостевой ОС, службы.

**Сводка:**
| | старт | вес |
|---|---|---|
| Контейнер | миллисекунды | мегабайты |
| VM | десятки секунд | гигабайты |

**Вывод.** Разница не в «мощности», а в том, что VM каждый раз **грузит целую
ОС**, а контейнер — нет. Отсюда и «плотность»: на одном сервере — тысячи
контейнеров, но лишь десятки VM.

## Образ vs контейнер

Коротко, без глубокого погружения (детали — в теме про Docker):

- **Образ** — шаблон «только для чтения», собранный из **слоёв** (базовый слой
  ОС → язык → зависимости → код).
- **Контейнер** — запущенный образ + тонкий **изменяемый слой** сверху.
- Один образ → **много контейнеров**: слои переиспользуются, не копируются
  (это делает слоистая ФС, OverlayFS).

**Аналогия.** Образ — как класс, контейнер — как объект (экземпляр) этого класса.
Из одного образа поднимают десятки одинаковых контейнеров.

## Частые ошибки и заблуждения

- **«Контейнер — это лёгкая виртуалка».** Нет. В контейнере нет своего ядра и
  своей ОС. Это процесс хоста с изолированным «видом». Вспомните блок про
  namespaces: тот же процесс, PID 40213 снаружи и PID 1 внутри.
- **«root внутри контейнера = root на хосте».** По умолчанию UID совпадают, и
  это риск. `user`-namespace умеет отобразить «root внутри» на непривилегированного
  пользователя хоста — отсюда rootless-контейнеры (подробнее в теме Docker).
- **«namespaces ограничивают память/CPU».** Нет: namespaces — это **видимость**,
  cgroups — **лимиты**. Разные механизмы, работают вместе.
- **`unshare` показал процессы хоста.** Забыли `--mount-proc` (или `--fork`):
  `ps` читает старый `/proc`. Формула наглядной демонстрации:
  `--pid --fork --mount-proc`.
- **cgroup-команды не работают / файлов нет.** Скорее всего система на **cgroup
  v1** или контроллер не включён в родителе. Проверьте `stat -fc %T /sys/fs/cgroup`
  (нужно `cgroup2fs`) и `cgroup.controllers`.
- **«Зачем это, если есть Docker?»** Чтобы, когда Docker сломается, вы понимали,
  что чинить. Docker — это обёртка над тем, что мы делали руками.

## Связь со следующей темой: Docker

Сегодня мы вручную сделали то, что делает Docker: изолировали процесс через
namespaces и ограничили его через cgroups. На следующем практическом блоке
курса — **Docker**: те же контейнеры, но одной командой, плюс образы, Dockerfile
и реестры. Магии там больше нет — только удобные обёртки над тем, что вы уже
видели своими глазами. Это фундамент ДЗ-3 и итогового проекта.
