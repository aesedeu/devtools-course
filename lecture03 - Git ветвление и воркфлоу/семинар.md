# Семинар к Лекции 3. Git: ветвление и воркфлоу

Этот конспект — разбор живой работы с ветками. Кульминация — **создать и
разрешить конфликт слияния своими руками**, а затем пройти полный цикл сдачи
через Pull Request. Все команды ниже стоит повторить в своём терминале: Git понимается только на пальцах, через практику.

## Что понадобится

- Репозиторий с 2–3 коммитами (можно продолжить `~/demo` с прошлого семинара) —
  чтобы не тратить время на подготовку.
- Настроенный доступ к GitHub; заранее создайте пустой приватный репозиторий для
  финального блока (или переиспользуйте вчерашний).
- Держите под рукой команду визуализации:
  `git log --oneline --graph --all --decorate` — запускайте её после каждого
  изменения истории, это главный «рентген» всего занятия.

## Зачем нужны ветки

Представьте ситуацию: вы пишете фичу, и тут прилетает срочный баг в проде. Как не
смешать одно с другим? Ответ — **отдельная ветка на каждую задачу**. Ветка
изолирует работу и не ломает рабочий `main`: недоделанная фича спокойно лежит в
своей ветке, а исправление бага едет отдельно.

Вспомните с прошлого занятия: ветка — это просто файл с одним хешом
(`cat .git/refs/heads/main`), поэтому создать её почти ничего не стоит. Именно
поэтому в Git ветки создают легко и часто — по ветке на каждую задачу.

## Ветка и fast-forward слияние

```bash
cd ~/demo
git switch -c feature/greeting        # создать и перейти
git branch                            # * feature/greeting — где мы
```
`*` в выводе `git branch` показывает текущую ветку. `HEAD` теперь указывает
именно на неё.

Поработаем в ветке:
```bash
echo "print('привет, мир')" >> app.py
git commit -am "add greeting"
git log --oneline --graph --all --decorate
```
После этого `feature/greeting` ушла на один коммит вперёд `main`.

Теперь сольём ветку обратно. В `main` не было новых коммитов, поэтому получится
fast-forward:
```bash
git switch main
git merge feature/greeting
git log --oneline --graph --all --decorate
```
Обратите внимание: git написал `Fast-forward`, а merge-коммита НЕ появилось —
`main` просто «догнал» ветку, передвинув указатель вперёд. История осталась
линейной.

Есть альтернатива — заставить git сохранить факт слияния отдельным коммитом:
```bash
git switch -c feature/x && echo "x=1" >> app.py && git commit -am "add x"
git switch main
git merge --no-ff feature/x -m "merge feature/x"
git log --oneline --graph --all --decorate
```
Флаг `--no-ff` (no fast-forward) заставил git создать merge-коммит — на графе
появляется характерная «дуга», по которой видно, что здесь была ветка.

## Конфликт — кульминация занятия

Конфликт слияния — это то, чего многие боятся. Разберём его медленно и увидим,
что бояться нечего.

Сначала создаём расхождение: две ветки меняют ОДНУ и ту же строку по-разному.
```bash
echo "port = 8000" > config.py
git add config.py && git commit -m "add config"

git switch -c feature/port
sed -i '' 's/8000/3000/' config.py        # (Linux: sed -i 's/8000/3000/')
git commit -am "port 3000"

git switch main
sed -i '' 's/8000/8080/' config.py
git commit -am "port 8080"
```

Теперь в `main` строка `port = 8080`, а в `feature/port` — `port = 3000`.
Пробуем слить — и получаем конфликт:
```bash
git merge feature/port
```
В выводе появится строка `CONFLICT (content): Merge conflict in config.py`. Это
не поломка: git честно сообщает, что не знает, какой порт правильный, и просит
решить вас. Он не «струсил» и не сломался — он не имеет права молча выбрать
что-то за вас.

```bash
git status                    # both modified: config.py
cat config.py
```
Разберём маркеры конфликта построчно:
```
<<<<<<< HEAD          ← ваша версия (main): 8080
port = 8080
=======               ← разделитель
port = 3000
>>>>>>> feature/port  ← версия из вливаемой ветки: 3000
```
Между `<<<<<<< HEAD` и `=======` лежит ваша текущая версия (то, что было в
ветке, куда вы вливаете). Между `=======` и `>>>>>>> feature/port` — версия из
вливаемой ветки.

Разрешаем конфликт вручную: откройте файл в редакторе, оставьте нужный вариант и
удалите все три строки-маркера. Здесь мы выбираем вариант `main`:
```bash
printf "port = 8080\n" > config.py     # выбрали вариант main
git add config.py                      # пометили как решённое
git commit                             # git уже подготовил сообщение о merge
git log --oneline --graph --all --decorate
```
Ключевая мысль: конфликт — это не поломка, а вопрос от git. Разрешение всегда
сводится к трём шагам: убрать маркеры, оставить правильное содержимое, затем
`git add` + `git commit`.

Полезно знать «кнопку отмены» на случай, если во время слияния вы запутались:
```bash
# если запутались во время merge:
# git merge --abort   ← вернёт всё как было до слияния
```

## Rebase и переписывание истории

Посмотрим на разницу с merge — она хорошо видна на графе.
```bash
git switch -c feature/rebase-demo
echo "a=1" >> app.py && git commit -am "add a"
echo "b=2" >> app.py && git commit -am "add b"
git switch main && echo "c=3" >> app.py && git commit -am "add c on main"

git switch feature/rebase-demo
git rebase main
git log --oneline --graph --all --decorate
```
Rebase «перенёс» ваши коммиты поверх свежего `main` — история осталась линейной,
но у перенесённых коммитов новые хеши. Это важный момент: rebase не двигает
существующие коммиты, а создаёт их копии поверх новой базы.

Интерактивный rebase позволяет «причесать» историю перед тем, как показывать её
другим:
```bash
git rebase -i HEAD~2
# в редакторе: второй pick → squash, объединяем два коммита в один
```
После `git log` вы увидите, что два коммита слились в один.

> **Золотое правило:** никогда не делайте rebase коммитов, которые уже видели
> другие. Переписав общую историю, вы сломаете её всей команде — у всех разъедутся
> хеши, и синхронизация превратится в кашу. Rebase хорош только для своей
> локальной, ещё никому не показанной работы.

## Спасательный круг: reflog

Смоделируем «катастрофу» и восстановление — этот сценарий хорошо запоминается.

```bash
git log --oneline                 # запомните верхний хеш
git reset --hard HEAD~2           # «ой, снёс два коммита!»
git log --oneline                 # их нет
```
После `git reset --hard HEAD~2` два верхних коммита пропали из истории — кажется,
что работа потеряна. Но это не так:
```bash
git reflog                        # журнал ВСЕХ перемещений HEAD
git reset --hard <хеш-из-reflog>  # вернули потерянное
git log --oneline                 # всё на месте
```
`git reflog` — это журнал всех перемещений `HEAD`, включая те коммиты, которые
уже не видны в обычном `git log`. Пока не прошла сборка мусора, почти ничего в
git не теряется навсегда, и `reflog` — ваш спасательный круг.

Отдельно стоит запомнить безопасную отмену для уже опубликованной, общей истории:
```bash
# git revert <commit>   ← создаёт НОВЫЙ коммит, отменяющий изменения,
#                          не переписывая историю. Безопасно для main.
```

## Полный цикл через Pull Request — прообраз ДЗ-2

Соберём всё вместе так, как устроена сдача домашней работы.

```bash
git switch -c feature/pr-demo
echo "print('via PR')" >> app.py
git commit -am "add via PR"
git push -u origin feature/pr-demo
```
Дальше работаем в браузере на GitHub:
1. Откройте Pull Request из `feature/pr-demo` в `main`.
2. Загляните во вкладку **Files changed** — это и есть diff, который видит
   ревьюер.
3. Оставьте комментарий-ревью и посмотрите, как выглядит обсуждение.
4. Запомните: **merge делает ревьюер после проверки**, автор сам ветку не сливает.

Прямая связь с ДЗ-2: в домашке ровно этот цикл. Вы чините код в ветке,
открываете PR с описанием — открытый PR это ваша заявка на проверку. Автопроверка
ставит балл и закрывает PR. Хотите пересдать — открываете новый PR.

## Частые ошибки

- **«Конфликт — всё сломалось!»** — нет, это вопрос от git; спокойно
  разрешаем маркеры (`add` + `commit`). Если запутались — перечитайте раздел про
  конфликт и пройдите шаги медленно.
- **«rebase затёр чужие коммиты»** — вот почему существует золотое правило; на
  общей ветке используйте только merge или revert.
- **«запушил не в ту ветку»** — переключитесь через `git switch` и запушьте
  заново.
- **«застрял в merge/rebase»** — есть аварийный выход: `git merge --abort` /
  `git rebase --abort`.
- **«не могу открыть PR»** — скорее всего, ветка не запушена
  (`git push -u origin <ветка>`).
